# 维护脚本密钥安全

`sync_suits.js` 和 `upload_stages.js` 是受信维护工具，不是网站功能。前者会批量写服装的套装关联，后者会写竞技场权重；本次仅清除硬编码密钥，不改变数据处理规则。不要为了测试防护而实际上传数据。

## 配置方式

两个脚本没有默认项目或默认密钥，只读取受控 Node 进程中的以下变量：

| 变量 | 含义 |
| --- | --- |
| `SUPABASE_MAINTENANCE_URL` | 本次已授权项目的 HTTPS 地址 |
| `SUPABASE_MAINTENANCE_PROJECT_REF` | 同一项目的标识，用来核对地址 |
| `SUPABASE_MAINTENANCE_SECRET_KEY` | 为维护用途单独准备的私密 API 密钥 |

缺少配置、项目不匹配、误用公开密钥或旧 JWT 密钥时，脚本在读入数据、连接数据库前停止。错误消息不显示输入值，客户端不保存或自动刷新用户登录会话。

这不是生产操作授权。development 仅使用 `nikki-calculator-dev`（`tfwejruvdahonacyldrg`），仍须遵守数据操作范围；生产维护、真实数据改写和实际凭据变更必须单独确认。脚本不会自动加载 `.env`，不得把维护密钥填入 `VITE_*`、网站配置、源文件、聊天或 PR。

## 已暴露密钥的处理

1. 在 Supabase 的生产项目 **Settings → API Keys → Secret keys** 核对已暴露密钥及使用方。不要展示或复制密钥到聊天。
2. 若仍有受信后台使用它，先在安全配置中替换为新密钥；确认不再依赖旧密钥后删除旧密钥。新增密钥不会自动停用旧密钥。不改网站公开密钥或 JWT 签名配置。
3. 回查旧密钥已删除、网站公开读取与登录正常；记录结果时只保存状态，不保存密钥值。

仅删除当前代码中的密钥不等于泄漏已解决：Git 历史和旧版本仍可能包含它。本变更不改写历史，必须以旧密钥已被服务端停用作为收口证据。若还有未核清的使用方，先停在确认环节，不宣布风险已解除。

## 验证与失败处理

`node --test tests/maintenanceClient.test.js` 使用虚构配置和替代客户端验证防护，不访问任何数据库。两个实际入口只在清除维护配置的子进程中启动，验证缺少配置立即停止。

代码问题可用前向修正恢复可用入口，但不能重新写入已暴露密钥或恢复默认生产地址。旧密钥删除不可撤销；维护中断时用新密钥恢复受信后台配置，不恢复旧密钥。没有数据库结构或业务数据变更，因此没有 migration 或数据 rollback。

参考：[Supabase API 密钥官方说明](https://supabase.com/docs/guides/getting-started/api-keys)。
