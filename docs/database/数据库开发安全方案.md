# 数据库开发安全方案

## 0. 目标

本文档用于规范 Supabase 数据库开发流程，避免在没有备份、没有环境隔离的情况下直接修改生产数据库。

当前风险状态：

- 已登记 production 与 development 两个 Supabase 项目，当前环境信息见 [`环境信息.md`](环境信息.md)。
- 执行任何数据库命令前，仍必须确认 Git 分支、目标环境和 Supabase project ref。
- 未确认 project ref 时，不得执行会读取或修改远程数据库状态的命令。
- 生产数据库操作仍必须先完成备份、development 验证、rollback 方案和用户明确确认。
- 因此，不应直接修改生产数据库，也不应把 production 当作开发测试环境。

## 1. 基本原则

1. 生产数据库不能作为开发测试环境。
2. 所有 schema 变更必须通过 migration 管理。
3. 所有 migration 必须先在开发环境验证。
4. 线上执行前必须完成备份。
5. 批量数据修复、清洗、状态迁移必须单独确认。
6. 不在前端代码中绕过数据库约束。
7. 不直接在 Supabase Dashboard 手动改生产表结构，除非是紧急修复并记录原因。

## 2. 环境规划

建议至少使用两个 Supabase 项目：

| 环境 | 用途 | 数据 | 允许操作 |
| --- | --- | --- | --- |
| `production` | 真实用户使用 | 真实数据 | 只允许已验证 migration 和必要运维操作 |
| `development` | 开发和验证 | 从生产脱敏或抽样同步 | 可反复测试 migration、RPC、RLS |

当前已登记环境见：[数据库环境信息](环境信息.md)。

Git 分支与部署环境对应关系见：[分支与环境治理规则](../governance/BRANCH_ENVIRONMENT_POLICY.md)。数据库任务必须同时确认 Git 分支、Vercel 环境和 Supabase project ref，避免把 feature / preview 工作误连到 production。

环境变量建议：

| 文件 | 用途 |
| --- | --- |
| `.env.local` | 本地开发环境，连接 development / staging |
| `.env.production` | 生产部署环境，不在本地随意使用 |
| `.env.example` | 示例变量，不包含真实 key |

前端应通过以下变量连接 Supabase：

```text
VITE_SUPABASE_URL=
VITE_SUPABASE_ANON_KEY=
```

## 3. 禁止直接执行的操作

在没有备份和开发环境验证前，不直接执行：

```powershell
supabase db push
supabase migration repair
supabase db reset --linked
supabase db remote commit
```

不直接在生产库执行：

```sql
drop table ...
drop column ...
delete from ...
truncate ...
update ... -- 批量更新且没有 where / 没有预检
alter table ... -- 未经开发库验证
create or replace function ... -- 会覆盖生产 RPC
```

允许安全准备但不影响远程的操作：

```powershell
npm run build
npm run db:types
supabase migration new <name>
supabase db diff --local
```

注意：

- `npm run db:types` 默认访问 development 项目。
- `npm run db:types:prod` 会访问 production 项目，只能在生产操作被批准后执行。
- `npm run db:dump` 依赖当前 linked project，执行前必须先确认 `supabase status`。

## 4. 备份策略

### 4.1 上线前必须备份

每次生产数据库变更前，至少完成一种备份：

1. Supabase Dashboard 备份。
2. 使用 `pg_dump` 导出 schema + data。
3. 至少导出受影响表的数据快照。

推荐备份文件命名：

```text
backups/YYYYMMDD_HHMM_production_pre_<change_name>.sql
backups/YYYYMMDD_HHMM_production_pre_<change_name>_schema.sql
backups/YYYYMMDD_HHMM_production_pre_<change_name>_data.sql
```

### 4.2 最低备份要求

如果只是新增表 / 新增字段：

- 至少备份 schema。
- 记录当前 migration list。

如果涉及数据修改：

- 必须备份受影响表数据。
- 必须先写预检 SQL。
- 必须先估算影响行数。

如果涉及 RPC 替换：

- 必须备份旧函数定义。
- 必须保留可回退版本或旧函数 SQL。

## 5. 开发库搭建流程

### 5.1 创建开发 Supabase 项目

在 Supabase Dashboard 创建一个新项目，例如：

```text
nikki-calculator-dev
```

### 5.2 本地连接开发项目

切换到开发项目：

```powershell
supabase link --project-ref <dev_project_ref>
```

确认当前链接项目：

```powershell
supabase status
```

如果需要查看远程 migration：

```powershell
supabase migration list
```

### 5.3 同步 schema 到开发库

推荐方式：

1. 使用当前仓库的 migrations 初始化开发库。
2. 如果 migrations 与生产不一致，先从生产 dump schema。
3. 在开发库执行 schema 恢复。
4. 再导入少量脱敏测试数据。

测试数据原则：

- 不导入真实用户敏感信息。
- `profiles.email` 等字段如需导入，应脱敏。
- 只导入能覆盖流程的数据：服装、套装、pending、用户角色。

## 6. Migration 开发流程

### 6.1 标准流程

1. 新建 migration：

```powershell
supabase migration new <change_name>
```

2. 在 migration 中写 SQL。
3. 在开发库执行：

```powershell
supabase db push
```

4. 重新导出 schema 和类型：

```powershell
supabase status
npm run db:dump
npm run db:types
```

5. 运行前端构建：

```powershell
npm run build
```

6. 更新：

- [`数据库变更记录.md`](数据库变更记录.md)
- [`技术实现文档.md`](../planning/技术实现文档.md)
- [`schema.md`](schema.md)

7. 开发库验收通过后，准备生产上线。

### 6.2 生产上线流程

生产执行前必须确认：

- migration 已在开发库通过。
- 已完成生产备份。
- 已写明影响表和影响功能。
- 已准备回滚方案。
- 已确认上线窗口。

执行后必须：

- 重新 dump schema。
- 重新生成 types。
- 检查关键功能。
- 更新 [`数据库变更记录.md`](数据库变更记录.md)。

## 7. 数据变更预检流程

任何批量 update / delete / insert-select 前，必须先写预检 SQL。

示例：

```sql
-- 1. 先统计影响行数
select count(*)
from public.clothes
where tags like '%中式中式%';

-- 2. 抽样检查
select id, name, tags
from public.clothes
where tags like '%中式中式%'
limit 20;

-- 3. 确认后再执行 update
update public.clothes
set tags = public.normalize_known_clothing_tags(tags)
where tags like '%中式中式%';
```

批量修改后必须复查：

```sql
select count(*)
from public.clothes
where tags like '%中式中式%';
```

## 8. RLS 安全流程

新增表后必须考虑 RLS：

| 表 | 默认策略 |
| --- | --- |
| `points_ledger` | 普通用户只能读自己的流水；写入只允许 RPC |
| `clothing_contributions` | 可公开读贡献者；写入只允许 RPC |
| `jury_votes` | 用户只能创建自己的投票；不能修改他人投票 |
| `re_review_items` | 用户可读开放项；自审限制必须在 RPC 中执行 |
| `correction_requests` | 用户可创建并查看自己的报错；管理员可处理 |
| `admin_terms` | 普通用户只读必要公开信息；超管可管理 |

RLS 验收：

1. 匿名用户不能写数据。
2. 普通用户不能改他人数据。
3. 普通用户不能伪造积分。
4. 普通用户不能越权审核自己的提交。
5. 管理员权限只通过 `profiles.role` 或 `admin_terms` 判断。

## 9. RPC 安全流程

RPC 需要满足：

- 校验当前用户。
- 校验角色和权限。
- 校验是否自审。
- 校验输入字段。
- 使用事务保证状态一致。
- 返回明确状态，不吞错。

高风险 RPC：

| RPC | 风险 |
| --- | --- |
| `submit_clothing_contribution` | 自动入库、贡献、积分写入 |
| `cast_jury_vote` | 一人一票、候选快照校验、状态流转 |
| `resolve_re_review_item` | 重审结论、正式库更新 |
| `submit_correction_request` | 正式库报错流程 |
| `award_points_for_contribution` | 积分发放 |

生产替换 RPC 前必须备份旧函数定义。

## 10. 回滚策略

### 10.1 新增表 / 字段

优先不删除，先停用入口。

可回滚方式：

- 前端隐藏入口。
- RPC 不再写入新表。
- 新字段保留但不读取。

### 10.2 RPC 出错

可回滚方式：

- 恢复旧函数定义。
- 使用新函数名发布新版 RPC，旧函数保留兼容。
- 前端切回旧调用。

### 10.3 数据错误

可回滚方式：

- 使用备份恢复受影响表。
- 对积分错误追加反向流水，不直接删除历史。
- 对错误状态追加修正记录。

### 10.4 RLS 出错

可回滚方式：

- 立即恢复上一个 policy。
- 临时关闭对应前端入口。
- 保留最小只读能力，避免数据泄露。

## 11. 上线检查清单

生产数据库变更前必须逐项确认：

- [ ] 当前 Git 分支和目标环境符合分支与环境治理规则。
- [ ] 已确认 Vercel production 仅对应 `main`。
- [ ] 已确认当前连接的是开发库还是生产库。
- [ ] 已确认 Supabase project ref。
- [ ] migration 已在开发库执行成功。
- [ ] 前端 `npm run build` 通过。
- [ ] 已完成生产备份。
- [ ] 已记录影响表、影响 RPC、影响页面。
- [ ] 已准备回滚 SQL 或回滚步骤。
- [ ] 已确认是否涉及批量数据更新。
- [ ] 已确认是否需要维护窗口。
- [ ] 已更新 [`数据库变更记录.md`](数据库变更记录.md) 草稿。
- [ ] 执行人和确认人已明确。

生产执行后必须确认：

- [ ] migration list 正常。
- [ ] schema dump 正常。
- [ ] 类型生成正常。
- [ ] 登录、图鉴查询、缺失项补录、管理员审核可用。
- [ ] RLS 未造成越权或误封。
- [ ] [`数据库变更记录.md`](数据库变更记录.md) 已补充执行结果。

## 12. 后续建议

在开始数据库开发前，建议先完成：

1. 完成生产库备份。
2. 将本地 Supabase link 切换到 development。
3. 写第一批 migration，但只在开发库验证。
4. 开发库验证通过后，再讨论是否推 production。

当前阶段推荐动作：

- 可以写 migration 草案。
- 可以写 SQL 预检语句。
- 可以写前端适配代码，但默认连接开发库。
- 不建议直接对生产库执行 `supabase db push`。

### 13.4 RPC 变更记录要求

如果变更 RPC，必须记录：

- RPC 名称。
- 旧函数定义备份位置。
- 新函数参数。
- 新函数返回值。
- 权限 grant / revoke。
- 是否 `security definer`。
- 是否校验当前用户。
- 是否校验角色。
- 是否校验自审。
- 回滚 SQL。

### 13.5 RLS 变更记录要求

如果变更 RLS，必须记录：

- 表名。
- 是否启用 RLS。
- 新增 / 修改 / 删除的 policy。
- anon 用户结果。
- authenticated 普通用户结果。
- admin 用户结果。
- super_admin 用户结果。
- 是否存在越权读取风险。
- 是否存在误封正常功能风险。
