# 产品设计书

## 0. 文档定位

本文档用于说明 Nikki Calculator 当前阶段的产品定位、目标用户、核心场景、功能边界和开发优先级。

它的作用不是替代 [`需求文档.md`](需求文档.md)，而是为需求和开发提供产品判断依据：

- 当需求变多时，用本文档判断哪些功能应该优先。
- 当功能设计出现分歧时，用本文档判断是否符合目标用户真实场景。
- 当开发遇到取舍时，用本文档判断是否会偏离“衣柜录入、图鉴维护、高分计算”的核心闭环。

本文档遵循现有项目文档：

- [`需求文档.md`](需求文档.md)
- [`开发文档.md`](../planning/开发文档.md)
- [`技术实现文档.md`](../planning/技术实现文档.md)
- [`缺陷文档.md`](../planning/缺陷文档.md)

## 1. 产品定位

Nikki Calculator 是面向《奇迹暖暖》玩家的衣柜管理、图鉴补全和高分计算工具。

当前阶段的核心定位是：

> 帮助玩家低成本录入自己的衣柜，基于个人衣柜获得可用的高分搭配结果，并通过社区贡献机制持续维护完整、可信的图鉴数据。

产品不是单纯的数据展示站，也不是泛社交社区。它的核心价值来自三条闭环：

1. **个人使用闭环**：录入衣柜 → 高分计算 → 返回游戏应用结果。
2. **图鉴维护闭环**：发现缺失 → 提交数据 → 审核入库 → 图鉴完善。
3. **社区信任闭环**：有效贡献 → 积分记录 → 信用等级 → 参与审核 → 提升数据质量。

因此，任何新功能都应优先服务这三条闭环。

## 2. 目标用户

### 2.1 普通算分用户

普通算分用户是数量最多、使用频率最高的用户。他们的主要目标是快速录入衣柜，并使用高分计算器获得搭配建议。

核心需求：

- 快速找到衣柜录入口。
- 通过搜索、批量录入、分类筛选快速管理已有部件。
- 保存个人衣柜，避免重复录入。
- 基于当前衣柜获得高分计算结果。
- 当数据不足、计算无结果或录入失败时获得明确提示。

设计原则：

- 路径短。
- 点击少。
- 移动端优先。
- 不要求用户理解审核、积分或数据库概念。

### 2.2 数据贡献用户

数据贡献用户会提交工具中缺失的新衣服、新部件或套装，是图鉴完整性的主要来源。

核心需求：

- 提交缺失服装、缺失部件或新套装。
- 补充名称、分类、短编号、星级、属性、特殊标签、套装状态等字段。
- 查看提交后的状态。
- 审核通过后获得贡献记录和积分。
- 被驳回或进入重审时知道原因和下一步操作。

设计原则：

- 表单字段清晰。
- 缺失字段要即时提示。
- 重复提交要明确拦截。
- 提交后状态要可追踪。

### 2.3 高信用玩家

高信用玩家通过长期有效贡献、正确审核和仲裁获得积分、等级和荣誉展示，是社区数据质量的重要维护者；陪审团按首次投票时的既有等级冻结 1 / 2 / 3 票权。

核心需求：

- 查看积分、等级、贡献记录和排行榜位置。
- 参与陪审团审核或仲裁。
- 通过正确提交和正确仲裁获得积分。
- 获得徽章、署名、首页鸣谢、彩名等荣誉反馈。
- 明确知道哪些内容可以审核，哪些因为自己参与过而不能审核。

设计原则：

- 信用来源可追溯。
- 陪审团计票口径清晰。
- 禁止自审。
- 荣誉展示不能影响核心数据准确性。

### 2.4 管理员用户

管理员用于处理普通投票无法解决的审核、重审、争议和高风险数据问题。

管理员分为：

- 普通管理员：独立处理既有低风险审核项，并通过多人共签参与套装、永久驳回和普通管理员治理。
- 超级管理员：站长完整保留全部业务治理、最终裁决、纠错、权限管理和技术管理权限，可单独执行，不受多人共签门槛限制。

核心需求：

- 查看待审核、重审、争议和报错修正项。
- 对数据进行通过、驳回、转入重审或最终裁决。
- 当前有效任期的普通管理员登录后可见“图鉴管理”入口，并按实际权限参与低风险单人审核或多人共签。
- 查看提交来源、字段差异、投票结果和历史记录。
- 避免审核自己提交或参与过的数据。
- 所有审核行为可追踪、可审计。

设计原则：

- 权限边界清晰。
- 高风险操作不隐藏来源记录。
- 普通管理员不能直接修改正式库历史数据；套装通过 / 驳回和永久驳回须 2 人同结论共签，手动任期、提前结束、候选排除 / 撤销须 3 人同结论共签。
- 超级管理员操作也必须留痕，但留痕不削减站长权限；超级管理员可以单独执行和纠正任何社区或自己的历史决定。
- 社区共治只增加受控共签与纠错，不改变 Lv1～Lv4 门槛、等级奖励、陪审票权、Lv2 候选资格、月度 5 席或原排序规则。

## 3. 核心使用场景

### 3.1 手机端边玩边用

用户经常在手机端同时打开游戏和网页工具，在二者之间频繁切换。

产品要求：

- 页面应适配移动端。
- 表单和按钮适合触屏。
- 切换应用后尽量保留输入状态。
- 网络恢复或页面唤醒后，用户能理解当前操作是否成功。

关联现有缺陷：

- `BUG-20260625-004`：刷新或网络波动导致录入内容丢失。

### 3.2 快速录入衣柜

用户获得新衣服后，希望快速录入到自己的衣柜中。

产品要求：

- 支持批量输入服装名。
- 已拥有、成功新增、图鉴缺失要分开展示。
- 成功录入后同步云端衣柜。
- 录入失败时保留用户输入或给出恢复方式。

### 3.3 缺失图鉴补录

用户发现工具中缺少服装或套装时，需要补充数据。

产品要求：

- 服装名称、分类、短编号、星级、五组属性为核心字段。
- 短编号必须填写，且只允许数字。
- 套装可以选择已有套装，也可以作为临时套装提交。
- 提交后进入待审核，不直接影响正式库。
- 5 次一致自动入库和管理员仲裁应使用同一套数据口径。

关联现有缺陷：

- `BUG-20260625-002`：套装选择异常。
- `BUG-20260625-003`：短编号必填和数字校验。
- `BUG-20260627-006`：正式入库后未自动加入用户衣柜。

### 3.4 高分计算

用户希望基于自己的衣柜获得关卡、竞技场、活动或主题搭配推荐。

产品要求：

- 计算结果应基于当前衣柜。
- 无结果时需要说明原因。
- 图鉴数据缺失不应让用户误以为自己操作失败。
- 计算功能优先级高于视觉权益和复杂社区功能。

### 3.5 报错与修正

用户发现正式库数据错误时，应能提交报错或修正建议。

产品要求：

- 报错不直接改正式库。
- 报错进入 `correction_requests` 或重审流程。
- 核心字段错误需要审核。
- 积分扣回、待定或修正必须通过流水记录。

## 4. 产品主流程

### 4.1 普通用户路径

```text
进入产品
  -> 登录 / 游客浏览
  -> 录入衣柜
  -> 保存云端衣柜
  -> 使用高分计算器
  -> 获得推荐结果
  -> 返回游戏应用
```

该路径是当前版本最重要的用户路径。任何后台审核、积分、排行榜功能都不应破坏该路径。

### 4.2 数据贡献路径

```text
发现缺失数据
  -> 打开缺失项补录
  -> 填写核心字段
  -> 提交到 pending
  -> 自动入库 / 陪审团 / 管理员审核
  -> 入库或重审或驳回
  -> 贡献记录与积分处理
```

关键要求：

- 提交前做字段校验。
- 提交后可追踪状态。
- 入库后记录贡献来源。
- 积分不能只写在用户资料表中。

### 4.3 审核修正路径

```text
发现正式库错误
  -> 提交报错 / 修正
  -> 生成 correction request
  -> 陪审团或管理员审核
  -> 通过后更新正式库
  -> 必要时触发重审或积分调整
```

关键要求：

- 正式库谨慎写入。
- 每次变更可审计。
- 不允许用户绕过审核直接改正式数据。

### 4.4 高信用审核路径

```text
用户获得积分
  -> 等级提升
  -> 获得等级和荣誉展示
  -> 参与可审核项
  -> 正确仲裁获得积分
  -> 提升社区数据质量
```

关键要求：

- 防自审。
- 陪审团按既有等级冻结票权。
- 审核结果可追踪。
- 高信用不等于无限权限。

## 5. 功能优先级

### 5.1 当前必须优先保障

1. 衣柜录入。
2. 云端衣柜保存。
3. 高分计算。
4. 缺失图鉴提交。
5. 套装选择 / 临时套装提交。
6. 新数据审核入库。
7. 重审和驳回状态。
8. 积分流水和贡献记录。
9. 管理员权限边界。
10. 移动端状态保留。

### 5.2 当前应推进但不能破坏主流程

1. 陪审团投票。
2. 高信用等级。
3. 排行榜。
4. 贡献者署名。
5. 正式库报错修正。
6. 管理员月度轮换。

### 5.3 当前不应优先投入

1. 社交聊天。
2. 复杂主页装扮。
3. 非核心娱乐功能。
4. 大型数据分析大盘。
5. 复杂商业化能力。
6. 动态彩名、进场提示、专属寄语等复杂视觉权益。

这些能力可以保留为后续迭代方向，但不能阻塞衣柜录入、图鉴维护、高分计算、积分记录和审核闭环。

## 6. 产品边界

### 6.1 本产品要解决的问题

- 玩家不知道自己衣柜如何用于高分搭配。
- 玩家录入衣柜成本高。
- 工具图鉴随游戏更新容易缺失。
- 缺失数据需要社区共同补全。
- 社区提交的数据需要审核，不能直接污染正式库。
- 有效贡献需要被记录和激励。

### 6.2 本产品当前不解决的问题

- 不做完整社交社区。
- 不做游戏账号托管。
- 不做自动读取游戏数据。
- 不承诺实时覆盖所有游戏更新。
- 不让普通用户直接编辑正式库。
- 不把积分总分只存在 `profiles` 中作为权威数据。

## 7. 交互设计原则

### 7.1 移动端优先

普通用户多数在手机端使用工具，因此核心页面需要满足：

- 触控区域足够大。
- 表单输入少跳转。
- 弹窗和下拉不遮挡关键内容。
- 长表单应避免误关闭和状态丢失。

### 7.2 状态保留

用户频繁切换游戏和网页，因此应尽量保留：

- 衣柜录入文本。
- 缺失图鉴补录表单。
- 搜索条件。
- 已勾选衣柜。
- 计算条件。

### 7.3 反馈明确

以下操作必须有清晰反馈：

- 保存衣柜。
- 缺失项提交。
- 审核通过。
- 审核驳回。
- 进入重审。
- 重复提交。
- 字段缺失。
- 权限不足。
- 网络失败。

### 7.4 普通用户不理解系统术语

普通用户熟悉“衣服、套装、属性、标签、关卡、分数”，但不应要求他们理解：

- 数据库表。
- RPC。
- RLS。
- 积分流水。
- 审核状态机。

因此，前端文案应使用用户能理解的语言。

示例：

- 使用“正在审核中”，少用 `pending`。
- 使用“需要补全信息”，少用 `re_review`。
- 使用“你的提交已通过”，少用 `approved`。

## 8. 数据与审核设计原则

### 8.1 正式库谨慎写入

任何会影响正式库的数据都应先进入审核或重审流程，包括：

- 新衣服。
- 新部件。
- 新套装。
- 正式库字段修正。
- 报错导致的数据修改。

### 8.2 数据可追溯

以下行为必须保留来源：

- 谁提交。
- 谁审核。
- 谁投票。
- 谁仲裁。
- 哪条 pending 进入正式库。
- 哪个修正改了正式库。
- 哪条积分来自哪个贡献。

### 8.3 防止自审

用户不能审核自己提交或参与过的数据。

防自审不应只靠前端隐藏入口，必须在数据库 RPC 或 RLS 中做限制。

### 8.4 积分流水化

积分权威来源应是 `points_ledger`。

产品层要求：

- 积分发放可追踪。
- 积分扣回应追加负数流水。
- 积分待定不进入正式榜单。
- `profiles` 不保存权威总分。

### 8.5 权限分层

权限设计应区分：

- 匿名用户。
- 普通用户。
- 高信用玩家。
- 普通管理员。
- 超级管理员。

不同角色看到的入口和可执行操作应不同。

## 9. 当前版本验收标准

### 9.1 普通用户验收

- 可以登录。
- 可以录入衣柜。
- 可以保存云端衣柜。
- 可以查看已拥有部件。
- 可以使用高分计算器。
- 移动端不出现明显遮挡、卡死或表单丢失。

### 9.2 数据贡献验收

- 可以提交缺失部件。
- 短编号必填且只允许数字。
- 可以选择已有套装。
- dev 库无套装时可提交临时套装名。
- 提交失败有原因提示。
- 提交成功后进入待审核。

### 9.3 审核验收

- 管理端可以看到待审核项。
- 5 次一致自动入库逻辑不被重复提交污染。
- 管理员仲裁入库可用。
- 套装审核可由 2 位不同的当前有效任期普通管理员同结论共签通过 / 驳回，或由超级管理员单独通过 / 驳回。
- 审核行为后状态变化可查。

### 9.4 数据安全验收

- Preview 环境连接 dev Supabase。
- Production 环境连接 production Supabase。
- 不提交 `.env.local`。
- 不提交 `supabase/.temp`。
- 数据库变更通过 migration。
- 生产数据库变更前先备份和确认。

## 11. 产品风险清单

### 11.1 高风险

1. 正式库被未经审核的数据污染。
2. 积分只存总分，无法追溯来源。
3. Preview 或测试环境误连生产库。
4. 用户可以审核自己的提交。
5. 重复提交污染自动入库判断。

### 11.2 中风险

1. 移动端切换应用导致表单丢失。
2. 套装名称重复或相似导致错误归类。
3. 等级展示字段被误用于计票，导致少数用户过度影响审核。
4. 管理员权限边界不清导致越权修改。
5. 缺失项入库后未同步用户衣柜，影响贡献体验。

### 11.3 低风险

1. 荣誉权益过度复杂，拖慢核心流程。
2. 排行榜和视觉激励提前开发，分散核心开发资源。
3. 商业化需求过早进入，影响普通用户体验。

## 12. 后续迭代建议

### 12.1 第一优先级

- 修复缺失图鉴补录体验缺陷。
- 完善本地草稿保存。
- 建立贡献记录和积分流水。
- 明确入库后是否自动加入用户衣柜。

### 12.2 第二优先级

- 建立重审池。
- 建立陪审团投票。
- 建立报错修正流程。
- 建立用户积分和等级展示。

### 12.3 第三优先级

- 排行榜。
- 首页鸣谢。
- 贡献者署名。
- 管理员月度轮换。

### 12.4 暂缓

- 动态彩名。
- 进场提示。
- 专属寄语。
- 广告免除。
- 打赏体系。
- 社交聊天。

## 13. 产品守护线

后续任何新增功能，如果不能回答以下问题，应暂缓：

1. 它是否帮助用户更快录入衣柜？
2. 它是否帮助用户更准确算分？
3. 它是否帮助图鉴数据更完整？
4. 它是否提高审核可信度？
5. 它是否保留了数据来源和审计记录？
