- 前 3 展示贡献者：从前 5 有效提交者中按提交时间排序取前 3 个用于页面展示。
- 陪审投票保存等级与票权快照：Lv0/Lv1 为 1 票，Lv2/Lv3 为 2 票，Lv4 为 3 票；历史票不随升级或降级追改。

- `re_review_items` 是待补套装状态的权威追踪来源。
- 待补套装状态在绑定正式套装后自动关闭。
- 重审池采用“社区参与、系统处理、管理员兜底”：未参与原始提交的登录用户可以提交完整补充资料，原提交者和来源参与者不得自审；普通用户不能直接覆盖正式库。

### 积分流水 `points_ledger`

- 第一版目标：记录通过审核、补全、重审修正、报错修正等行为产生的积分流水；`points_ledger` 作为积分唯一权威来源。

- 第一版口径：图鉴审核通过后积分默认 `awarded` 并立即生效；报错推翻非空原值时按已确认规则追加基础积分和等级奖励的负数流水。

### 贡献者记录

- 第一版目标：入库时记录前 5 个有效提交者；服装详情或后续展示最多展示前 3 位贡献者。
- 不做什么：第一版不做复杂荣誉、动态彩名、首页鸣谢、广告免除。
- 第一版口径：前 5 有效提交者从与最终入库数据一致的提交者中按提交时间排序取前 5；前 3 展示贡献者从前 5 中按提交时间排序取前 3。

### 重审池 `re_review_items`

- 第一版目标：承接缺套装、字段冲突、字段缺失、被报错后需要修正的数据，形成可追踪状态。
- 不做什么：不允许普通用户绕过陪审团门槛直接覆盖正式库。
- 第一版口径：用户明确选择“所属套装待确认”且编号、核心字段完整时允许正式入库，同时创建 `re_review_items`；纯散件不创建该重审项。
- 社区参与：未参与原始提交的登录用户可查看开放项，并针对全部缺失或冲突字段提交一份完整资料；数据库必须阻止原提交者和来源参与者自审，管理员只作为兜底。

### 报错修正 `correction_requests`

- 第一版目标：用户可对正式库条目提交单字段错误报告和建议修正，并直接进入社区陪审流程。
- 不做什么：第一版不做公开留言板、不做建议点赞排序、不自动改正式库。
- 当前阶段：用户先选择正式服装和明确问题字段；页面默认显示并带入当前值，分类、星级、属性和套装使用结构化选项，也允许在没有合适选项时手动填写。提交相同内容可安全重试，同一活动字段不得覆盖改写。
- 目标边界：新报错原子进入该服装唯一的活动陪审项，不等待管理员转交、不直接修改正式资料；报错者作为来源禁止自审。审核单同时列出正式资料中的其他缺失字段，最终精确采用报错建议时唯一 `+5`，转陪审时不提前奖励。
- 扣回边界：不按字段名称划分风险；只要最终批准的报错替换了非空原值，就按来源 pending 的该字段快照精确扣回与旧值一致的原贡献积分及其等级奖励。

## 1. 用户、积分与荣誉体系

### 1.1 积分规则

积分来源：

1. 新增部件通过审核后，提交数据与最终录入数据完全一致的用户获得积分，积分 +10。
2. 多人提交制下，符合最终入库数据的提交者都可获得积分。
3. 参与仲裁且仲裁结果正确，积分 +10。
4. 同一用户对同一 `category + game_id` 只能计分一次。
5. 自动入库只奖励前 5 个有效提交者；与最终入库数据一致的提交者按提交时间取前 5。
6. 重复提交、低质量提交不计分。
7. 重审改正者和原始错误提交者的积分分别记录；重审修正按已确认分值奖励，不与原贡献扣回合并为一条流水。
8. 报错最终推翻非空原值时，按来源 pending 的被修正字段快照精确扣回命中的原贡献基础积分及其等级奖励；其他贡献不受影响。

积分数据来源：

- `points_ledger` 是积分的唯一权威来源。
- `profiles` 不保存权威总分，避免用户资料表与积分流水不一致。
- 总分、等级、排行榜通过 SQL view / RPC 汇总生成。
- 后期如有性能压力，可增加积分缓存表，但缓存只用于展示加速，必须能从 `points_ledger` 重建。

### 1.2 积分排行榜

排行榜类型：

- 总榜：累计全部 `awarded` 流水，实时排名。
- 当月榜：按 `Asia/Shanghai`（UTC+8）自然月汇总 `awarded` 流水，实时排名。
- 上月榜：每月 1 日北京时间 00:05 冻结上一完整自然月的积分与 dense rank 名次；首次启用时补冻最近一个已结束自然月。
- 同分用户并列同一名次，后续名次连续计算。
- 仅登录用户可见；展示公开名称、积分、名次和当前用户标记，不返回 email、账号 ID 或积分流水。
- 上月榜冻结后不因积分流水变化而追改；公开名称与账号注销状态仍按当前事实展示。

后续候选（不属于本次上月榜冻结范围）：

- 上月排名前 10 的活跃用户网站首页滚动鸣谢。
  - 活跃用户：当月至少有 5 次提交行为或审核行为。
- 当月榜首可获得 Lv4 限时体验权益，下个月 1 日回收。
- 广告免除权。

### 1.3 高信用玩家等级

等级名称、门槛和铜 / 银 / 金 / 皇冠静态主题保持不变。第一版功能性权益如下：

| 等级 | 名称与门槛 | 额外积分 | 陪审票权 | 审核与管理员资格 | 分级数据查看 |
| --- | --- | ---: | ---: | --- | --- |
| Lv0 | 未评级，0 分 | 0 | 1 | 保留查看、提交候选和投票；无管理员资格 | 公开数据和本人总积分 |
| Lv1 | 见习搭配师，500 分 | +1 | 1 | 同 Lv0 | 增加本人积分流水 |
| Lv2 | 资深收集者，2000 分 | +2 | 2 | 首次投票可附 200 字内复核意见；可进入月度候选池 | 增加本人贡献、投票及当月匿名社区统计 |
| Lv3 | 图鉴守护者，5000 分 | +3 | 2 | 同 Lv2 | 增加最近 12 个月按原因、结果汇总的匿名统计 |
| Lv4 | 奇迹编年史官，10000 分 | +5 | 3 | 同 Lv2 | 增加匿名管理员任期、低风险处理和积压统计 |

Lv4 特殊规则：

- 累计 10000 分获得的 Lv4 权益为永久权益。
- 当月榜首体验权益不在第一版自动授予范围。
- Lv4 的首次投票按 3 票冻结；任何等级的旧票均不追改。
- 不允许审核自己的提交。

积分与投票固定边界：

- 额外积分只叠加于成功结算的入库、补全、重审修正和报错采纳；陪审首次投票的 `+1` 不叠加等级奖励。
- 按奖励发生前的等级快照计算，升级当次和历史流水均不追补；奖励作为关联基础流水的独立唯一流水，扣回同步追加负数流水。
- 额外积分计入等级、总榜、月榜和管理员候选冻结积分，但奖励流水不重复计为有效行为次数。
- 通过必须至少有 5 位不同用户赞成，且加权赞成票高于加权反对票；退回必须至少有 3 位不同反对用户，且加权反对差达到 3。
- Lv2 以上的复核意见只允许在首次投票时提交，不可修改、不另奖积分；对陪审员匿名展示等级，对管理员保留审计来源。
- 月度管理员候选按冻结时累计积分等级要求 Lv2 以上，并继续满足至少 5 次有效行为、最多 5 席、排除、任期和原排序规则。等级不自动授予管理员权限，任期内降级不提前撤权。

激励展示：

- 服装详情页展示贡献者名单，最多展示前 3 位。
- 前 3 位展示贡献者从前 5 个有效提交者中按提交时间排序取前 3。
- 所有有效贡献者均显示当前公开名称；Lv0 使用普通样式，Lv1 起显示正式贡献者署名标识。
- Lv2 只做视觉强调，不改变既有前 3、前 5和时间排序。

## 2. 管理员制度

### 2.1 普通管理员

来源与任期：

- 普通管理员每月 1 日轮换。
- 北京时间 00:10 在上月榜冻结成功后执行；候选必须至少有 5 次上月正向有效积分行为。
- 按上月冻结积分、有效行为数、最后有效行为时间和用户 ID 固定排序，选出最多 5 位；不足时保留空席，不降低门槛。
- 超级管理员、已有有效手动/过渡任期用户、已注销账号和命中有效排除记录的用户不参与月度席位。
- 月初候选顺序固定；退出、撤销或新增排除后按顺序自动补位。
- 任期结束后自动收回权限。
- 手动任期不占月度五席，必须填写原因和明确结束时间，最长 31 天。

权限范围：

- 只可处理“新增服装多数审核”：正式库不存在、完整资料至少由 5 位不同用户支持、无最高票并列，允许存在少数不同意见。
- 通过只采用多数资料并保留少数意见；驳回必须填写原因且允许用户重新提交。
- 不可处理高风险项、争议项、自己参与过的项。
- 不显示自己提交或参与过的数据审核入口。
- 无数据库后台管理权限。
- 不能直接编辑正式库历史数据。
- 只能通过审核流程产生新增或状态变更。

### 2.2 超级管理员

权限范围：

- 拥有普通管理员所有权限。
- 可对高风险项和争议项做最终裁决。
- 拥有用户管理入口，可手动授权或取消普通管理员权限。
- 可维护带原因和有效期的候选排除，查看候选跳过原因、任期历史与低风险审核审计。

## 3. 服装录入与审核机制

### 3.1 数据库分层

现有正式库：

现有待审核库：

- `pending_clothes`：待审核衣物提交。
- `pending_suits`：待审核套装提交。

规划重审库：

- 用于保存字段缺失、字段冲突或被报错的数据。
- 允许用户补全或修正字段。
- 修正后重新进入 `pending` 流程。

规划贡献与积分记录：

- `clothing_contributions(event_id, clothes_id, user_id, source_pending_id, contribution_type, contribution_rank, source_created_at)`：记录正式入库后的贡献事实、来源和稳定排名；不复制积分值或积分状态。
- `points_ledger(user_id, delta, status, source_type, source_id, reversal_of, occurred_at)`：作为积分唯一权威流水，记录发放、扣回及其来源。

### 3.2 服装录入规则

录入方式：

- 新增服装按照 `分类 + 短编号` 的形式录入。
- 名称、分类、短编号、星级、五组属性、套装状态为核心字段。
- 特殊标签为选填字段。

部件自动仲裁：

1. 编号和套装信息完整，且 5 次提交完全一致，自动进入正式库。
2. 缺套装但编号完整，可进入正式库，并创建 `re_review_items` 记录追踪待补套装状态。
3. 缺编号的数据不参与自动仲裁，直接进入重审或补全流程。
4. 累计 5 次提交但字段不一致，进入人工仲裁或重审。

缺套装追踪：

- 缺套装但编号完整的数据允许进入正式库。
- 待补套装状态通过 `re_review_items` 追踪。
- 如后续新增 `clothes.needs_suit_review`，它只作为查询加速或冗余标记，权威流程仍以 `re_review_items` 为准。

套装自动仲裁：

1. 套装名称 3 次相同提交可直接入库。
2. 套装名称存在相似但不完全相同的情况，进入仲裁池，由用户选择或管理员裁决。

### 3.3 陪审团制度

陪审团行为：

- 同一件服装同时只对应一个开放审核项；每个审核项只对应一份内容完整且投票期间不可替换的待审核资料，用户只能投赞同或反对。
- 页面一次只展示一张审核卡片；移动端支持左右滑动切换，单张卡片内部纵向滚动。
- 每位用户只保留一条不可修改的投票事实，并按首次投票时等级冻结 1 / 2 / 3 票权；通过与退回同时保留不同用户人数门槛。
- 用户不能审核自己提交或参与过的来源数据。
- 管理员可以按普通陪审员身份投一票，但投票后不能再对同一审核项执行管理员终审；管理员终审单独记录，不写入 `jury_votes`。

流转规则：

1. 只有完整服装资料可以进入投票；已一致字段保持只读，只允许修改审核项列出的缺失或冲突字段。
2. 同意票数达到 5 且多于反对票数后，系统按本轮完整资料自动修改正式库。
3. 资料不完整时保留在重审池，由其他用户补充或核对全部问题字段后再进入投票。
4. 反对票数比同意票数至少多 3 时，自动退回重审并要求重新补充；不得修改正式库，不得关闭或永久驳回审核项。
5. 未达到通过或退回门槛时，审核项保持投票状态，继续投票。
6. 永久驳回只能由未参与该项投票的管理员通过独立终审决定。

### 3.4 重审制度

进入重审的情况：

- 缺编号。
- 字段缺失。
- 5 次提交后字段仍不一致。
- 陪审团反对票数比同意票数至少多 3，审核项退回并要求重新补充完整资料。
- 正式库数据被用户报错后需要修正。

重审要求：

- 用户需要补全或审核部件信息。
- 名称、分类、短编号、星级、五组属性、套装状态必须明确。
- 特殊标签可为空。

退出重审：

- 重审修正后进入 `pending`。
- 待审核资料完整、同意票数达到 5 且多于反对票数时，按本轮完整资料修改正式库并移除重审列表。

### 3.5 审核状态流转

```text
pending
  -> approved -> clothes
  -> re_review
  -> rejected

re_review
  -> pending
  -> admin_review
  -> abandoned

admin_review
  -> approved
  -> re_review
  -> rejected
```

## 4. 用户反馈与报错机制

### 4.1 留言板

留言板分为两个模块：

- 错误报告：优先级最高。
- 优化建议：支持点赞机制，高赞优先更新。

优化建议流程：

```text
玩家提议 -> 开发者审核评估 -> 计划中 / 技术无法实现
```

留言板建议点赞与陪审团计票分离；第一版所有登录用户点赞权重相同，只用于产品排序参考。

第一版详细公开范围、提交限制、不可编辑 / 撤回、排序、状态、超级管理员处理、隐私、审计和滥用边界以 [`DECISIONS.md`](../ai/DECISIONS.md#优化建议留言板与点赞排序第一版) 为准。匿名可读、登录可提交与点赞；不与图鉴报错、技术日志、积分、等级或管理员轮换复用业务事实。

### 4.2 报错功能

报错流程：

```text
用户选择问题字段、建议内容并上传游戏内图鉴图片
  -> 生成 correction request
  -> 直接进入陪审团审核
  -> 通过后更新 clothes
```

- 新报错必须上传 JPG、PNG 或 WebP 格式的游戏内图鉴图片，单张最大 8 MB。
- 图片空间为私有；报错者可查看自己的图片，当前有资格参与对应事项的陪审员可在审核卡片中查看，其他登录用户和匿名用户不可读取。
- 补丁生效前的历史报错可保留为空，不要求回填图片。

积分规则：

- 报错未推翻非空原值时，原贡献者积分不调整；包括空字段补全、未采纳、退回重审和仍在投票。
- 报错最终采用新值并推翻非空原值时，只对来源 pending 在被修正字段上等于原值的原贡献，追加基础积分全额负数流水，并同步扣回关联等级奖励；不修改原流水、贡献记录或公开归属。

## 7. 需求审核与逻辑风险

### 7.1 高优先级风险

1. 陪审团审核项必须绑定单一完整且投票期间不可替换的资料，否则用户投票可能把缺字段或未收敛的冲突数据直接推入正式库。
2. 积分扣回必须流水化。`points_ledger` 是权威来源，报错推翻原资料时由同一事务追加关联原流水与报错请求的负数流水，不直接修改用户总分。
3. 加权票必须同时保留不同用户人数门槛，不能让单个高等级用户独立通过或退回；等级快照不得反向改写历史票。

### 7.2 中优先级风险

1. 管理员“每月前 5 活跃用户自动轮换”需要排除处罚用户、异常刷分用户和当月无登录用户。
2. 已通过“是否最终替换非空原值 + 来源 pending 字段快照是否等于旧值”消除原贡献积分边界冲突，不再按字段名称主观区分核心或非核心错误。
3. 套装 3 次相同入库需要去重约束，否则相同套装可能重复进入 `suits`。
4. 同一用户对同一 `category + game_id` 只能计分一次，但 `game_id = N` 或缺编号时无法形成稳定唯一键，需要单独规则。

### 7.3 低优先级风险

1. 高信用等级里的视觉权益较多，建议等核心审核闭环稳定后再实现。
2. 留言板建议点赞只用于产品排序参考，不与陪审团票数或等级挂钩。
3. 广告免除权依赖商业化方案，当前可以保留为待定，不宜阻塞审核主流程。

### 7.4 下一步建议

优先实现顺序建议：

1. 先只建立空的 `clothing_contributions` 与 `points_ledger` 基础事实表、约束和默认拒绝权限，保证后续贡献和积分可审计。
2. 基础表在 development 验证通过后，再单独建立最小积分 / 贡献者只读查询面；不在 DB-1 同时创建汇总视图。
3. 建立 `re_review_items`，承接缺套装但可入库的数据、字段冲突和其他重审状态。
4. `jury_votes` 已把一人一条投票、等级 / 票权快照、去重、防自审、复核意见不可修改和投票期间内容不可替换的边界固化到数据库。
5. `correction_requests` 受理入口已把正式库报错从普通 pending 中拆开；后续单独接入管理员处理和争议项转重审。
6. 排行榜上月冻结榜独立交付后，再评估管理员轮换和高信用视觉权益。
