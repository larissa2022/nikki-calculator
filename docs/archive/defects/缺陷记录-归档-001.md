## BUG-20260625-002 缺失图鉴提交套装选择异常

### 现象

- 缺失图鉴提交表单中，套装选项不可用或无有效选项。
- 选择套装后，表单没有正确展示已选择套装。
- 部分情况下页面会卡死，影响继续录入。

### 影响

- 用户无法可靠提交带套装信息的缺失图鉴。
- 可能导致数据进入 `pending_clothes` 时缺少 `suit_id` / `suit_name` / `temp_suit_name` 等字段。
- 如果页面卡死，用户已填写内容会丢失。

### 期望行为

- 支持搜索并选择已有套装。
- 选择后在表单中稳定展示套装名称。
- 如果没有匹配套装，应允许录入临时套装名或明确提示“无套装”。
- 不应因套装搜索、选择或清空导致页面卡死。

### 建议修复方向

1. 检查缺失图鉴提交表单中套装搜索数据源。
2. 统一 `suit_id`、`suit_name`、`temp_suit_name` 的前端状态。
3. 增加套装选择后的回显逻辑。
4. 对空结果、清空选择、网络错误增加兜底状态。

### 修复记录

- 2026-06-27：共享表单增加“已选择套装 / 临时套装 / 散件提交”状态回显。
- 2026-06-27：用户编辑套装搜索框时自动清空旧 `suit_id`，避免文本和真实套装 ID 不一致。
- 2026-06-27：dev 库无套装数据时展示空态提示，允许继续输入临时套装名并申请。
- 2026-06-27：新增 development-only 测试数据脚本 `docs/database/dev_test_data.sql`，用于在 dev 库插入测试套装。
- 2026-06-27：补充修复套装典藏馆数据源。典藏馆不再只从 `clothes.suit_name` 聚合套装，也会读取正式 `suits` 表；正式套装即使暂无部件，也会作为未集齐套装展示，并提示“待补部件”。

## BUG-20260625-003 缺失图鉴提交短编号缺少必填校验

### 现象

- 缺失图鉴提交时，短编号可以为空或显示为 `N`。
- 游戏内服装必然存在短编号，因此空短编号不是有效数据。

### 影响

- 缺失项进入待审核后无法和图鉴条目稳定匹配。
- 可能影响“5 次相同提交自动入库”的确定性判断。
- 管理端需要人工补齐短编号，增加审核成本。

### 期望行为

- 短编号为必填。
- 仅允许有效编号格式。
- 未填写时阻止提交，并提示“请填写游戏内短编号”。

### 建议修复方向

1. 在缺失图鉴提交表单增加短编号必填校验。
2. 提交 RPC 前再次校验，避免绕过 UI。
3. 如果后续确认短编号只允许数字，应增加数字格式校验。

### 修复记录

- 2026-06-27：前端提交前增加短编号校验，空值和非数字值均阻止提交。
- 2026-06-27：共享表单短编号输入框改为数字输入提示，不再提示 `N`。
- 2026-06-27：新增数据库 migration，在 `submit_clothing_contribution` RPC 内校验短编号只允许数字，避免绕过前端提交非法值。
- 已验证：Preview 环境中空值、`N`、字母均被拦截，数字短编号允许提交；2026-06-30 人工回归确认按分类 + 短编号录入衣柜通过。

## BUG-20260625-004 刷新或网络波动导致录入内容丢失

### 现象

- 缺失图鉴提交流程中，页面刷新、网络波动或请求失败后，已填写内容容易丢失。

### 影响

- 用户需要重复录入，体验差。
- 长表单更容易因一次失败造成数据损失。

### 期望行为

- 表单内容在提交前可临时保存。
- 请求失败时保留当前填写内容。

2. 按用户和表单类型区分草稿 key。
3. 表单字段变化时节流保存。
4. 提交成功后清理草稿。
5. 恢复草稿时给出明确提示，避免用户误用旧数据。

## BUG-20260625-005 `profiles.role` 使用 text 存储存在权限风险

### 现象

- 当前 `profiles.role` 为 `text`。
- 角色值使用 `user`、`admin`、`super_admin` 字符串区分。

### 风险

- 容易出现拼写错误、大小写不一致或非法角色值。
- 前端、RPC、RLS 中的字符串判断可能不一致。
- 后续如果加入更多角色，字符串散落会提高维护成本。

### 期望行为

- 数据库存储稳定枚举值，例如：
  - `0`：普通用户
  - `1`：普通管理员
  - `2`：超级管理员
- 前端使用 option / 常量表映射展示文案和权限含义。
- RPC / RLS 使用统一函数判断权限。

### 建议修复方向

1. 设计 `role_level` 或等价数字字段。
2. 迁移现有 `role` 字符串到数字值。
3. 保留兼容期，避免一次性破坏现有前端和 RPC。
4. 更新 `is_super_admin()`、管理员判断函数、前端权限展示。
5. 迁移完成后再考虑删除旧 `role` 字段。

### 修复记录

- 2026-06-27：development 已新增 `profiles.role_level`，并从旧 `profiles.role` 回填。
- 2026-06-27：新增 `profiles_role_level_check` 约束，限制角色等级只能为 `0 / 1 / 2`。
- 2026-06-27：新增同步触发器，兼容旧代码写 `role` 和新代码写 `role_level`。
- 2026-06-27：`is_super_admin()`、`is_admin_or_super_admin()` 已改为优先识别 `role_level`，并兼容旧 `role`。
- 2026-06-27：前端新增角色映射工具，管理入口、权限大盘和用户权限修改已接入统一判断。
- 2026-06-27：用户验证角色权限冒烟流程无误。

## BUG-20260627-006 缺失图鉴正式入库后未自动加入用户衣柜

### 现象

- 用户提交缺失图鉴后，缺失部件经过自动入库或管理员审核进入正式 `clothes`。
- 正式库已经出现该部件，但提交用户的 `user_wardrobes.owned_clothes` 没有自动加入该部件。

### 影响

- 用户贡献了缺失部件，但自己的衣柜状态不会自动更新。
- 用户需要再次手动录入同一部件，体验不完整。
- 后续如果要做贡献奖励、署名和衣柜联动，这里会形成数据闭环缺口。

### 期望行为

- 缺失图鉴正式入库成功后，应自动把正式 `clothes.id` 加入符合条件用户的 `user_wardrobes.owned_clothes`。
- 自动入库时，应覆盖触发本次自动入库的当前提交者，以及此前参与同一缺失项、且被本次 5 次一致规则命中的所有有效提交者。
- 管理员仲裁入库时，应覆盖该仲裁聚类下所有 `pending_clothes` 原提交者。
- 不能只覆盖最终被系统选为参考数据的提交者。

### 已确认规则

1. 自动加入衣柜的对象是“所有有效提交者”，不是“参考数据提交者”。
2. 管理员手动仲裁入库时，也自动加入该聚类下所有原提交者衣柜。
3. 如果用户衣柜中已经存在该 `clothes.id`，只去重，不重复写入。
4. 本次先按“被管理员纳入同一仲裁聚类的提交者”处理；如果后续需要排除错误提交者，需要在仲裁 UI 增加“无效提交者”标记。

### 建议修复方向

1. 在入库 RPC 或管理员审核入库逻辑中集中处理衣柜写回。
2. 使用数据库函数对 `user_wardrobes.owned_clothes` 做 upsert 和去重。
3. 避免前端直接承担正式入库后的衣柜同步，防止刷新、断网或多端登录导致漏写。
4. 与 `clothing_contributions` 表设计一起处理，确保贡献记录和衣柜写回使用同一批有效贡献者。

### 修复记录

- 2026-06-27：新增 migration `20260627143000_sync_approved_clothes_to_submitter_wardrobes.sql`。
- 2026-06-27：新增数据库内部函数 `add_clothes_to_submitter_wardrobes(user_ids, clothes_id)`，集中对 `user_wardrobes.owned_clothes` 做 upsert 和去重。
- 2026-06-27：替换 `submit_clothing_contribution`，自动入库时将新衣服同步到所有被 5 次一致规则命中的提交者衣柜。
- 2026-06-27：新增 `approve_pending_clothes_arbitration` RPC，管理员仲裁入库时由数据库统一完成正式入库、pending 标记通过、所有提交者衣柜写回。
- 已验证：dev / Preview 环境中缺失图鉴正式入库后，所有有效提交者衣柜可自动获得入库部件；2026-06-30 Preview / production 人工回归确认提交者衣柜写回通过。

## BUG-20260627-007 套装典藏馆全部套装刷新慢且经常不刷新

### 现象

- 套装典藏馆页面刷新速度较慢。
- “全部套装”列表经常不刷新或刷新不及时。
- 用户可能需要多次刷新页面，才能看到最新的套装状态或套装列表。

### 影响

- 用户无法可靠判断当前套装数据是否已经同步。
- 新增套装、套装部件入库或衣柜状态变化后，页面展示可能滞后。
- 会影响“未集齐 / 已集齐 / 全部”套装筛选的可信度。

### 期望行为

- 进入套装典藏馆时，应稳定加载当前 dev / production 库中的最新套装数据。
- 用户切换“全部 / 已集齐 / 未集齐”时，列表状态应立即按当前数据重新计算。
- 新增套装或衣柜变化后，应能明确触发刷新，避免用户依赖浏览器整页刷新。
- 加载慢时应显示明确 loading 状态，失败时应显示可重试状态。

### 初步判断

- 可能与套装数据和衣柜数据分开加载、缓存命中、IndexedDB / 本地缓存未失效、组件 mounted 后未重新拉取有关。
- 也可能是 `SuitGallery.vue` 在合并 `suits` 表和衣柜内套装部件时，缺少统一的刷新入口或加载状态。
- 如果 `clothes` 或 `suits` 更新后仍复用旧缓存，前端会出现“数据库已有但全部套装不刷新”的感知。

### 建议修复方向

1. 梳理 `SuitGallery.vue` 的数据来源：`suits` 表、`clothes` 表、用户衣柜、前端缓存。
2. 增加显式刷新函数，进入套装典藏馆或点击刷新时重新拉取 `suits` 和必要的衣柜 / 图鉴数据。
3. 检查 `useWardrobe.loadData()` 的缓存判断逻辑，避免仅用 `clothes` 数量判断缓存是否有效。
4. 为套装典藏馆增加 loading / error / retry 状态。
5. 如果刷新慢来自全量查询，应评估分页、字段裁剪或数据库视图。

### 修复记录

- 2026-06-27：`useWardrobe.loadData()` 增加 `force` 参数，可绕过 IndexedDB 旧缓存重新拉取 `clothes` 和 `stages`。
- 2026-06-27：进入“套装图鉴”页时触发 `refresh-catalog`，强制刷新图鉴数据，并重新同步当前用户衣柜。
- 2026-06-27：`SuitGallery.vue` 增加套装列表刷新按钮、loading 状态、错误提示和重试入口。
- 验证记录：2026-06-30 Preview / production 人工回归通过，套装选择与刷新稳定，套装数据可正常显示与更新。

## BUG-20260627-008 所属套装下拉偶发数据缺失

### 现象

- 缺失图鉴补录表单中，“所属套装”下拉偶发只显示“无关联套装（纯散件）”和“暂无套装数据”。

### 影响

- 如果用户未刷新直接提交，可能导致本应关联正式套装的缺失部件进入无套装或临时套装路径。
- 因刷新后可恢复，当前不判定为高风险数据缺陷。

### 初步判断

- 可能是 `availableSuits` 尚未加载完成时，`ClothesEntryForm.vue` 已先渲染下拉空态。

- 权重：低。
- 暂不作为主线修复项，优先观察复现频率。
- 若后续出现“刷新后仍缺失”“提交数据被污染”“多用户稳定复现”，再提升为中优先级修复。

### 建议处理方向

1. 为 `ImportZone.vue` 的套装列表加载增加 loading 状态，避免未加载完成时显示“暂无套装数据”。
2. 在打开缺失项补录表单时，如果 `availableSuits` 为空，可尝试重新拉取一次套装列表。
3. 在“暂无套装数据”文案中区分“加载中”和“数据库确实为空”。
4. 若继续复现，再考虑给所属套装下拉增加手动刷新按钮。

### 历史验收补充

- 2026-06-30 Preview / production 人工回归通过，套装选择与刷新符合预期，状态收口为“已关闭”。

### 现象

- 缺失图鉴补录表单点击提交后，按钮长时间停留在“正在提交申请...”。
- 页面看起来没有继续响应，用户无法判断是仍在提交、提交成功未返回，还是网络已经假死。
- 刷新页面后，通常可以重新提交。

### 影响

- 用户容易误以为数据正在提交，长时间等待。
- 可能导致重复刷新、重复提交或放弃补录。
- 如果没有明确提示，用户不知道本地草稿是否保留，也不知道下一步应该等待还是刷新。

### 初步判断

- 旧逻辑只对 RPC 上传阶段做超时赛跑。
- 提交前的云端短编号查重请求如果网络假死，超时保护不会触发，按钮会一直保持 submitting 状态。
- 属于前端网络状态提示和全链路超时保护不足。

### 期望行为

- 整个云端提交流程都应有超时保护，包括短编号查重和最终 RPC 提交。
- 请求超过数秒仍未返回时，应在按钮附近提示“网络响应较慢，草稿已保存，可刷新后重试”。
- 超时后应解除按钮锁定，并明确询问用户是否刷新页面。
