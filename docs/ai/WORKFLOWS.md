# Codex 单人开发工作流

## 0. 用途与权威关系

本文档记录可调整的执行步骤。自动入口是仓库根目录 `AGENTS.md`，强规则是 [`RULES.md`](RULES.md)，产品 Final 口径是 [`DECISIONS.md`](DECISIONS.md)。当前执行状态从本地分支、工作区和开放 PR 得出；冲突时以 `RULES.md` 为准。

目标是让 Codex 把主要时间用于业务实现：本地连续开发、一次最终验证、一次远端交付。安全门禁集中保留在 production、数据库写入、破坏性数据操作和未确认产品语义上。

## 1. 默认执行流

### 1.1 任务分类

- `read-only`：调查、解释、审计，不改变外部状态。
- `docs`：独立文档或治理成果。
- `business`：业务代码、页面和普通缺陷。
- `database`：schema、SQL、RPC、RLS、migration 或远端数据。
- `config`：构建、CI、Vercel 或环境配置。
- `release`：`main`、production、hotfix 和正式发布。

一个任务只设一个主目标。支持该目标的 migration、前端、测试、类型和记录文档不再机械拆成多个目标或多个 PR。

### 1.2 启动回执

普通修改只需一次简短回执：

```text
目标与范围：
验证与停止点：
```

涉及 database、production、权限、数据删除或规则修改时增加：

```text
目标环境与精确对象：
失败处理与 rollback：
```

用户已明确要求执行时，回执用于说明理解，不是新的等待点。

### 1.3 连续批次

默认连续完成：

1. 任务开始时刷新一次目标分支并确认工作区。
2. 创建或复用一个任务分支。
3. 连续实现；开发中只运行受影响的快速测试。
4. 到达最终边界后运行一次完整的相称验证。
5. 一次更新必要支持文档，一次检查最终 diff。
6. 集中 commit、push，创建或更新一个 PR。
7. 用户可见功能先用目标 PR 最新提交对应的 Preview / development 入口交付业务验收；反馈继续更新同一 PR，只重验受影响流程，不为同一业务结果建立跟随 PR。
8. 等待最新提交的自动检查。用户可见功能必须同时具备对应最新版本的业务验收通过事实后才合并；非用户可见的普通 `develop` PR 可在检查通过后直接合并。用户要求停在合并前时严格停止。
9. 合并并回读后，执行任务分支和临时文件收尾。

不得把分支、单文件修改、测试、commit、push、PR 创建、PR ready 或普通 `develop` merge 拆成多轮审批。用户可见功能的业务验收是合并事实门禁，不是过程审批；发生实际远端写入、不确定结果或合理状态变化前，不重复查询同一事实。

### 1.4 必须暂停的情况

- 产品存在互斥选择，仓库事实无法确定。
- 目标文件、环境、project ref、migration 集合或数据范围改变。
- 验证失败且修复会扩大原目标，或 rollback 不完整。
- 即将进入 `main`、production、真实数据删除 / 回填、env / 凭据、历史改写，或删除未合并 / 状态不明确的分支。
- 远端写入结果不确定，且一次只读回查仍无法判断是否成功。

技术实现细节、文件位置、测试命令和已有代码行为由 Codex 调查决定，不向负责人重复询问。

## 2. 最小上下文与任务长度

- 只读取 `AGENTS.md` 路由出的文件和目标代码；长文档先检索标题或索引，再读取命中章节。
- 工具输出在本地聚合，只回传结论、计数和最多 10 条异常样本。
- 不因“可能有用”加载全部治理文档、数据库历史、缺陷归档或旧对话。
- 同一业务目标可以连续执行到交付；目标完成后结束任务。新的独立目标使用新任务，避免超长上下文反复重送。
- 网络或工具失败不触发从头重跑。先判断失败发生在哪一步，复用已经证明且未变化的事实。
- 用户只说“继续”或“下一步”时，先恢复当前分支和开放 PR 中尚未完成的目标；没有进行中工作时，再使用可选的本机任务指针。不得用过期文档覆盖当前 Git / PR 事实。

## 3. Git 与 GitHub

### 3.1 事实边界

- 本地分支和工作区表示正在开发的事实。
- GitHub 表示已共享、PR、checks、merge 和发布事实。
- GitHub 不是过程日志；不为每个阶段、验证结果或看板变化立即 push。

### 3.2 默认远端次数

一个普通任务原则上只需要：

1. 开始时一次 `fetch`。
2. 最终验证后一次 `push` 和 PR 创建 / 更新；业务验收反馈只更新该 PR，不创建跟随 PR。
3. 最新 checks 完成，且用户可见功能的最新版本通过业务验收后，一次合并与回读。

只有最终检查发现真实问题并修复时才增加一次 push。EOF、超时或断流后先只读回查远端 SHA / PR 状态；远端已经成功时不得重复写入。

### 3.3 发布前的单次最终检查

最终 push 前集中确认：

- 变更文件只属于当前业务目标。
- `git diff --check` 通过。
- 没有 `.env*`、`tmp/**`、`supabase/.temp/**`、凭据、真实用户数据或 production 写库脚本。
- 受影响测试和构建通过。
- rollback 与实际变更相匹配。

不在 push 前再做一轮完整 PR 审计；PR 合并前也不重复本地已经证明且提交未变化的检查。最终远端检查只确认 base/head、最新 SHA、checks、mergeability 和 changed files。

### 3.4 PR 与合并

- 一个业务结果默认一个 PR；标题、正文和支持文档一次写成合并后仍成立的状态。
- 非用户可见的普通 `develop` PR，任务授权包含 checks 通过后的 merge。用户可见功能还必须确认验收包与反馈报告指向最新 head commit / Preview，且负责人已明确验收通过；任一条件缺失都保持 PR 未合并。
- 验收反馈直接提交到原分支并更新原 PR；最新提交只重跑受影响的自动验证和业务验收。只有原 PR 已因不可逆外部原因合并，且无法恢复为同一开放 PR 时，才允许建立一个集中收口的验收反馈 PR。
- 用户明确说“不 merge”“保持 Draft”或“停在合并前”时严格停止。
- `main`、production 和 hotfix merge 永远进入发布流程，不能由普通开发授权推断。
- 合并后只回读一次 `mergedAt`、merge commit 和目标分支包含关系；不再为合并状态单独修改看板或创建 PR。

### 3.5 合并后的分支收尾

- 业务验收完成后运行 `npm run cleanup:audit`，把分支分为“可安全清理 / 需要负责人决定 / 必须保留”。
- 只有 PR 已合并到 `develop`、head 提交已进入 `origin/develop`、没有开放 PR、不是当前分支、未被 worktree 使用且名称为标准任务前缀时，才属于可安全清理。
- 切换到 `develop` 后，以精确 PR 编号执行 `npm run cleanup:task -- --apply --pr <PR编号>`；脚本会重新验证所有条件并失败关闭。
- 首次治理存量或周期性清理时，可以执行 `npm run cleanup:task -- --apply-safe`；它只处理当次审计仍属于“可安全清理”的标准任务分支，任一分支状态变化即停止。
- 未合并、来源不明、状态无法回读或包含 develop 外提交的分支只报告，不自动删除。

## 4. 相称验证

### 4.1 开发中

- 修改纯文档：检查链接、职责冲突、过时术语和 diff，不运行前端构建。
- 修改单个业务模块：运行相关单测或最小可复现检查。
- 修改多个业务模块或公共数据流：运行完整测试；最终再运行一次构建。
- 修改 UI：自动测试后进行一次目标页面浏览器验证；纯数据库或纯文档任务不做双浏览器回归。

### 4.2 最终验证

- 普通 business：相关测试；涉及构建链或多个模块时运行 `npm run verify:local`。
- database：数据库专项验证 + 相关业务测试 + 类型 / 构建（仅在相应产物受影响时）。
- docs：Markdown 链接、关键词冲突、`git diff --check`。
- config / release：按影响范围验证构建、环境映射和部署差异。

同一提交未变化时不重复运行同一全量测试。Vercel / GitHub checks 已覆盖的构建，不在 checks 之后再本地重复构建，除非远端失败或环境不同。

## 5. Database 与 Supabase

### 5.1 授权和固定环境

- 一级（无需确认）：只读查询、Advisor、类型 / schema 回读和以 `ROLLBACK` 结束的 fixture。
- 二级（项目级常驻授权）：固定 development 项目的无业务数据 migration，以及明确验收任务中的专用测试账号 / 数据准备。Codex 负责环境、文件哈希、事务、持久行和 rollback 校验，不向负责人索要技术字符串。
- 三级（单独确认）：production、真实数据删除 / 回填 / 批量改写、非专用测试账号、真实凭据和环境绑定。
- 二级操作在启动回执中给出自然语言说明，但不形成等待点；三级操作使用授权卡并等待负责人回复“同意”。

三级授权卡固定为：

```text
环境：
目的：
会改变：
不会改变：
失败处理 / rollback：
需要确认：是否允许本次操作？
```

project ref、migration 文件和 SHA-256 只进入自动前检、数据库变更记录和 PR 审计，不作为负责人必须复制的授权语句。

### 5.2 链接复用

- 工作区已经 link 到 development 时不重复执行 `supabase link`。
- 实际远端操作前运行 `npm run db:check`，固定确认 development project ref `tfwejruvdahonacyldrg`。
- project ref 不匹配或链接缺失时停止；只有修复链接需要远端认证时才处理 link。
- CLI、MCP 或 API 选择一个可用入口完成任务。传输故障时最多切换一次等价入口，不在多个入口间反复试错。

### 5.3 单次 migration 闭环

同一 migration 的 development 远端流程固定为：

1. 一次聚合前检：project、migration history、目标对象、受影响基线和旧定义 / 权限。
2. 一次 dry-run 或事务 rehearsal（工具支持且确有价值时）。
3. 一次 apply。
4. 一次事务 fixture，结束时 rollback；覆盖权限、幂等、业务断言和故障整体回滚。
5. 一次聚合后检：history、目标对象 / 权限、持久行数和异常残留。
6. 一次更新类型、schema 摘要和数据库变更记录，仅更新实际发生变化的产物。

前检已经证明且目标未变化时不重新执行。apply 返回不确定结果时先查询 migration history 和目标对象，确认未应用后才能重试。

### 5.4 Advisor、dump 与生成物

- 函数 / 权限型 migration 默认只检查 Security Advisor、目标函数定义、owner、`search_path`、grants 和业务断言。
- 只有修改表、索引、查询计划或有性能证据时才运行 Performance Advisor。
- 只有 schema 契约实际变化时才生成 types；只有需要提交正式结构快照或检测漂移时才 dump schema。
- Advisor 的既有告警只记录一次，不在每个 migration 重复展开；只阻断本次新增或明显恶化的问题。

### 5.5 Rollback

- 已应用 migration 不删除、不重写；使用新的 patch migration 停用或修正。
- 审计事实默认保留；错误积分等通过追加反向流水处理。
- 测试 fixture 默认事务 rollback。需要清理持久测试数据时，按精确身份、前值、依赖和数量断言执行，并单独遵守数据删除授权。

## 6. 文档、本机状态与业务验收

### 6.1 文档与任务指针

- `docs/ai/CURRENT_TASK.md` 不再由 Git 跟踪。它是可选的本机任务指针，只保留当前目标、唯一下一步、需要负责人决定和更新时间。
- 本机任务指针可以保存短时工作状态，但不得 stage、commit、push、进入 PR 或被称为仓库事实源；文件缺失不阻断任务。
- 数据库变更记录只在 migration 实际设计变化或 development / production apply 事实变化时更新；不记录重复查询过程。
- 需求、开发和技术文档只有其权威内容改变时才更新，不为证明“已经阅读 / 已经验证”机械同步多份文档。
- 缺陷、验收和数据库支持文档随业务主 PR 一次提交，不建立纯状态 commit 或 PR。
- 独立治理、需求或设计文档本身就是交付物时，可以建立一个 docs PR。

### 6.2 验收包

- 业务验收前，Codex 直接在 development 准备账号和数据，不让负责人通过网页造数。账号可以复用；每一轮业务数据使用可追溯的验收批次和固定身份，交付前回读起始状态。
- 验收包统一从 [`templates/验收清单模板.md`](templates/验收清单模板.md) 生成，并写入 Git 忽略的 `tmp/验收清单.md`。保留模板中的验收范围、已准备数据、最短验收流程、总通过标准、异常反馈格式、数据保留与清理和 Rollback；不得增加“账号与密码”总表或“账号与密码放置规则”模块。
- 验收目标必须绑定目标 PR、精确 head commit 和对应 Preview，不得写成已合并后的模糊 `develop` 状态。
- 无需登录的公开场景使用独立匿名测试模块，模块内不写账号或密码；登录场景严格按账号拆成 `### ...（一次登录）` 测试模块，每个模块只填写一个账号和该账号的明确密码，并合并该账号可顺序完成的场景。账号和密码不得写在模块外，也不得使用统一密码。自动 fixture 已覆盖的权限、幂等和 rollback 不再要求网页重复验收。
- development 专用验收账号使用便于负责人手工输入的简单密码：8 至 16 位，仅使用英文字母和数字，并同时包含字母与数字；不使用随机长串、特殊符号或真实凭据。密码仍只允许进入本地 Git 忽略的验收清单。
- 交付前运行 `npm run acceptance:check`。该检查不输出密码，只验证验收包未被 Git 跟踪、位于忽略路径、模块和字段完整、每个账号与简单密码均位于对应的一次登录模块内。
- 对负责人只发送本地验收包链接和一个可直接打开的 Preview 链接，不发送 Vercel 控制台链接，也不在聊天中重复密码。

### 6.3 验收反馈与轮次关闭

- 负责人只需按清单标记成功；失败时提供步骤号、实际现象、北京时间和截图。带修改意见的“已验收”视为该版本尚未全部通过：Codex 在同一 PR 修复后，只重测失败或受修复影响的流程。
- `tmp/验收清单.md` 是负责人执行测试的操作文档；`tmp/验收报告.md` 只记录目标版本、反馈和最终状态，不重复账号或密码。每轮验收报告写入 Git 忽略路径，防止旧失败报告覆盖新版本事实。
- 验收全部通过后，报告收口为“全部通过、无待修复项”，并记录与 PR 最新 head commit 一致；随后等待该提交 checks 通过并合并。合并后删除本地凭据，或在下一批次前轮换测试密码。

## 7. 任务收尾与文件清理

### 7.1 自动清理范围

- 可自动清理：本任务创建、位于 Git 忽略路径且能够精确归属的临时日志、空输出、验收凭据、过期 Preview 交付物和中间产物。
- 必须通过正常 PR 删除：被 Git 跟踪的代码、文档、脚本、配置和测试。删除前检查引用、替代物和相称验证。
- 永不按废弃物直接删除：已应用 migration、数据库变更记录、投票 / 积分 / 审计事实、未合并分支独有文件、来源不明的用户文件和仍承担 rollback / 恢复职责的材料。

### 7.2 清理顺序

1. 业务验收完成，报告已关闭。
2. 回读 PR merge、`origin/develop` 包含关系和开放 PR。
3. 运行 `npm run cleanup:audit`。
4. 精确清理符合第 3.5 节的任务分支。
5. 删除本任务创建且已无用途的忽略文件；不使用 `git clean` 或宽泛目录删除。
6. 回读工作区，只允许保留明确属于用户或下一目标的改动。

### 7.3 任务关闭标准

功能完成、自动验证通过、PR 合并、需要的业务验收通过、报告收口、任务分支和临时文件清理完成后，任务才标记完成。无法判断归属的分支或文件列入“需要负责人决定”，不得为了形式完整擅自删除。

## 8. Production 与发布

非紧急发布由完成验收的需求里程碑触发：

1. 确认 `main = production`、`develop = development / preview`。
2. 对 `develop -> main` 做一次完整差异分类，确认未验收内容已经隔离。
3. 提交一次发布决策卡：里程碑、随带变更、验证、环境影响和 rollback。
4. 用户明确授权后创建 release PR；production merge 再按本次发布明确确认。
5. 涉及数据库时重新确认 production project ref、备份、前值、影响数量和 rollback。
6. 合并 / 发布后只观察和回读，不自动 rollback。

紧急 production 缺陷走独立 hotfix，不携带无关 develop 变更。

## 9. 异常处理

- 命令失败：保留已完成且仍有效的证据，只重试失败的最小步骤。
- GitHub 写入不确定：先查 PR、远端 SHA 或 merge commit，再决定是否重试。
- Supabase 写入不确定：先查 migration history、目标对象和持久基线，再决定是否重试。
- 验证失败：在原目标内可修复时继续修复；需要扩大业务语义、环境或数据范围时暂停。
- 工具不可用：最多切换一次经过验证的等价方式，不为绕过安全门禁切换工具。

## 10. 最终回传

项目汇报只回答：

```text
当前任务：解决了什么。
已经完成：确认成立的业务结果。
当前进度：调查 / 修改 / 验证 / 待发布 / 完成。
下一步：唯一最重要的后续事项。
需要负责人决定：没有，或一个确实需要产品 / production 决策的问题。
```
