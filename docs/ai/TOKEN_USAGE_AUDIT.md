# Token 使用审计

> 审计对象：上一目标“清理文件、删除废弃分支并同步 main/develop”；时间：2026-07-12（北京时间）。

## 先区分两个数字

任务完成工具记录的 `tokensUsed = 96,697` 是目标控制器的任务计数，不等同于模型 API session 的累计 usage。上一目标结束前的 session 日志显示：

| 指标 | 上一目标开始前 | 上一目标结束时 | 增量 |
| --- | ---: | ---: | ---: |
| total tokens | 69,874,039 | 86,147,430 | 16,273,391 |
| input tokens | 69,643,872 | 85,884,879 | 16,241,007 |
| cached input | 67,471,232 | 83,533,952 | 16,062,720 |
| output tokens | 230,167 | 262,551 | 32,384 |
| reasoning output | 54,674 | 64,495 | 9,821 |

这两套数字口径不同，不能相加。可以确认的是：上一目标的成本绝大部分来自重复输入上下文，而不是最终回答文字。

## 证据规模

- 会话上下文窗口：约 353,400 tokens。
- 上一目标区间包含 72 条普通消息、74 条 reasoning、68 次 Codex 工具编排和 15 次等待。
- 整个会话日志约 9.9MB，包含 3 次 compaction、47 个 turn context 和大量重复系统 / 工具说明。
- 每轮常见输入约 200,000～235,000 tokens；其中约 98% 属于 cached input，但仍被重复处理。

## 最大消耗源

1. 长对话累积了完整旧审批、IDE 上下文、规则、skill 清单和数据库历史；每轮都接近上下文窗口上限。
2. 任务被拆成许多微步骤：文件清理、分支分类、PR、合并、发布同步、hook 修复各自重新恢复上下文。
3. 为了确认安全边界，多次读取大段文档、PR 输出和审计结果；安全检查有价值，但原始输出进入对话没有价值。
4. 出现连接器传输错误、hook 无条件拦截 merge、临时分支状态不一致后，产生了额外复查和修复轮次。
5. 最后为了让 `CURRENT_TASK.md` 的累计分支数字准确，又增加了多轮仅文档同步 PR；这是可以避免的设计问题。

## 下次执行规则

- 每个独立目标使用新对话，交接只保留五项执行单和当前看板，不复制完整历史。
- 超过约 20,000 tokens 的 JSON、日志或 SQL 只在本地解析，返回计数、异常和少量样本。
- 一个 database / release 批次一次授权覆盖 precheck、apply、postcheck 和 rollback；失败或范围变化才重新确认。
- `CURRENT_TASK.md` 不记录累计操作次数、分支删除数量等易过期数字，只写稳定事实。
- 低成本模型处理文档整理、状态汇总和只读分类；高推理模型只用于复杂代码和高风险数据判断。
- 任务完成后立刻关闭当前对话，禁止在同一长对话追加第二个独立目标。

安全门禁不能删除：production 前值检查、事务数量检查、提交后回读、rollback 依据，以及用户录入 before / after 历史。
