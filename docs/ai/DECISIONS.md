### 已登录用户高分计算输入可信化第一版

- 已登录用户的高分计算只使用本人云端衣柜内的服装；衣柜为空、尚未读取完或读取失败时，不使用完整图鉴代替本人衣柜，也不展示误导性分数和搭配结果。
- 页面明确区分登录确认中、衣柜读取中、空衣柜和读取失败；空衣柜提供录入入口，读取失败提供可理解的重试提示。
- 切换账号或退出登录时立即清空上一身份的本地衣柜计算状态，旧请求不得回写当前身份。
- 匿名用户保持现有完整图鉴试算口径；第一版不修改评分公式、饰品惩罚、图鉴、衣柜数据、积分、权限或数据库。

### 管理员审核卡片文案

- UI 不使用：版本、变体、字段组合、冲突版本、一致提交。
- UI 使用：资料一致情况、最多人认可、不同意见、可按多数入库、需要继续收集。
- 5 人以上相同且无不同意见：状态显示为“可入库”。

- 人数不足保持“人数不足”。

### 积分第一版规则

- 积分权威来源为 `points_ledger`。
- `profiles.total_points`、`profiles.current_month_points`、`profiles.monthly_action_count` 不作为权威积分来源；如后续保留，只能作为历史字段或可重建缓存。
- 图鉴 / 衣柜条目审核通过并成功入库后，符合最终入库数据的有效提交者获得积分。
- 积分分值按来源区分配置，不采用所有来源统一 +10。
- 第一版积分分值配置：
  - 自动入库：+10。
  - 管理员仲裁入库：+10。
  - 正式库空字段补全：+5。
  - 重审修正通过：+8。
  - 陪审员对每份待审核内容的首次有效投票：+1；同票重试不重复奖励，退回或驳回后不追回。
  - 报错通过：+5。
- 自动入库与管理员仲裁入库同为“有效提交最终入库”，第一版保持同分。
- 空字段补全低于完整入库。
- 重审修正高于普通报错，但低于完整入库。
- 报错通过保持轻量激励，避免破坏等级平衡。
- Lv1 至 Lv4 对成功结算的自动入库、管理员仲裁入库、正式库空字段补全、重审修正和报错采纳，分别追加 `+1 / +2 / +3 / +5` 等级奖励；陪审首次投票 `+1` 不叠加等级奖励。
- 等级奖励按基础流水发生前的累计积分等级快照计算；升级当次不追补，历史流水不补发。奖励是关联基础流水的独立、唯一流水，基础流水扣回时同步追加奖励负数流水。
- 等级奖励计入累计等级、总榜、月榜和管理员候选冻结积分，但奖励流水不重复计为有效行为次数。
- 未列明来源的分值在确认前不得在实现中固化。
- 第一版积分状态：默认 `awarded`。
- `awarded` 积分在审核通过后立即生效。
- 积分写入只做追加流水，不直接覆盖用户总分。
- 积分扣回采用追加负数流水机制。
- 不允许修改或删除历史积分记录。
- 所有积分变更必须可追溯。

### 积分系统可重算模型（Event Sourcing Lite）

- 积分不再存储最终值。
- 当前积分 = `points_ledger` 聚合计算。
- `points_ledger` 成为积分唯一事实源。
- 所有积分变化必须以事件形式记录。
- 不允许直接修改积分结果。
- 陪审团通过必须写入 ledger。
- 重审通过必须写入 ledger。
- 报错通过必须写入 ledger。
- 系统奖励 / 扣减必须写入 ledger。
- 积分系统支持积分重算机制。
- 任意用户可通过 ledger 重建历史积分状态。
- 支持时间回溯计算。
- `snapshot_flag` 可作为性能优化，不影响逻辑正确性。

### 正式库资料补全规则

- 正式库空字段允许通过审核后的 pending 数据补全。
- 正式库已有非空字段时，默认不允许覆盖。
- 正式库已有非空字段若被报错且需要修正，必须进入审核库并执行陪审团制度。
- 不允许绕过审核库直接覆盖正式库。

### 报错 / 修正审核路径规则

- 用户对正式图鉴的报错选择一个明确字段并给出建议；页面默认带入正式值，分类、星级、属性和套装优先使用结构化选项，没有合适选项时允许切换为手动输入。
- 新报错必须上传一张能核对该服装正确资料的游戏内图鉴图片；图片存放在私有空间，只允许报错者本人和当前有资格参与该事项的陪审员读取。补丁生效前的历史报错允许没有图片。
- 新提交的明确字段报错直接进入该服装唯一的活动审核项，不以管理员转交作为前置条件；报错者登记为来源，不得补充、投票或终审自己的报错。
- 同一审核项投票期间收到新的报错字段时，不新建事项也不拒绝提交；当前候选退回补充，问题字段合并到原事项。已产生的投票和陪审参与积分作为历史事实保留，正式资料不变。
- 同一审核单必须同时列出正式资料中已有的其他缺失字段，补充者只核对页面列出的字段，未列字段保持不变。
- 报错受理和转陪审不得直接修改正式库；只有陪审内容达到通过门槛后才允许按本轮完整资料更新正式库。
- 管理员报错队列只用于处理补丁生效前已经存在的待处理记录和异常兜底，不再是新报错的必经路径。
- 正式库已有非空字段修改默认不允许直接修改。
- 正式库已有非空字段若被报错且需要修正，必须进入审核库并执行陪审团制度。
- 正式库已有非空字段修正不允许绕过审核库直接覆盖正式库。
- 多人提交冲突、字段争议、无法由管理员单人判断的修正进入审核库，并执行陪审团制度。
- 管理员终审单独建立终审记录，不写入 `jury_votes`。
- 第一版不使用“低风险 / 高风险字段分级表”作为执行规则。
- 报错建议只有在陪审最终资料精确采用该建议时结算唯一 `+5`；仅提交、转陪审、退回或未采用均不奖励。

### 报错推翻原资料后的原贡献积分规则

- 只有报错最终通过、报错字段在原正式资料中非空，且采纳值确实替换原值时，才扣回与被推翻资料直接关联的原贡献积分。空字段补全、未采纳、退回重审、仍在投票或新旧值相同均不扣回。
- 扣回对象只限 `clothing_contribution` 正向基础流水，且其来源 pending 在该报错字段上的快照必须等于被推翻的原值；同一服装后来针对其他字段形成的独立补全贡献不受影响。
- 每条命中基础流水按原始正向分值全额追加负数 `reversal` 流水；若该基础流水曾产生等级奖励，则同步按原奖励全额追加等级奖励负数流水。原正向流水、贡献事实与公开贡献者归属均保留不改。
- 基础扣回必须同时关联原积分流水和最终批准的 `correction_request`，并以原流水唯一防重；报错批准、正式资料更新和积分扣回处于同一事务，任一失败则全部失败。
- 陪审首次投票、重审补充者、报错者及其他无关奖励不因本规则扣回；本规则不回填补丁生效前的历史报错或历史资料变更。

### 陪审团制度第一版最小业务规则

- 陪审团触发条件：非空字段报错修正、多人提交冲突、字段争议。
- 同一件服装同时只对应一个开放审核项，审核项列出全部缺失或冲突字段。
- 陪审页面一次只展示一张审核卡片；移动端可左右滑动切换事项，卡片内部纵向滚动完成核对和操作。
- 补充者必须提交完整服装资料；已一致字段保持只读，只允许修改审核项列出的字段。投票期间内容不得替换，内容变化时必须结束本轮并重新补充。
- 陪审团只提供赞同 / 驳回两种票。首次投票按当时累计积分冻结等级与票权：Lv0/Lv1 为 1 票，Lv2/Lv3 为 2 票，Lv4 为 3 票；升级或降级不追改旧票。
- 用户不得投票审核自己提交或参与过的来源数据；管理员作为普通陪审员投票时也遵守相同限制。
- 管理员可以作为普通陪审员投票，按其投票时等级快照计权；同一管理员投过某审核项后，不得再对该项执行管理员终审。
- 管理员终审与陪审团投票是两种独立行为：终审不写入 `jury_votes`，也不补算或覆盖普通票。
- 陪审团计票按三个结果分流：
  - 至少 5 位不同用户赞成，且加权赞成票高于加权反对票：通过，系统按本轮完整审核内容自动修改正式库。
  - 至少 3 位不同用户反对，且加权反对票与加权赞成票之差达到 3：退回重审，要求重新补充；不得修改正式库，不得关闭或永久驳回审核项。
  - 其他情况：保持投票状态，继续投票。
- 永久驳回不由普通票数自动触发：超级管理员可单独决定；普通管理员必须由 2 位未参与该项投票、提交或来源数据的当前有效任期管理员对同一结论共签。

### 陪审团投票记录与自动修改边界第一版

- 陪审团投票记录应记录每个用户每次投票。
- 陪审团投票记录不只记录最终统计结果。
- 同一用户同一审核项（user_id + audit_id）只能存在一条有效投票记录。
- 系统必须保证投票请求幂等。
- 重复请求（网络重试 / 前端重复点击 / 多端提交）不会产生多条有效票。
- 如果重复提交的投票内容相同，忽略重复请求。
- 如果重复提交的投票内容不同，按“不允许改票”规则拒绝或返回错误。
- 后端写入为唯一真相。
- 前端状态不可信。
- 同一用户同一审核项不允许改票。
- 投票事实同时保存等级快照和票权快照，不从当前等级反算历史票。
- Lv2 及以上可在首次投票时附一条不超过 200 字的结构化复核意见；意见与投票一并不可修改，不额外奖励积分。对其他陪审员只匿名展示等级，管理员审计保留来源身份。
- 投票提交后不可修改；该规则只在提交确认时向用户说明。
- 若因页面假死、误点、重复提交造成异常，先作为异常处理，不在第一版开放改票。
- 陪审团达到通过门槛后，系统立即按本轮完整审核内容自动修改正式库。
- 达标后不再额外进入管理员终审后修改。
- 自动修改正式库时，必须记录变更前值和变更后值。
- 变更记录应能追溯本次陪审团审核项、投票结果和修改时间。
- 自动修改失败时，重新进入陪审库，交由其他人继续审核。
- 自动修改失败不静默失败。
- 自动修改失败不直接标记完成。
- 管理员终审不写入 `jury_votes`，单独建立终审记录。
- 不新增未经确认的字段名、表字段、状态值。

### 陪审团系统最小数据库结构第一版

- `jury_votes` 为投票事实表。
- `jury_votes` 记录 user_id + audit_id + vote。
- `jury_votes` 不允许修改历史记录。
- `jury_votes` 遵循同一用户对同一审核内容只能保留一张有效票、投票后不可修改的约束。
- `jury_votes` 中所有投票必须可追溯。
- `re_review_items` 为陪审团审核池。
- `re_review_items` 存储所有进入陪审团的争议项。
- `re_review_items` 支持 pending / voting / approved / rejected / failed。
- `re_review_items` 负责所有复杂审核流转。
- `points_ledger` 为积分事实表。
- `points_ledger` 中所有积分变化只追加不修改。
- 积分由 delta 汇总计算。
- `points_ledger` 记录积分来源与来源对象。

### 数据库约束规则（v1）

- `jury_votes` 必须具备 UNIQUE(user_id, audit_id) 约束。
- `jury_votes` 不允许 UPDATE vote，只允许插入。
- `jury_votes.vote` 只能是 approve / reject。
- `points_ledger` 只允许 INSERT。
- `points_ledger` 禁止 UPDATE / DELETE。
- 积分由 SUM(delta) 计算。
- `re_review_items.status` 只能是 pending / voting / approved / rejected / failed。
- `re_review_items` 状态流转由 service 层控制。
- DB 只负责约束 `re_review_items.status` 合法值。

### 前 5 有效提交者规则

- 有效提交者必须满足：提交数据与最终入库数据一致，且 `submitted_by` 可识别为真实用户。
- 有效提交者按提交时间升序排序。
- 只取前 5 个有效提交者获得本次入库积分。
- 匿名历史数据不补造真实用户身份。

### 积分贡献来源保留与幂等规则

- 自动入库必须保留每一条有效来源 pending，不再删除匹配 pending。
- 触发自动入库的当前提交也必须先形成 pending 来源记录，再与本次选中的来源记录一起标记为 `approved`。
- 每条贡献记录必须能追溯到保留的来源 pending；不可变快照可以作为补充证据，但不替代来源 pending。
- 同一次初始入库中，自动入库与管理员仲裁是互斥路径；同一用户对同一服装的初始入库奖励只能获得一次。
- 同一用户后续参与正式库空字段补全、重审修正或报错通过等独立有效行为时，可以按对应来源再次获得积分。
- 每个来源事件必须幂等；网络重试、重复点击或重复 RPC 调用不得产生重复贡献、重复积分或重复衣柜写回。

### 账号删除后的贡献与积分审计保留规则

- 用户账号删除后，贡献记录和积分流水作为历史审计事实继续保留，不级联删除。
- 与已删除账号的身份关联应解除，相关用户外键允许置空；历史记录不得继续暴露原用户名、昵称或其他可识别信息。
- 已删除账号在贡献者展示中统一显示为“已注销用户”。
- 匿名化只影响身份展示，不修改或删除历史贡献、积分 delta、来源、时间和排名事实。

### 前 3 展示贡献者规则

- 页面展示贡献者从前 5 有效提交者中产生。
- 展示贡献者按提交时间升序排序。
- 页面最多展示前 3 位贡献者。
- 所有有效贡献者均显示当前公开名称；Lv0 使用普通样式，Lv1 起显示正式贡献者署名标识。
- Lv2 及以上只增加视觉强调，不改变前 3、前 5或时间排序。

### 缺套装入库规则

- 用户界面统一使用“所属套装待确认”；不得追加其他候选词，也不得向用户展示 `missing_suit`、`needs_suit_review` 等内部名称。
- “无关联套装（纯散件）”与“所属套装待确认”是两个不同事实：纯散件不创建待补套装重审项，只有用户明确选择后者才进入该流程。
- 历史 `suit_id = null / temp_suit_name = null` 数据继续按纯散件解释，不自动回填为待补套装；新的待确认状态必须显式保存。
- 缺套装但短编号完整、核心字段完整的数据允许进入正式库。
- 入库同时创建 `re_review_items`。
- `re_review_items` 状态标记为待补套装。
- `re_review_items` 是待补套装状态的权威追踪来源。
- 待补套装状态在绑定正式套装后自动关闭，不需要管理员手动关闭。

### `re_review_items` 第一版使用规则

- 第一版用于追踪：待补套装、字段冲突、字段缺失、报错转重审。
- `missing_suit`、字段冲突、字段缺失和正式资料修正统一进入同一队列；同一服装的活动事项必须复用，不得重复建项。
- 第一版采用“社区参与、系统处理、管理员兜底”，不得把全部重审处理责任只交给管理员或最高站长。
- 未参与原始提交的登录用户可以查看开放重审项并提交完整补充资料；原提交者和任一来源参与者不得审核自己的数据。
- 第一版不允许普通用户直接覆盖正式库。
- 重审修正不得绕过陪审团通过门槛直接修改正式库；通过门槛后允许系统自动修改正式库。

### 等级功能性权益

- 等级名称、累计门槛和铜 / 银 / 金 / 皇冠静态主题保持为 Lv1 500、Lv2 2000、Lv3 5000、Lv4 10000。
- Lv0：额外积分 0、陪审票权 1；保留公开数据、本人总积分、查看、提交候选和投票能力。
- Lv1：额外积分 +1、陪审票权 1；增加本人积分流水。
- Lv2：额外积分 +2、陪审票权 2；增加首次投票复核意见、月度管理员候选资格、本人贡献与投票记录、当月匿名社区统计。
- Lv3：额外积分 +3、陪审票权 2；增加最近 12 个月按审核原因和结果汇总的匿名统计。
- Lv4：额外积分 +5、陪审票权 3；增加匿名管理员任期、低风险处理和积压统计。
- 五类权益均通过受控实现开放，不开放积分、投票、管理员或证据底表；分级只读 RPC 不返回用户 ID、邮箱、手机号或私密证据。
- 等级不会自动授予管理员权限；任期内降级不提前撤权，管理员能力仍只来自有效任期或超级管理员事实。

### 管理员终审、多人共签与纠错规则（社区共治 V2.1）

- 管理员终审不写入 `jury_votes`。
- 普通用户投票与管理员终审语义分离。
- 管理员终审应单独建立不可删除的决定、共签、原因、时间和执行结果记录。
- 套装通过、套装驳回和永久驳回，普通管理员必须由 2 位不同的当前有效任期管理员对同一结论共签后执行；超级管理员可单独执行。
- 普通管理员不得共签自己提交、参与来源、已经投票或存在其他利益冲突的事项；同一人重复操作不计为多人共签。
- 陪审团反对票达到退回门槛只会退回重审，不得自动永久驳回。
- 已执行决定遇到新证据时，沿用现有重审池和陪审团门槛重新审理；原提交者、来源参与者、原决定共签者和原轮次投票者不得参与对应的新审理环节。
- 纠错不删除原决定或历史事实；正式数据按执行前后快照原子恢复或应用，积分只通过追加 delta 扣回或补发。
- 超级管理员可以纠正任何社区决定，也可以纠正自己此前的决定；纠错同样必须填写原因并完整留痕，但不得以留痕要求削减其权限。

### 普通管理员月度轮换与社区共治 V2.1

- 普通管理员权限唯一事实为当前有效的 `admin_terms`；`profiles.role` 不再承载普通管理员权限，`super_admin` 继续作为兼容字段。
- 北京时间每月 1 日 00:10，在上月榜 00:05 冻结后，从上月冻结积分用户中按“积分降序、有效行为数降序、最后有效行为时间升序、用户 ID”固定排序，自动授予最多 5 个当月席位。
- 候选冻结时累计积分等级必须至少为 Lv2，且上月必须至少有 5 条排除 `level_bonus` 后的正向有效积分行为；超级管理员、已有有效手动/过渡任期用户、已注销账号和命中有效显式排除的用户跳过，不足 5 人保留空席。
- 月初候选快照和跳过原因冻结，月中新积分不重排；轮值管理员退出、被撤销或新增排除后，按该快照自动顺延补位。同一服务月已经退出或被撤销的候选不重复入席。
- 上月榜未成功冻结时不授予新月度权限；旧月度任期按时间自然失效。部署当月不追授，第一次轮换从下一个完整自然月开始。
- 手动任期独立于月度 5 席，必须填写原因和结束时间，最长 31 天；旧 `profiles.role = admin` 精确迁移为 31 天 `legacy_transition` 受限任期。
- 普通管理员可独立处理新增、无套装语义、正式库不存在、完整多数资料至少由 5 位不同有效用户支持且不存在最高票并列的服装；允许保留少数不同意见，但审核者不得参与该组任何提交。
- 普通管理员通过时只批准多数资料对应的 pending，并复用贡献、积分、衣柜原子写回；驳回必须填写原因，只可逆驳回多数资料，用户可重新提交，记录不删除。
- 当前有效任期的普通管理员登录后应显示“图鉴管理”入口；入口内按实际能力显示低风险单人审核、套装多人共签及其可参与的治理事项，不得因前端隐藏而抹去已授予能力。
- 套装通过、套装驳回和永久驳回按 2 位不同当前有效任期普通管理员同结论共签执行；超级管理员可单独执行。正式库已有资料补全、重审和图鉴报错继续遵守既有陪审团自动通过 / 退回门槛，普通管理员不得绕过陪审团直接修改正式库。
- 手动授予普通管理员任期、提前结束任期、候选排除和撤销排除，必须由 3 位不同的当前有效任期普通管理员对同一结论共签；超级管理员可单独执行。普通管理员不得给自己授权、处理自己的任期或排除，也不得管理超级管理员身份。
- 超级管理员即站长，完整保留现有及后续业务治理、最终裁决、纠错、管理员治理和技术管理权限，可以选择不行使，但不得因社区共治被取消、降级或附加多人共签门槛。
- 普通管理员不获得超级管理员身份、密钥、部署、数据库后台或底表直写权限；客户端不能直接新增、修改或删除任期、排除、候选快照、审核决定、共签和正式业务事实，只能调用函数内重新校验身份、任期、人数门槛、同结论、自审与冲突的受控 RPC。
- 原等级名称、累计门槛、等级奖励、陪审票权、Lv2 候选门槛、每月最多 5 席和原排序规则全部保持不变；社区共治 V2.1 不建立新的身份等级或治理等级。
- 优化建议留言板的状态与可见性治理不纳入社区共治 V2.1，仍只向超级管理员开放。
- 本节为 2026-08-30 已冻结的目标规则；当前 development 的 DB-15 / DB-21 实现尚未具备上述多人共签和普通管理员套装能力，不得描述为已完成 V2.1，也不得在负责人验收前合并对应用户可见变更。

### 编号校验规则

- 编号字段不允许为空。
- 缺编号数据不应通过提交校验。
- 缺编号数据不应通过入库校验。
- 缺编号数据不进入积分判断分支。

### 积分排行榜与上月榜冻结规则

- 第一版只提供总榜和当月榜，均从 `points_ledger` 中 `awarded` 流水实时汇总，不建立缓存或快照。
- 排行榜仅登录用户可见；匿名请求不得获得任何榜单行。
- 当月榜按 `Asia/Shanghai`（UTC+8）自然月统计。
- 同分用户并列同一名次，后续名次连续计算。
- 页面只展示公开名称、积分、名次和当前用户标记；缺少名称时使用不可逆化名，不返回 email、账号 ID 或积分流水。
- 上月榜在每月 1 日北京时间 00:05 冻结上一完整自然月，并在能力首次启用时补冻最近一个已结束自然月。
- 上月榜只冻结 `points_ledger` 中 `awarded` 流水汇总后的积分与 dense rank 名次；冻结后新增、扣回或修正流水均不追改该月榜。
- 上月榜展示名称和账号注销状态按当前事实读取：改名后显示新名称，账号删除后显示“已注销用户”；不保留或返回 email、账号 ID。
- 上月榜沿用仅登录用户可见、同分并列且后续名次连续的规则。
- 上月冻结榜 dense rank 并列第一的全部有效账号，在次月获得独立、可审计的 Lv4 体验资格；资格从次月北京时间月初生效，到该月月底自然失效并补记回收时间，不递补、不改写累计积分等级，也不改变任何排行榜的等级展示。
- 月榜首 Lv4 体验严格只包含三项：有效业务成功结算时额外 +5 分、首次陪审投票冻结为 3 票，以及 Lv4 匿名治理统计。复核意见、本人数据分级等其他能力仍按累计等级开放。
- 体验资格不授予普通或超级管理员权限，不授予月度管理员候选资格，也不进入 `admin_terms` 或管理员候选快照；候选等级继续只按累计积分计算。体验期间实际获得的 +5 奖励仍作为正常积分流水累计，但资格本身不补造积分或永久等级。
- 已达到累计 Lv4 的月榜首仍保留当月资格审计；资格到期只结束临时叠加，不降低其累计等级或永久 Lv4 权益。冻结快照中的账号已注销时不授予资格，已经授予后注销则立即失去可用权益但保留去身份化审计。
- 能力首次启用时，若上一自然月已经冻结，则立即授予当前这个次月的剩余有效期；不追补启用前已经发生的积分事件、投票或治理读取。
- 首页鸣谢第一版只使用最近一个已冻结的北京自然月：在冻结榜用户中筛选该月至少 5 条排除 `level_bonus` 的正向有效积分行为，沿用冻结候选的“积分降序、有效行为数降序、最后有效行为时间升序、用户 ID”顺序取最多 10 人；月中新积分、扣回或修正不追改名单顺序。
- 首页鸣谢对匿名和登录用户公开，只返回月份、展示顺序与当前公开名称；账号注销后不再展示，缺少公开名称时使用不可逆化名。无符合条件名单或读取失败时不显示模块。
- 首页鸣谢不新增积分、等级、广告、权限或管理员权益；仅在搭配计算首页滚动展示，并为减少动态效果的系统偏好停用滚动。

### 独立打赏支持第一版

- 页面明确项目继续免费、打赏完全自愿，并说明服务器、域名、存储和维护用途；微信、支付宝使用负责人提供并确认收款人展示信息可公开的静态二维码。

### 优化建议留言板与点赞排序第一版

- 留言板只承载产品优化建议；图鉴资料错误继续走图鉴报错，系统异常继续走技术日志，三类事实、状态和管理队列保持分离。
- 未登录用户可查看公开建议、状态、公开处理说明、点赞数和时间；只有登录用户可提交建议、点赞、取消点赞和撤回自己的待评估建议。公开结果不展示作者身份、用户名、用户 ID、邮箱或等级。
- 建议标题 5～80 字、说明 10～1000 字，只支持安全纯文本；每个用户每个北京自然日最多提交 5 条，不占图鉴提交 quota。同一规范化标题与正文的公开建议不得重复创建，语义相似但文字不同的建议第一版不自动合并。
- 建议提交后不得编辑；作者只能撤回仍处于“待评估”的公开建议。撤回后不公开、不参与排序，但正文、点赞和时间作为审计事实保留。
- 同一用户对同一建议最多一个活动点赞，允许取消后再次点赞；作者可以点赞自己的建议，所有登录用户权重均为 1。点赞只用于产品排序参考，不产生积分、等级、陪审票权、管理员资格、开发承诺或上线时限。
- 待评估建议按有效点赞数降序、提交时间升序、建议 ID 稳定排序；“计划中”和“技术无法实现”分别按最近处理时间降序展示。撤回、重复归档和滥用隐藏建议不参与公开排序。
- 正常业务状态仅为“待评估 → 计划中 / 技术无法实现”；第一版不增加开发中、已完成或已发布。允许已评估建议重新回到待评估，但必须填写内部原因并保留历史；“技术无法实现”必须填写公开说明，“计划中”公开说明可选。
- 撤回、重复归档、滥用隐藏和恢复属于可见性治理，不是开发评估结论。仅超级管理员可以评估状态、重新打开、标记重复、隐藏或恢复；普通月度 / 手动任期管理员不得获得处理权限。所有处理记录处理人、北京时间和原因。
- 公共读取只返回建议内容、安全状态、公开说明、点赞数和时间；作者本人可读取“我的建议”。超级管理员仅为滥用处置读取内部用户 ID 和公开名称，不返回 email。账号删除后作者、点赞者和处理者外键置空，建议、历史点赞与事件匿名保留，历史有效点赞仍计数。
- 建议不物理删除；取消点赞以不可变旧行的取消状态和时间表达，再点赞形成新活动事实；提交、评估、重新评估、撤回、重复归档、隐藏和恢复均追加独立事件，排名从事实重算。
- 第一版不建设用户举报、评论、回复、附件、标签、搜索、关注通知、语义去重、点赞转移、建议合并、完成状态、外部工单同步、自动内容审核、封禁、关键词库或批量处罚；最小滥用边界为登录、每日提交上限、纯文本渲染和超级管理员隐藏 / 恢复。

### 当前推进原则

- 优先保障衣柜录入、图鉴提交、审核入库、提交者衣柜写回等已验证主流程稳定。
- 积分 / 贡献者 / 重审池 / 报错修正按最小闭环逐步落地。
- 排行榜实时总榜、实时当月榜、上月冻结榜和普通管理员月度轮换均按独立最小闭环推进；视觉权益继续后置。
