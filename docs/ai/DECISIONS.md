# 决策记录

用途：记录已经确认的产品、技术和流程决策，作为当前项目规则的唯一真实来源。需求文档、开发文档和技术实现文档如与本文冲突，以本文为准。

## Rule Lock Phase 1

本阶段将规则分为三类：

- Final：已确认，可直接作为开发输入。
- User Decision Required：需用户确认，确认前不得开发会固化该规则的功能。
- Rejected Ideas：废弃设计，不再作为默认方案推进。

## Final

### AI 协作流程

- ChatGPT 负责整理任务、写任务单、判断下一步。
- Codex 负责按任务单执行。
- 用户负责功能审核、流程把控、产品测试和最终产品判断。
- Codex 完成阶段任务后，应记录执行结果；若当前任务禁止修改 `CODEX_REPORT.md`，则在最终回复中输出报告。

### 数据库安全

- 不直接操作 production。
- production 写库脚本不放入可提交路径。
- 涉及数据库前必须确认 dev / prod 状态。
- 数据库任务必须先看数据库安全文档和变更记录。
- 生产数据库变更前必须经过 development 验证、备份确认和回滚方案确认。

### 管理员审核卡片文案

- UI 不使用：版本、变体、字段组合、冲突版本、一致提交。
- UI 使用：资料一致情况、最多人认可、不同意见、可按多数入库、需要继续收集。
- 5 人以上相同且无不同意见：状态显示为“可入库”。
- 5 人以上相同但有不同意见：状态显示为“可按多数入库”。
- 有不同意见但未达到 5 人：状态显示为“需要继续收集”。
- 人数不足保持“人数不足”。

### 积分第一版规则

- 积分权威来源为 `points_ledger`。
- `profiles.total_points`、`profiles.current_month_points`、`profiles.monthly_action_count` 不作为权威积分来源；如后续保留，只能作为历史字段或可重建缓存。
- 图鉴 / 衣柜条目审核通过并成功入库后，符合最终入库数据的有效提交者获得积分。
- 第一版积分值：每个有效提交者 +10 分。
- 第一版积分状态：默认 `awarded`。
- `awarded` 积分在审核通过后立即生效。
- 积分写入只做追加流水，不直接覆盖用户总分。

### 前 5 有效提交者规则

- 有效提交者必须满足：提交数据与最终入库数据一致，且 `submitted_by` 可识别为真实用户。
- 有效提交者按提交时间升序排序。
- 只取前 5 个有效提交者获得本次入库积分。
- 匿名历史数据不补造真实用户身份。

### 前 3 展示贡献者规则

- 页面展示贡献者从前 5 有效提交者中产生。
- 展示贡献者按提交时间升序排序。
- 页面最多展示前 3 位贡献者。

### 缺套装入库规则

- 缺套装但短编号完整、核心字段完整的数据允许进入正式库。
- 入库同时创建 `re_review_items`。
- `re_review_items` 状态标记为待补套装。
- `re_review_items` 是待补套装状态的权威追踪来源。

### `re_review_items` 第一版使用规则

- 第一版用于追踪：待补套装、字段冲突、字段缺失、报错转重审。
- 第一版不做完整陪审团投票闭环。
- 第一版不允许普通用户直接覆盖正式库。
- 重审修正不得绕过审核直接改正式库。

### 当前推进原则

- 优先保障衣柜录入、图鉴提交、审核入库、提交者衣柜写回等已验证主流程稳定。
- 积分 / 贡献者 / 重审池 / 报错修正按最小闭环逐步落地。
- 暂不直接开发排行榜、复杂权益、普通管理员轮换、完整陪审团系统等大模块。

### AIOS v1.1 轻量协作机制

- 采用轻量版 AIOS v1.1，用于沉淀 Lessons、Rules、Rejected Ideas、Weekly Review 和可复用 Prompt。
- 不一次性搭复杂系统，优先保持文档可读、可审查、可维护。
- Rule 必须经用户本人审核后才能进入正式规则。
- ChatGPT 只能提出 Lesson / Pattern / Rule Candidate，不能自行批准正式 Rule。
- Codex 按当前任务单和已批准规则执行。
- Gemini 用于 challenge、发现反例和风险，不负责批准规则。
- 使用 `REJECTED_IDEAS.md` 记录未采纳方案、拒绝原因和未来重新考虑条件。

## User Decision Required

- 正式库已有但资料不全时，是只补空字段，还是允许覆盖已有非空字段。
- 自动入库、管理员仲裁、正式库补全、重审修正、报错修正是否都使用 +10 分，还是按来源配置不同分值。
- 积分扣回是否只追加负数流水，不删除原流水。
- 匿名历史数据是否在页面展示为“匿名历史数据”，以及是否参与前 5 / 前 3 展示。
- 待补套装状态什么时候关闭：绑定正式套装后自动关闭，还是需要管理员确认关闭。
- 重审项是否允许普通用户提交候选修正版，还是第一版只允许管理员处理。
- 报错修正哪些字段属于低风险，哪些字段属于高风险。
- 报错通过是否奖励报错者积分。
- 报错导致原数据被推翻时，原贡献者积分是否进入 pending 或直接扣回。
- `game_id = N` 或缺编号时是否完全不计分。
- Lv4 可信权重是否参与自动入库。
- 管理员终审是否写入 `jury_votes`，还是单独建立终审记录。
- 上月前 10 权益是广告免除权、首页鸣谢，还是两者都有。
- 月榜冻结由数据库定时任务、手动触发，还是前端读取时计算。
- 当前没有独立服装详情页时，贡献者展示先放在哪里。
- 陪审团入口放首页、后台，还是单独页面。
- 重审池是否对普通用户开放。
- 报错入口是否所有登录用户可见。
- 套装名称唯一性按原始名称，还是按 trim / 统一大小写 / 简繁处理后的标准名。
- 是否允许先建表但不接 UI，用于逐步迁移。
- 低风险项 / 高风险项的判定规则。
- 普通管理员是否能驳回数据，还是只能提交终审建议。
- 异常刷分用户是否能进入管理员候选。

## Rejected Ideas

- 废弃：图鉴审核通过后的积分默认先进入 `pending` 等管理员确认。当前第一版规则为默认 `awarded` 并立即生效。
- 废弃：使用 `profiles` 保存权威积分总分。当前规则为 `points_ledger` 是唯一权威积分来源。
- 废弃：前 3 展示贡献者按积分、信用等级或最终一致度排序。当前第一版规则为从前 5 有效提交者中按提交时间排序取前 3。
- 废弃：缺套装但编号完整的数据必须留在 pending，不能进入正式库。当前规则为允许入库，并创建 `re_review_items` 追踪待补套装。
- 废弃：重审修正直接覆盖正式库且无记录。当前规则为重审修正必须可追踪，不得绕过审核直接改正式库。
