# 测试清单

用途：记录需要人工或自动验证的测试项，帮助确认改动是否满足预期且未引入回归。

## Preview / Production 人工回归测试清单

### 1. 衣柜保存与刷新后数量稳定

- 测试目标：确认用户录入大量衣服后，刷新页面不会从几千件异常缩水到一百多件。
- 操作步骤：
  1. 使用已登录账号进入“我的衣柜”。
  2. 记录当前总收集数量。
  3. 连续新增或取消若干衣服，触发云端同步。
  4. 等待同步完成提示消失。
  5. 刷新页面并重新进入“我的衣柜”。
  6. 对比刷新前后的总收集数量和最近操作的衣服状态。
- 预期结果：
  - 刷新后总收集数量稳定。
  - 最近新增或取消的衣服状态正确保留。
  - 页面不长时间卡在“正在同步到云端”。
- 是否通过：通过

### 2. 按分类 + 短编号录入衣柜

- 测试目标：确认用户可通过选择分类并输入短编号批量录入已有图鉴衣服。
- 操作步骤：
  1. 进入“录入衣柜”。
  2. 选择一个分类，例如“发型”或“连衣裙”。
  3. 输入多个短编号，例如 `0001, 0002, 0003`。
  4. 提交录入。
  5. 查看录入结果报告。
  6. 返回“我的衣柜”确认对应衣服已加入。
- 预期结果：
  - 正式库存在的编号进入“本次成功录入”。
  - 未匹配到图鉴编号的项目进入缺失提示。
  - 成功录入的衣服刷新后仍保留在衣柜中。
- 是否通过：通过

### 3. 管理员审核卡片文案

- 测试目标：确认管理员审核卡片不再出现技术感文案，并按确认口径展示状态。
- 操作步骤：
  1. 使用管理员账号进入“图鉴管理”。
  2. 查看“自动入库候选”中的不同卡片。
  3. 分别检查全部一致、多数一致但有不同意见、未达 5 人、人数不足的展示。
  4. 打开卡片详情或入库表单，查看提示文案。
- 预期结果：
  - 页面不出现“版本 / 变体 / 字段组合 / 冲突版本 / 一致提交”。
  - 使用“资料一致情况 / 最多人认可 / 不同意见 / 可按多数入库 / 需要继续收集”等文案。
  - 全部一致显示“可入库”。
  - 多数一致但有不同意见显示“可按多数入库”。
  - 有不同意见但未达 5 人显示“需要继续收集”。
  - 人数不足显示“人数不足”。
- 是否通过：通过

### 4. 正式库已有但资料不全的补全路径

- 测试目标：确认正式库已有同名同分类衣服但资料不全时，管理员可从 pending 补全缺失资料。
- 操作步骤：
  1. 在管理员审核页面找到“正式库已有但资料不全”的待处理项。
  2. 打开补全表单。
  3. 检查名称、分类、短编号、星级、五组属性、套装状态、特殊标签等字段。
  4. 补齐缺失字段并提交。
  5. 返回正式库或前台图鉴页面检查该衣服资料。
- 预期结果：
  - 提交不因唯一约束重复而失败。
  - 正式库已有记录被补齐缺失资料。
  - 已有的非空资料不被意外覆盖。
  - 页面给出清晰的成功或失败提示。
- 是否通过：通过

### 5. Pending 状态变化

- 测试目标：确认审核或补全后，相关 pending 记录状态按预期变化。
- 操作步骤：
  1. 在管理员页面记录待处理项数量。
  2. 对一个可入库或可补全的项目执行处理。
  3. 处理完成后刷新管理员页面。
  4. 查看该项目是否仍出现在原待处理列表。
  5. 如页面提供状态信息，检查状态是否从 pending 变为 approved、re_review 或其他预期状态。
- 预期结果：
  - 已处理项目不再重复出现在原待处理列表。
  - 未入库的不同意见提交不会被误标为已入库。
  - 状态变化和页面展示一致。
- 是否通过：通过

### 6. 提交者衣柜写回

- 测试目标：确认用户提交的缺失衣服入库或补全后，会自动进入提交者衣柜。
- 操作步骤：
  1. 使用普通用户提交一个缺失图鉴项。
  2. 使用管理员账号审核通过或补全该项目。
  3. 回到普通用户账号。
  4. 进入“我的衣柜”搜索该衣服。
  5. 刷新页面后再次检查。
- 预期结果：
  - 审核通过或补全后，该衣服出现在提交者衣柜中。
  - 刷新后仍保留。
  - 不会误加入未参与提交的用户衣柜。
- 是否通过：通过

### 7. 套装选择与刷新

- 测试目标：确认所属套装加载稳定，选择套装或无关联套装后不会卡死，刷新后展示一致。
- 操作步骤：
  1. 进入缺失图鉴补录或管理员补全表单。
  2. 点击“所属套装”输入框。
  3. 搜索已有套装并选择。
  4. 再测试选择“无关联套装（纯散件）”。
  5. 提交或关闭后刷新页面。
  6. 重新打开同一表单或相关列表检查展示。
- 预期结果：
  - 套装列表可以正常出现。
  - 选择已有套装后展示套装名称。
  - 选择无关联套装时在输入框内清晰展示，不出现框外重复提示。
  - 页面不假死、不长时间空白。
- 是否通过：通过

### 8. 生产环境不显示 Vue DevTools

- 测试目标：确认 production 构建不会加载 Vue DevTools。
- 操作步骤：
  1. 打开 production 站点。
  2. 打开浏览器开发者工具。
  3. 查看控制台和扩展面板。
  4. 刷新页面后再次确认。
- 预期结果：
  - 生产环境不出现 Vue DevTools 注入提示。
  - 不加载开发环境专用调试工具。
  - 页面正常渲染，无构建相关报错。
- 是否通过：通过

### 9. DB-8 正式图鉴报错受理

- 验收状态：待最小权限 patch 应用后由负责人验证。
- 测试范围：只验证用户提交报错、本人记录、刷新 / 重进和幂等提示；不验证管理员处理、转陪审、正式库修正或报错积分。
- 目标环境：仅 development / Preview，项目 ref `tfwejruvdahonacyldrg`；不得进入 production。
- 前置条件：
  1. 使用一个 development 普通用户账号登录。
  2. 任选一件已存在的正式服装，记录其名称、短编号、星级和当前积分。
  3. 建议内容使用明显的测试标记，例如“DB8验收：建议改为四星”，不要填写真实用户隐私。
- 操作步骤：
  1. 进入“图鉴报错”，用服装名称或短编号搜索并选择记录。
  2. 依次切换“服装名称、短编号、分类部位、星级、属性分值、所属套装、特殊标签、其他资料”，确认页面能明确显示当前记录。
  3. 选择一个问题字段，填写 1–500 字建议和 10–1000 字判断依据后提交。
  4. 确认成功提示明确说明提交不会直接修改正式图鉴，并在“我的报错记录”看到同一服装、字段、建议、依据和“等待处理”。
  5. 刷新页面并离开后重新进入“图鉴报错”，确认记录仍可读取，页面不空白、不假死。
  6. 对同一服装、同一字段再次提交完全相同的建议和依据，确认提示已有记录且不新增第二条。
  7. 对同一服装、同一字段改写建议或依据后再次提交，确认系统拒绝覆盖待处理报错。
  8. 返回正式图鉴和用户中心，确认服装原资料与积分均未变化；如可使用第二个 development 账号，确认其“我的报错记录”看不到第一账号的记录。
- 预期结果：
  - 仅登录用户可以提交；匿名用户没有入口，数据库也拒绝调用。
  - 同一活动报错相同重试幂等、不同内容不可覆盖。
  - 刷新、离开重进和请求回读不会丢失已有记录或锁死页面。
  - 受理动作不修改正式服装、不创建陪审事项、不发放积分。
- 异常反馈格式：

```text
环境：development / Preview
账号角色：普通用户
步骤：9.x
服装名称与短编号：
问题字段：
结果：通过 / 失败
页面实际提示：
发生时间（北京时间，精确到分钟）：
刷新或重进后是否恢复：是 / 否
是否已停止后续操作：是 / 否
```

- 测试数据处置：报错记录作为 development 验收事实保留，便于后续管理员处理功能复用；不复制到 production。
- 清理 / rollback：当前页面不提供删除报错；若必须清理，停止验收并单独申请精确 development SQL 授权，不直接改表、不删除 migration history。已应用 schema 如需撤销，只能使用新的前向 migration。
