# 工作流优化方案

## 0. 目标

在保持生产风险可控的前提下，减少缺陷处理的等待和重复确认。

核心原则：

1. 生产安全优先，不为速度跳过 dev 验证。
2. 小前端缺陷快速闭环，不强制写长方案。
3. 数据库 / 权限 / RLS / RPC 变更必须走 migration。
4. 工作区按功能提交，避免多个缺陷混在一个提交里。

## 1. 缺陷分级流程

### A 类：纯前端体验问题

适用范围：

- UI 文案、显示状态、页面刷新体验。
- 不修改数据库结构。
- 不影响权限、积分、正式库写入。

流程：

1. 登记缺陷一句话。
2. 直接修复。
3. 执行 `npm.cmd run build`。
4. 用户验证。
5. 更新缺陷状态为“已修复”。
6. 单独提交。

推荐提交格式：

```powershell
git commit -m "修复：<问题描述>"
```

### B 类：数据库 / 权限 / RPC 问题

适用范围：

- schema、RLS、RPC、trigger、批量数据修复。
- 权限、管理员、积分、正式库写入链路。

流程：

1. 登记缺陷。
2. 写 migration。
3. 本地执行安全检查：

```powershell
npm.cmd run db:check
```

4. 仅对 development 执行：

```powershell
npm.cmd run db:push:dev
npm.cmd run db:types:safe
npm.cmd run build
```

5. 用户在 dev 预览环境冒烟测试。
6. 更新数据库变更记录和缺陷状态。
7. 单独提交。

production 执行前必须额外确认：

- 已备份。
- dev 已验证。
- migration 文件已提交。
- 回滚方案已写入数据库变更记录。

### C 类：需求风险 / 产品口径不明

适用范围：

- 会改变用户路径、审核规则、积分规则、权限边界。
- 需求存在多种合理解释。

流程：

1. 先写风险点。
2. 给出 1 到 2 个推荐方案。
3. 等用户确认后再开发。

## 2. 日常命令

前端验证：

```powershell
npm.cmd run build
```

确认当前 Supabase link 是否为 dev：

```powershell
npm.cmd run db:check
```

数据库变更后的一键安全验证：

```powershell
npm.cmd run verify:db
```

只推 dev migration：

```powershell
npm.cmd run db:push:dev
```

## 3. 提交策略

推荐每次最多提交一种类型的变更：

| 类型 | 示例 |
| --- | --- |
| 前端缺陷 | `修复：昵称修改后即时显示` |
| 数据库缺陷 | `修复：迁移用户角色为数字权限` |
| 文档 | `文档：补充产品设计书` |
| 流程 | `流程：增加数据库开发安全检查` |

不要把以下内容混在同一个提交：

- 数据库 migration 和无关 UI 调整。
- 用户未验证的实验代码和已验证修复。
- 生产配置和 dev 测试数据。

## 4. 工作区收口清单

每轮结束前检查：

1. `git status --short` 是否只剩明确暂缓文件。
2. 已验证功能是否都有独立提交。
3. 未验证功能是否还停留在工作区或单独分支。
4. 数据库变更记录是否写明 dev / production 状态。
5. 缺陷文档状态是否和实际一致。

## 5. 当前建议节奏

1. 先处理已验证且低风险的提交。
2. 再提交数据库类已验证变更。
3. 最后保留未验证 / 未归属文件，不强行收进提交。
