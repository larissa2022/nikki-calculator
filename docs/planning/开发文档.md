# 开发文档

## 0. 开发原则

本文档基于 [`需求文档.md`](../requirements/需求文档.md) 制定，用于指导后续图鉴审核、积分、重审、报错和权限体系开发。

开发原则：

1. 功能以当前 [`需求文档.md`](../requirements/需求文档.md) 为准。
2. 遇到需求风险、规则冲突、字段缺失或会改变用户行为的地方，先暂停并向产品确认，不直接开发。
3. 优先实现数据闭环，再实现界面和视觉权益。
4. 所有积分、贡献、投票、审核结果必须可追溯。
5. 线上数据变更前必须先确认迁移影响，涉及批量更新时单独确认。

## 2. 阶段一：数据库基础层

### 2.1 目标

建立后续审核闭环所需的数据基础，保证贡献、积分、投票、重审都能被记录和审计。

### 2.2 计划新增或调整

建议新增：

| 表 / 字段 | 用途 |
| --- | --- |
| `re_review_items` | 标记并追踪“缺套装但编号完整”的正式服装，以及其他重审项 |
| `clothing_contributions` | 记录贡献者、来源 pending、奖励状态 |
| `points_ledger` | 权威积分流水，支持发放、待定、扣回和月榜冻结 |
| `jury_votes` | 陪审团投票记录，支持权重、去重、防自审 |
| `correction_requests` | 用户报错和正式库修正流程 |
| `admin_terms` | 普通管理员月度任期记录 |

### 2.3 建议约束

- `suits.name` 建议唯一或做标准化唯一约束。
- `jury_votes` 对同一用户、同一审核对象只能投一次。
- `clothing_contributions` 对同一 `clothes_id + user_id + contribution_type` 做去重。
- `points_ledger` 是积分唯一权威来源，不直接覆盖积分，只追加流水。
- `profiles` 不维护权威总分；总分通过 view / RPC 汇总，后期可加可重建缓存。
- `admin_terms` 需要保存任期月份、来源、开始时间、结束时间和状态。

### 2.4 暂停确认点

开始开发前必须确认：

1. 套装名称唯一性是否按原始名称，还是按 trim / 统一大小写 / 简繁处理后的标准名。
2. 是否允许先建表但不接 UI，用于逐步迁移。

已确认：

- 缺套装待补状态使用 `re_review_items` 追踪。
- 积分使用方案 C：`points_ledger` 为权威来源，view / RPC 汇总，缓存只作展示加速。

### 2.5 验收标准

- Supabase migration 可重复追踪。
- [`schema.md`](../database/schema.md) 和 `supabase/schema.sql` 可更新。
- 新表具备 RLS 或访问控制策略。
- 不影响现有图鉴查询、缺失项补录、管理员入库功能。

## 3. 阶段二：提交与自动入库闭环

### 3.1 目标

完善现有提交 RPC，使“5 次一致自动入库”“前 5 个有效提交者奖励”“缺套装标记”形成闭环。

### 3.2 开发内容

- 调整 `submit_clothing_contribution` RPC。
- 入库时写入 `clothing_contributions`。
- 根据最终入库数据匹配有效提交者。
- 对前 5 个有效提交者生成待发放或已发放积分流水。
- 对缺套装但编号完整的数据写入正式库，并创建 `re_review_items` 追踪套装待补状态。
- 对字段不一致的 5 次提交转入人工仲裁或重审。

### 3.3 暂停确认点

遇到以下情况暂停确认：

1. `game_id = N` 或缺编号时，是否完全不计入“同一 `category + game_id` 只能计分一次”。
2. 缺套装但编号完整的数据进入正式库后，是否展示给普通用户使用。
3. 自动入库时，如果 5 条提交中只有部分字段一致，是否允许管理员用众数合并。
4. 积分发放是自动发放，还是先进入 pending 状态等待管理员确认。

### 3.4 验收标准

- 同一用户重复提交不会污染 5 次一致判断。
- 5 次完全一致可自动入库。
- 入库后能追踪前 5 个有效提交者。
- 积分流水能找到来源 pending 记录。
- 缺套装数据不会丢失待补状态。

## 4. 阶段三：陪审团投票机制

### 4.1 目标

实现用户赞同 / 驳回机制，并按信用等级计算净胜票。

### 4.2 开发内容

- 新增投票 API 或 RPC。
- 根据用户积分等级计算投票权重。
- 防止用户审核自己的提交。
- 防止同一用户重复投票。
- 根据净胜票触发状态流转：
  - 字段完整且候选唯一，净胜达到 5 可入库。
  - 字段缺失或候选冲突，净胜达到 5 进入管理员终审或重审完成流程。
  - 净胜达到 -3 进入重审。

### 4.3 暂停确认点

遇到以下情况暂停确认：

1. Lv4 的“可信权重 +3”是否只用于陪审团投票，不参与自动 5 次入库。
2. 管理员投票是否算普通投票，还是作为终审动作单独记录。
3. 候选数据冲突时，用户是否只能赞同 / 驳回，还是可以选择某个候选版本。

已确认：

- 陪审团阈值使用“达到阈值”触发，不要求恰好等于阈值。

### 4.4 验收标准

- 用户不能投自己的提交。
- 投票权重按等级生效。
- 投票记录可审计。
- 达到阈值后状态自动流转。
- 字段缺失数据不会被普通投票直接推入正式库。

## 5. 阶段四：重审与报错机制

### 5.1 目标

将缺编号、字段冲突、正式库报错从普通 pending 中拆出，形成可修正、可追踪、可关闭的重审流程。

### 5.2 开发内容

- 建立 `re_review_items` 流程。
- 建立 `correction_requests` 流程。
- 重审项支持补全字段后重新进入 pending。
- 报错通过后可更新 `clothes`。
- 核心字段错误触发积分待定或扣回流程。

### 5.3 暂停确认点

遇到以下情况暂停确认：

1. 报错修正哪些字段时不扣分，哪些字段时需要进入积分待定或扣回。
2. 被重审推翻的数据是否保留原贡献者署名。
3. 重审项是否允许普通用户直接编辑，还是只能提交候选修正版。

已确认：

- 重审净胜达到 5 且字段完整后，进入正式库。

### 5.4 验收标准

- 重审项来源可追踪。
- 重审修正不会直接覆盖正式库而无记录。
- 报错处理流程有明确状态。
- 积分调整有流水。

## 6. 阶段五：管理员制度

### 6.1 目标

实现普通管理员和超级管理员的职责边界，避免自审和越权。

### 6.2 开发内容

- 普通管理员可处理低风险项。
- 高风险项、争议项、自己参与过的项不展示。
- 超级管理员可最终裁决。
- 超级管理员可手动授权或取消普通管理员。
- 月度管理员轮换记录写入 `admin_terms`。

### 6.3 暂停确认点

遇到以下情况暂停确认：

1. “低风险项”和“高风险项”的具体判定规则。
2. 普通管理员是否能驳回数据，还是只能提交终审建议。
3. 异常刷分用户是否能进入管理员候选。

已确认：

- 普通管理员月度轮换第一版按规则自动执行，并写入 `admin_terms`。

### 6.4 验收标准

- 管理员看不到自己参与过的审核项。
- 普通管理员不能处理争议项和高风险项。
- 超级管理员可做最终裁决。
- 任期变更可追踪。

## 7. 阶段六：积分、排行榜与权益

### 7.1 目标

基于积分流水生成等级、排行榜、月榜冻结和权益展示。

### 7.2 开发内容

- 从 `points_ledger` 通过 view / RPC 汇总用户总积分。
- `profiles` 不保存权威积分总分；如需性能优化，可建立可重建缓存。
- 生成当月榜、上月榜、总榜。
- 每月 1 日按 UTC+8 冻结上月榜。
- 计算 Lv1 至 Lv4 等级。
- 接入投票权重、贡献者排序、首页鸣谢、广告免除权。

### 7.3 暂停确认点

遇到以下情况暂停确认：

1. 月榜冻结用数据库任务、手动触发，还是前端读取时计算。
2. 上月前 10 的权益是“广告免除权”还是“首页滚动鸣谢”。当前需求文档中两处表述不完全一致。
3. 贡献者名单前 3 位按提交时间、积分、信用等级，还是最终一致度排序。
4. Lv4 当月榜首体验卡是否和累计 10000 分永久权益共用同一字段。

### 7.4 验收标准

- 总积分可由流水复算。
- 月榜可按 UTC+8 冻结。
- 等级和投票权重一致。
- 权益展示不影响核心审核流程。

3. 重审池是否对普通用户开放。

## 10. 推荐开发顺序

建议按以下顺序推进：

1. 确认剩余暂停点。
2. 新增数据库基础表和必要约束。
3. 改造自动入库 RPC，写入贡献和积分流水。
4. 接入陪审团投票。
5. 建立重审和报错流程。
6. 完善管理员权限边界与自动轮换。
7. 实现排行榜和高信用权益。
8. 做前端整合和体验修正。
