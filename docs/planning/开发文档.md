# 开发文档

## 0. 开发原则

本文档基于 [`需求文档.md`](../requirements/需求文档.md) 制定，用于指导后续图鉴审核、积分、重审、报错和权限体系开发。

规则来源说明：

- [`DECISIONS.md`](../ai/DECISIONS.md) 是当前唯一真实规则源。
- 本文档只记录开发阶段、落地顺序和暂停点；如与 `DECISIONS.md` 冲突，以 `DECISIONS.md` 为准。
- 本文档属于执行计划层，承接已确认需求，用于拆分阶段、暂停点、验收标准和开发顺序。
- 本文档不承载 Final 决策；未写入 `DECISIONS.md` 的待确认事项不得直接进入实现。
- 从需求进入开发前，必须先确认需求来源、已确认规则、未确认事项、技术影响和风险分类。

开发原则：

1. 功能以当前 [`需求文档.md`](../requirements/需求文档.md) 为准。
2. 遇到需求风险、规则冲突、字段缺失或会改变用户行为的地方，先暂停并向产品确认，不直接开发。
3. 优先实现数据闭环，再实现界面和视觉权益。
4. 所有积分、贡献、投票、审核结果必须可追溯。
5. 线上数据变更前必须先确认迁移影响，涉及批量更新时单独确认。

## 0.2 Rule Lock Phase 1：规则冻结摘要

本节只摘要规则冻结结果，完整可执行定义以 [`DECISIONS.md`](../ai/DECISIONS.md) 为准。

### Final

- 积分权威来源为 `points_ledger`。
- 图鉴 / 衣柜条目审核通过并成功入库后，符合最终入库数据的有效提交者获得积分；自动入库 / 管理员仲裁 +10、正式库空字段补全 +5、重审修正 +8、报错通过 +5。
- 第一版积分状态默认 `awarded`，审核通过后立即生效。
- 积分只追加流水；扣回追加负数流水，不修改或删除历史记录。
- 前 5 有效提交者按提交时间排序取前 5。
- 前 3 展示贡献者从前 5 有效提交者中按提交时间排序取前 3。
- 匿名历史数据不补造真实用户身份；缺编号数据不进入积分判断分支。
- 缺套装但编号完整、核心字段完整的数据允许正式入库，同时创建 `re_review_items`，状态为待补套装。
- `re_review_items` 是待补套装状态的权威追踪来源。
- 重审池采用“社区参与、系统处理、管理员兜底”；未参与原始提交的登录用户可以提交候选修正版，原提交者和来源参与者不得自审，普通用户不能直接覆盖正式库。

### User Decision Required

- 当前重审池基础没有待确认的参与边界；后续陪审团和最终处理进入对应阶段时单独确认。

### Rejected Ideas

- 废弃积分审核通过后默认 `pending`。
- 废弃 `profiles` 作为权威积分总分来源。
- 废弃前 3 展示贡献者按积分、信用等级或最终一致度排序。
- 废弃缺套装但编号完整的数据必须留在 pending。

本阶段按独立 database / business 批次逐步实施。DB-1 至 DB-6 基础和缺套装接入均已进入 development。其余未实现的 RPC、RLS 和前端入口仍必须先在 development 验证，production 执行前必须按数据库安全方案完成备份和确认。

### 0.3.1 积分流水 `points_ledger`

第一版目标：

- 新增权威积分流水，记录积分发放、扣回和来源。
- 支持从流水汇总用户总分、月积分和等级。
- 入库、补全、重审修正、报错修正产生积分时，只追加流水，不直接覆盖用户资料总分。

不做什么：

- 只做总榜与当月榜实时只读页面，不做上月榜冻结。
- 不做 Lv4 月榜首体验权益。
- 不做积分缓存表。
- 不删除 `profiles.total_points` 等历史字段，但明确它们不作为权威来源。

依赖哪些现有表 / RPC / 页面：

- 依赖 `profiles` 识别用户和角色。
- 依赖 `pending_clothes`、`clothes`、`submit_clothing_contribution` 和 `approve_pending_clothes_arbitration` 识别积分来源。
- 依赖后续 `clothing_contributions` 关联贡献者和积分来源。
- 前端第一版可只在管理端或个人中心展示只读结果，不影响现有录入流程。

已确认第一版口径：

- 积分状态默认 `awarded`。图鉴审核通过后，积分立即生效。
- 自动入库 / 管理员仲裁 +10，正式库空字段补全 +5；重审修正 +8、报错通过 +5 在后续阶段接入。
- 扣回只追加负数流水，不删除或修改原流水。

开发风险：

- 如果积分和贡献者不共用同一批“有效提交者”判定，会导致署名和得分不一致。
- 如果 `profiles.total_points` 被继续当作权威来源，会和流水汇总冲突。
- 如果积分默认自动发放，错误入库后的扣回流程必须同时可用。

建议开发顺序：

1. 先与 `clothing_contributions` 一起建立基础表、来源约束和追加式保护，不建立 public view，不接入现有 RPC。
2. 再单独建立最小只读查询面，并验证 Data API 暴露、table grants、RLS 和角色矩阵。
3. 最后按“正式库补全 → 管理员仲裁 → 自动入库”逐条接入写路径，每条路径独立验证和 rollback。

### 0.3.2 贡献者记录 / 前 5 有效提交者 / 前 3 展示

第一版目标：

- 新增贡献者记录，保存 `clothes_id`、`user_id`、来源 pending、贡献类型和积分状态。
- 入库或补全时记录前 5 个有效提交者。
- 预留前端展示前 3 位贡献者的数据来源。

不做什么：

- 不做复杂贡献者徽章。
- 不做贡献者主页。
- 不做动态彩名、首页鸣谢、广告免除。
- 不把匿名历史数据强行补成真实贡献者。

依赖哪些现有表 / RPC / 页面：

- 依赖 `pending_clothes.submitted_by` 识别提交者。
- 依赖 `clothes` 作为正式入库目标。
- 依赖 `submit_clothing_contribution`、`approve_pending_clothes_arbitration`、`complete_existing_clothes_from_pending` 的入库 / 补全结果。
- 依赖 `user_wardrobes` 写回逻辑保持“有效提交者”和“衣柜写回用户”一致。

来源追溯要求：

- 管理员仲裁和正式库补全当前会把 pending 标记为 `approved`，可保留 `source_pending_id`。
- 自动入库实现必须改为：当前提交先写入 pending，再将本次有效来源 pending 一起标记为 `approved`；不得删除来源 pending。
- 每条贡献必须关联保留的来源 pending；不可变快照只作补充证据，不替代 `source_pending_id`。
- 排名必须先按提交时间稳定排序，再按用户去重并取前 5；不得使用无序 `array_agg(distinct submitted_by)` 直接生成贡献排名。
- 同一次初始入库中，自动入库与管理员仲裁互斥且每个用户只奖励一次；后续补全、重审、报错等独立有效事件可以分别奖励，但每个来源事件必须幂等。
- 账号删除后保留贡献和流水，用户关联置空并显示“已注销用户”，不得级联删除历史事实。

需用户确认：

- 匿名历史数据是否展示为“匿名历史数据”，以及是否参与前 5 / 前 3。

已确认第一版口径：

- 前 5 有效提交者：与最终入库数据一致的提交者，按提交时间排序，取前 5 个获得积分。
- 前 3 展示贡献者：从前 5 有效提交者中，按提交时间排序，取前 3 个用于页面展示。

开发风险：

- 当前生产存在 `submitted_by is null` 的历史 pending，不能强行计入真实贡献者。
- 如果管理员仲裁选择的 pending 集合含有少数错误提交者，贡献者记录可能被污染。
- 贡献者写入和衣柜写回如果分散在前端，会出现漏写或重复写。

建议开发顺序：

1. 先建立 `clothing_contributions` 去重约束和只读查询。
2. 再把自动入库、管理员仲裁、正式库补全统一写入贡献者记录。
3. 最后接入前 3 展示位置。

#### 0.3.3.3 database PR 拆分顺序

1. **development 只读前检（无 PR / 无写入）**：确认 project ref、migration list、schema / types 漂移、`clothes(category, game_id)` 重复键、现有 RLS / grants / function execute 和 Security Advisor。
2. **DB-1 基础事实表**：只新增 `clothing_contributions`、`points_ledger`、外键 / 唯一约束 / 必要索引和 RLS 默认拒绝；不建 public view，不开放客户端写入，不改现有 RPC，不回填历史。
3. **DB-2 最小只读面**：单独增加“用户读自己的积分”和“贡献者公开展示候选”的查询接口；分别验证 Data API 暴露、table grants、RLS、`security_invoker` 和 anon / authenticated / admin / super admin。
4. **DB-3 正式库补全接入**：只改 `complete_existing_clothes_from_pending`，同事务写贡献、积分和原有衣柜写回；验证 +5、前 5、重试幂等和旧功能不退化。
5. **DB-4 管理员仲裁接入**：只改 `approve_pending_clothes_arbitration`，增加服务端候选一致性校验后写贡献与 +10 积分。
6. **DB-5 自动入库接入**：按已确认规则改 `submit_clothing_contribution`，保留并批准来源 pending；自动入库、来源保存、衣柜写回、贡献和 +10 积分必须同事务完成。
7. **business / frontend PR**：数据库链路稳定后再展示积分和前 3 贡献者；不与 database PR 混合。
8. **历史回填**：单独设计、单独授权；匿名或来源不完整记录不得补造用户身份。

每一项均以前一项在 development 验证通过为前置；任一项失败即停止，不继续下一个 PR。

### 0.3.4 重审池 `re_review_items`

第一版目标：

- 承接缺套装、字段冲突、字段缺失、被报错后需要修正的数据。
- 记录来源、原因、状态、原始 payload、处理人和处理结果。
- 让“暂不入库 / 需要补全 / 需要管理员确认”的数据不再混在普通 pending 中。

不做什么：

- 不做完整陪审团投票。
- 不做普通用户直接覆盖正式库。
- 不做复杂的多候选版本编辑器。
- 不强行迁移所有历史 pending。

依赖哪些现有表 / RPC / 页面：

- 依赖 `pending_clothes` 当前状态流转。
- 依赖 `clothes` 关联正式库已有条目。
- 依赖 `ClothesEntryForm.vue` 作为后续重审修正表单，但本阶段不开发 UI。
- 依赖管理员审核入口后续展示重审池列表。

已确认第一版口径：

- 缺套装但编号完整的数据允许正式入库，同时创建 `re_review_items`，状态为待补套装。
- 未参与原始提交的登录用户可提交候选修正版；原提交者和全部来源参与者不得自审，管理员作为兜底，候选不能直接覆盖正式库。

开发风险：

- 待补套装状态必须在绑定正式套装后自动关闭，不能依赖管理员手动收口。
- 如果重审项直接更新正式库，会破坏审计链路。
- 如果没有清晰关闭状态，重审池会变成新的积压池。

建议开发顺序：

1. 先定义 `re_review_items` 原因和状态。
2. 再接入字段冲突、缺套装、报错转重审三类来源。
3. 最后规划管理端重审池 UI。

### 0.3.5 报错修正 `correction_requests`

第一版目标：

- 允许用户对正式库服装提交错误报告和建议修正。
- 记录报错原因、建议 patch、提交者、处理状态和审核人。
- 报错通过后进入管理员修正或重审流程，而不是直接改正式库。

不做什么：

- 不做留言板优化建议。
- 不做点赞排序。
- 不做自动覆盖正式库。
- 不做复杂处罚或即时扣分。

依赖哪些现有表 / RPC / 页面：

- 依赖 `clothes` 作为被报错对象。
- 依赖 `profiles` 和角色判断处理管理员权限。
- 依赖后续 `re_review_items` 承接非空字段修改和争议修正。
- 用户报错入口和本人进度查询已实现；管理员处理入口仍后置。

已确认边界：

- 正式库空字段补全走管理员审核；非空字段修改或争议修正进入审核库和陪审团路径。
- 报错通过奖励 +5；如需扣回历史积分，只能追加负数流水。
- 第一版不使用“低风险 / 高风险字段分级表”作为执行规则。

开发风险：

- 如果报错修正可以直接覆盖正式库，容易绕过审核。
- 如果所有报错都进入管理员终审，可能形成积压。
- 如果积分扣回规则未确认，报错修正会影响贡献者权益争议。

建议开发顺序：

1. 已建立 `correction_requests` 记录表、提交 / 本人查询 RPC 和用户入口；受理不修改正式库、不触发重审或积分。
2. 下一步接入管理员处理状态。
3. 最后把非空字段修改和争议修正转入 `re_review_items`，并按确认规则结算报错奖励。

### 0.3.6 阶段建议开发顺序

1. `clothing_contributions` 与 `points_ledger`：先保证贡献和积分来源可审计。
2. 入库 / 补全 RPC 接入贡献者记录和积分流水：保证当前已验证主流程不退化。
3. `re_review_items`：承接不能直接入库或需要补全的数据。
4. `correction_requests`：受理入口已建立；管理员处理及非空字段修改、争议修正转重审仍待独立接入。
5. 陪审团投票、排行榜、普通管理员轮换后置，等待本阶段闭环稳定后再拆下一阶段。

## 3. 阶段二：提交与自动入库闭环

### 3.1 目标

完善现有提交 RPC，使“5 次一致自动入库”“前 5 个有效提交者奖励”“缺套装标记”形成闭环。

### 3.2 开发内容

- 调整 `submit_clothing_contribution` RPC。
- 入库时写入 `clothing_contributions`。
- 根据最终入库数据匹配有效提交者。
- 对前 5 个有效提交者生成已发放积分流水，第一版默认 `awarded`。
- 对缺套装但编号完整的数据写入正式库，并创建 `re_review_items` 追踪套装待补状态。
- 对字段不一致的 5 次提交转入人工仲裁或重审。

### 3.3 已确认执行边界

1. 自动入库保留来源 pending 并标记 `approved`；不可变快照不替代来源记录。
2. 同一次初始入库每个用户只奖励一次；后续独立有效行为可按来源再次奖励，每个事件必须幂等。
3. 账号删除后保留贡献和流水，解除身份关联并显示“已注销用户”。

### 3.4 验收标准

- 同一用户重复提交不会污染 5 次一致判断。
- 5 次完全一致可自动入库。
- 入库后能追踪前 5 个有效提交者。
- 积分流水能找到来源 pending 记录。
- 缺套装数据不会丢失待补状态。

## 4. 阶段三：陪审团投票机制

### 4.1 目标

实现针对一份完整且投票期间不可替换资料的用户赞同 / 反对机制，并按一人一票计算结果。

### 4.2 开发内容

- 新增投票 API 或 RPC。
- 所有登录用户按一人一票计票，等级只用于排序和展示。
- 防止用户审核自己的提交。
- 防止同一用户重复投票。
- 管理员可按普通陪审员身份投一票，但投票后不能再终审同一审核项；终审单独记录。
- 根据票数触发状态流转：
  - 本轮完整资料获得至少 5 张同意票且同意票多于反对票时，按该资料修改正式库。
  - 字段缺失或冲突未处理完时保留在重审池，补充为一份完整资料后再投票。
  - 反对票数比同意票数至少多 3 时退回重审，要求重新补充完整资料，不修改正式库、不关闭审核项。
  - 未达到通过或退回门槛时保持投票状态，继续投票。
  - 永久驳回只允许由未参与该项投票的管理员通过独立终审决定。

### 4.3 已冻结规则

- 陪审团阈值使用“达到阈值”触发，不要求恰好等于阈值。
- 所有等级均为一人一票；Lv4 不获得额外票数。
- 管理员普通投票与管理员终审分开记录，同一人不得在同一审核项中兼任两种角色。
- 用户只对本轮一份完整资料赞同或反对；问题字段未处理完时不得发起普通投票。

### 4.4 验收标准

- 用户不能投自己的提交。
- 所有等级均按一人一票计票。
- 投票记录可审计。
- 达到阈值后状态自动流转。
- 退回重审不会修改正式库或把审核项标记为永久驳回。
- 未达到任一阈值时审核项继续投票。
- 字段缺失数据不会被普通投票直接推入正式库。
