## BUG-20260711-015 短编号无法唯一匹配时提示难以理解

### 现象

- 用户按分类和短编号录入衣柜时，部分编号在图鉴中对应多件服装。
- 浏览器弹窗提示“存在多个归一化短编号相同的图鉴条目，本次已跳过这些编号”。
- 用户看不懂“归一化短编号”和“图鉴条目”，也不知道应该如何继续录入。

### 影响

- 安全跳过逻辑本身有效，但错误文案会让用户误以为输入格式错误或系统故障。
- 用户不知道其他可识别编号仍会继续录入，也不知道可以改用名称录入。
- 影响“快速录入衣柜”核心流程的可理解性。

### 期望行为

- 使用普通玩家能理解的语言说明：图鉴中有多件服装使用相同编号，系统无法确定具体服装。
- 明确告知这些服装没有加入衣柜，其他可识别编号不受影响。
- 给出可执行的下一步：改用“按名称录入”。

### 修复记录

- 2026-07-11：优化短编号冲突弹窗，移除“归一化短编号、图鉴条目”等内部术语。
- 2026-07-11：同步优化录入结果报告，统一说明未录入原因、其他编号不受影响和按名称录入的处理方式。
- 待验证：在 development 输入存在多条匹配的分类 + 短编号，确认弹窗和结果报告文案清晰，且其他可识别编号仍正常录入。

## BUG-20260628-014 刷新后衣柜显示数量大幅减少

### 现象

- 用户已录入几千件衣服。
- 刷新页面后，衣柜显示数量变成一百多件。
- 用户感知为已录入衣服消失。

### 影响

- 直接影响普通玩家衣柜录入和高分计算路径。
- 用户会误判为云端衣柜数据丢失，信任风险高。
- 若在错误状态下继续操作，可能进一步触发基于不完整图鉴的录入、套装补齐或统计误差。

### 初步判断

- `user_wardrobes.owned_clothes` 是云端保存的用户衣柜 ID 数组。
- 页面刷新后需要先加载完整 `clothes` 图鉴，再用衣柜 ID 反查展示；旧实现单次查询可能受 Supabase 默认返回上限影响。
- 更高风险点是衣柜保存使用整包 JSON 数组覆盖：如果云端同步未完成、页面假死、用户一次录入很多衣服，前端可能用不完整的本地数组覆盖原有几千件云端衣柜。
- 录入和套装补齐本质上是“加法操作”，不应使用整包覆盖语义。

### 修复方向

1. 将 `clothes` 全量读取改为分页循环读取，直到最后一页不足 1000 条。
2. `stages` 读取也统一走分页函数，避免后续关卡数据增长出现同类问题。
3. 从云端同步衣柜时，对 `owned_clothes` 做数组校验、字符串化和去重。
4. 录入和套装一键补齐改为“读取云端当前衣柜 + 合并新增 ID + 去重保存”。
5. 普通覆盖保存增加大幅缩水拦截，避免几千件被异常覆盖为少量数据。
6. 本次不修改生产数据库，不做批量数据修复。

### 修复记录

- 2026-06-28：`useWardrobe.loadData()` 改为分页读取完整 `clothes` 与 `stages`。
- 2026-06-28：`syncWardrobeFromCloud()` 读取云端衣柜后对 ID 数组做规范化处理。
- 2026-06-28：`saveWardrobeToCloud()` 增加 `merge` 保存模式；录入和套装补齐使用合并保存，避免覆盖云端已有衣柜。
- 2026-06-28：普通覆盖保存增加大幅缩水拦截，检测到云端几千件将被覆盖为少量数据时阻止保存并提示刷新。
- 2026-06-28：批量录入匹配过程分批让出主线程，降低大量输入时页面假死概率。
- 2026-06-28：本地 `npm.cmd run build` 通过。
- 验证记录：2026-06-30 Preview / production 人工回归通过，衣柜保存与刷新后数量稳定，未复现几千件衣柜刷新后异常缩水。

## BUG-20260625-001 注册流程缺少前端状态校验

### 现象

- dev 项目注册测试时，用户曾收到确认链接并完成激活。
- 之后继续按“验证码注册”理解流程时，前端没有清晰提示该邮箱已经存在或已经确认。
- 用户会误以为“自己不能给自己发邮件”或“验证码没有发送成功”。

### 影响

- 新用户注册体验不稳定，容易卡在错误路径。
- 测试人员难以判断问题来自 Supabase 邮件模板、邮箱投递、账号已确认，还是前端流程。
- 如果生产环境也存在同类状态，可能导致重复注册咨询和用户流失。

### 期望行为

- 注册提交后，如果 Supabase 返回邮箱已注册、已确认、重复注册或验证码无法重发，应展示明确中文提示。
- 对已确认账号，应引导用户直接登录。
- 对未确认账号，应允许重新发送注册验证码。
- 前端文案需要区分“账号已存在”“账号未验证”“验证码已发送”“邮件发送频率限制”。

### 初步判断

- 当前代码使用 `signUp`、`verifyOtp({ type: 'signup' })` 和 `resend({ type: 'signup' })`。
- Auth 配置已经能完成注册，但前端缺少足够细的错误分支和用户状态处理。
- 该问题优先作为前端认证状态机缺陷处理，不需要立即改数据库结构。

### 建议修复方向

1. 梳理 `AuthModal.vue` 中注册、验证、重发、登录、找回密码五个状态。
2. 增加 Supabase Auth 错误码 / 错误信息映射。
3. 对“已注册且已确认”的邮箱，提示用户直接登录。
4. 对“已注册但未确认”的邮箱，保留重发验证码入口。
5. 顺手修复重置密码重发逻辑中引用未定义变量的风险。

### 修复记录

- 2026-06-27：`AuthModal.vue` 增加更细的 Supabase Auth 错误文案映射，区分邮箱未验证、账号密码错误、邮箱已注册、验证码过期和发送频率限制。
- 2026-06-27：注册时如果识别到邮箱已存在，引导用户回到登录流程，并清空密码和验证码状态。
- 2026-06-27：登录时如果返回邮箱未验证，自动切到邮箱验证激活状态，保留重新发送验证码入口。
- 2026-06-27：修复重置密码模式下“重新发送”误用 `cleanOtp` / `cleanPassword` 未定义变量的问题，改为重新发送 recovery 邮件。
- 待验证：分别测试已注册邮箱、未验证邮箱、验证码错误 / 过期、重发验证码和重置密码重发流程。

## BUG-20260625-003 缺失图鉴提交短编号缺少必填校验

### 现象

- 缺失图鉴提交时，短编号可以为空或显示为 `N`。
- 游戏内服装必然存在短编号，因此空短编号不是有效数据。

### 影响

- 缺失项进入待审核后无法和图鉴条目稳定匹配。
- 可能影响“5 次相同提交自动入库”的确定性判断。
- 管理端需要人工补齐短编号，增加审核成本。

### 期望行为

- 短编号为必填。
- 仅允许有效编号格式。
- 未填写时阻止提交，并提示“请填写游戏内短编号”。

### 建议修复方向

1. 在缺失图鉴提交表单增加短编号必填校验。
2. 提交 RPC 前再次校验，避免绕过 UI。
3. 如果后续确认短编号只允许数字，应增加数字格式校验。

### 修复记录

- 2026-06-27：前端提交前增加短编号校验，空值和非数字值均阻止提交。
- 2026-06-27：共享表单短编号输入框改为数字输入提示，不再提示 `N`。
- 2026-06-27：新增数据库 migration，在 `submit_clothing_contribution` RPC 内校验短编号只允许数字，避免绕过前端提交非法值。
- 已验证：Preview 环境中空值、`N`、字母均被拦截，数字短编号允许提交；2026-06-30 人工回归确认按分类 + 短编号录入衣柜通过。

## BUG-20260625-004 刷新或网络波动导致录入内容丢失

### 现象

- 缺失图鉴提交流程中，页面刷新、网络波动或请求失败后，已填写内容容易丢失。

- 请求失败时保留当前填写内容。

1. 增加本地草稿保存，优先使用 `localStorage`。
2. 按用户和表单类型区分草稿 key。
3. 表单字段变化时节流保存。
4. 提交成功后清理草稿。
5. 恢复草稿时给出明确提示，避免用户误用旧数据。

### 修复记录

- 2026-06-27：`ImportZone.vue` 增加录入报告草稿，保存输入框、缺失项列表、统计结果和成功录入列表，刷新后可恢复缺失项入口。
- 2026-06-27：`MissingItemsQueue.vue` 增加按缺失项名称区分的补录表单草稿，保存表单字段和套装搜索文本。
- 2026-06-27：缺失项提交成功后自动清理对应草稿；草稿有效期为 24 小时，避免长期旧数据误导。
- 待验证：填写缺失图鉴补录表单后刷新页面，应恢复录入结果报告和对应缺失项表单内容；提交成功后再次打开不应恢复旧草稿。

## BUG-20260625-005 `profiles.role` 使用 text 存储存在权限风险

### 现象

- 当前 `profiles.role` 为 `text`。
- 角色值使用 `user`、`admin`、`super_admin` 字符串区分。

### 风险

- 容易出现拼写错误、大小写不一致或非法角色值。
- 前端、RPC、RLS 中的字符串判断可能不一致。
- 后续如果加入更多角色，字符串散落会提高维护成本。

### 期望行为

- 数据库存储稳定枚举值，例如：
  - `0`：普通用户
  - `1`：普通管理员
  - `2`：超级管理员
- 前端使用 option / 常量表映射展示文案和权限含义。
- RPC / RLS 使用统一函数判断权限。

### 建议修复方向

1. 设计 `role_level` 或等价数字字段。
2. 迁移现有 `role` 字符串到数字值。
3. 保留兼容期，避免一次性破坏现有前端和 RPC。
4. 更新 `is_super_admin()`、管理员判断函数、前端权限展示。
5. 迁移完成后再考虑删除旧 `role` 字段。

### 修复记录

- 2026-06-27：development 已新增 `profiles.role_level`，并从旧 `profiles.role` 回填。
- 2026-06-27：新增 `profiles_role_level_check` 约束，限制角色等级只能为 `0 / 1 / 2`。

3. 只恢复合法页面值，避免旧缓存或错误值导致空白页面。
4. 如果后续引入路由，可改为使用 URL query / hash 表达当前页面。
