# 缺陷文档

本文档是缺陷记录的常驻入口，用于登记已经复现或高度可信的产品缺陷、技术缺陷和待验证异常。它不替代需求文档；需求文档记录“应该怎么做”，缺陷文档记录“当前哪里没有按预期工作”。

## 使用与轮转规则

- 默认读取路径固定为“常驻索引 → 一个详情位置 → 一个目标章节”，不得自动读取全部归档。
- 常驻正文保留全部待修复、待观察或重新打开的缺陷，以及最多 10 条详细记录。
- 达到 10 条边界时移动最旧的完整已结束上下文组；重新打开的缺陷必须将完整详情移回常驻文档。
- 同一 BUG 只能保留一份详细正文；索引始终保留全部历史编号和唯一详情位置。

## BUG-20260721-018 纯散件提交在审核时丢失显式套装状态

### 现象与复现

- 两个普通测试用户在 development 提交 `DB4验收-0721-A` 时均明确选择“无关联套装（纯散件）”。
- 对应 pending `53`、`54` 的 `suit_id` 与 `temp_suit_name` 均为 `null`，数据库事实符合纯散件存储口径；两条记录均已成功审核入库。
- 管理员打开审核表单时，套装状态却显示为空，没有还原“无关联套装（纯散件）”，审核员需要再次选择后才能继续。

### 影响

- 审核员无法从表单状态区分“用户明确选择纯散件”和“用户尚未选择套装状态”。
- 重复选择增加误关联已有套装或误填临时套装名的风险，也会让审核流程产生不必要的阻塞。
- 数据库中的纯散件事实没有丢失，本缺陷不影响 DB-4 管理员仲裁、积分和衣柜写回的人工验收结论。

### 根因判断（高可信）

- 提交表单用前端状态 `suit_status = 'none'` 表示用户明确选择纯散件，同时清空 `suit_id` 和临时套装名。
- 提交载荷只持久化 `suit_id` 与 `temp_suit_name`；纯散件因此按设计保存为 `null / null`，不会持久化仅供界面使用的 `suit_status`。
- 审核页重建表单时仅在存在 `suit_id` 时还原 `existing`，对 `null / null` 还原为空状态，而不是 `none`；同一审核链路的候选摘要已经能将该组合显示为“无关联套装”，说明问题集中在审核表单状态还原。

### 期望行为

- 对经过提交校验的 `suit_id = null`、`temp_suit_name = null` 记录，审核表单应还原为明确的“无关联套装（纯散件）”状态。
- 审核员不需要再次选择即可继续审核；已有套装和临时套装两条路径的行为保持不变。
- 数据库存储继续使用 `null / null` 表示纯散件，不为界面状态新增数据库字段或改写历史数据。

### 修复与验证边界

1. 预计只需修复前端审核状态还原，不需要 migration 或数据库写入；若调查出现相反证据，必须重新确认任务类型和范围。
2. 回归覆盖纯散件、已有套装、临时套装三条提交路径，确认候选摘要、审核表单和最终入库语义一致。
3. 完整复测“普通用户提交 → 管理员审核 → 正式入库”，确保 DB-4 仲裁、积分与衣柜写回不回退。
4. 本次仅登记缺陷，不包含业务代码修复。

## BUG-20260721-017 正式库补全误判属性数据不一致

### 现象与影响

- 负责人在 PR #87 Preview 中使用 pending `23` 补全正式服装 `db3_acceptance_20260721_01`，连续三次返回“补全正式库失败”。
- Supabase API 日志记录三次 RPC `400`；Postgres 原始错误均为“存在与本次正式库补全最终数据不一致的待审核记录，已拒绝自动通过”。
- 每次失败后 pending、正式服装、贡献、积分和衣柜均保持原值，事务回滚有效，但第一条积分写路径无法完成真实业务验收。

### 根因

- 缺失图鉴提交使用 `calculateItemScores()` 保存固定 10 个属性键，未选中的反向属性明确保存为 `0`。
- 图鉴审核页另行重建分值，只发送 5 个选中属性键；数值语义相同，但 JSON 结构不同。
- DB-3 为防止错误 pending 被自动通过，使用 `pending.scores is not distinct from p_scores` 严格核对；自动事务 fixture 使用了相同的精简 JSON，未覆盖真实前端表示差异。

### 修复与验证

- 提交端与审核端改为共用同一标准分值构造函数，统一生成 10 属性 JSON；数据库严格校验保持不变。
- 前端补充真实“连衣裙 + 五项完美”的回归样本，必须生成与 pending `23` 相同的 10 属性结构。
- 补全错误映射增加服务端实际不一致文案，后续异常不再退化成无技术原因的通用提示。
- 2026-07-21：本地测试 8 项与生产构建通过；同一真实 pending / 正式服装 / 管理员身份的 development 事务 rehearsal 成功生成贡献、`+5` 积分、衣柜写回和 pending 通过，随后整体 rollback，未消耗人工验收数据。
- 2026-07-21：负责人已明确确认修复版 Preview 页面操作成功；development 回读确认 pending 已批准、正式服装已补全，并形成 1 条贡献、1 条 `+5` 积分流水和衣柜写回，五项事实一致，状态收口为“已关闭”。

## BUG-20260711-015 短编号无法唯一匹配时提示难以理解

### 现象

- 用户按分类和短编号录入衣柜时，部分编号在图鉴中对应多件服装。
- 浏览器弹窗提示“存在多个归一化短编号相同的图鉴条目，本次已跳过这些编号”。
- 用户看不懂“归一化短编号”和“图鉴条目”，也不知道应该如何继续录入。

### 影响

- 安全跳过逻辑本身有效，但错误文案会让用户误以为输入格式错误或系统故障。
- 用户不知道其他可识别编号仍会继续录入，也不知道可以改用名称录入。
- 影响“快速录入衣柜”核心流程的可理解性。

### 期望行为

- 使用普通玩家能理解的语言说明：图鉴中有多件服装使用相同编号，系统无法确定具体服装。
- 明确告知这些服装没有加入衣柜，其他可识别编号不受影响。
- 给出可执行的下一步：改用“按名称录入”。

### 修复记录

- 2026-07-11：优化短编号冲突弹窗，移除“归一化短编号、图鉴条目”等内部术语。
- 2026-07-11：同步优化录入结果报告，统一说明未录入原因、其他编号不受影响和按名称录入的处理方式。
- 2026-07-12：本地 production build 通过；development 页面加载正常，无错误覆盖层或控制台错误。
- 2026-07-12：development 当前无真实重复编号样本，使用仅限临时浏览器会话的响应拦截构造重复编号；混合输入冲突编号与有效编号后，冲突项被安全跳过，有效项正常录入。
- 2026-07-12：弹窗和结果报告均使用玩家可理解的说明，明确冲突项未加入衣柜、其他编号不受影响，并引导改用“按名称录入”；状态收口为“已关闭”。

## BUG-20260628-014 刷新后衣柜显示数量大幅减少

### 现象

- 用户已录入几千件衣服。
- 刷新页面后，衣柜显示数量变成一百多件。
- 用户感知为已录入衣服消失。

### 影响

- 直接影响普通玩家衣柜录入和高分计算路径。
- 用户会误判为云端衣柜数据丢失，信任风险高。
- 若在错误状态下继续操作，可能进一步触发基于不完整图鉴的录入、套装补齐或统计误差。

### 初步判断

- `user_wardrobes.owned_clothes` 是云端保存的用户衣柜 ID 数组。
- 页面刷新后需要先加载完整 `clothes` 图鉴，再用衣柜 ID 反查展示；旧实现单次查询可能受 Supabase 默认返回上限影响。
- 更高风险点是衣柜保存使用整包 JSON 数组覆盖：如果云端同步未完成、页面假死、用户一次录入很多衣服，前端可能用不完整的本地数组覆盖原有几千件云端衣柜。
- 录入和套装补齐本质上是“加法操作”，不应使用整包覆盖语义。

### 修复方向

1. 将 `clothes` 全量读取改为分页循环读取，直到最后一页不足 1000 条。
2. `stages` 读取也统一走分页函数，避免后续关卡数据增长出现同类问题。
3. 从云端同步衣柜时，对 `owned_clothes` 做数组校验、字符串化和去重。
4. 录入和套装一键补齐改为“读取云端当前衣柜 + 合并新增 ID + 去重保存”。
5. 普通覆盖保存增加大幅缩水拦截，避免几千件被异常覆盖为少量数据。
6. 本次不修改生产数据库，不做批量数据修复。

### 修复记录

- 2026-06-28：`useWardrobe.loadData()` 改为分页读取完整 `clothes` 与 `stages`。
- 2026-06-28：`syncWardrobeFromCloud()` 读取云端衣柜后对 ID 数组做规范化处理。

## BUG-20260627-012 重置密码成功后提示网络超时

### 现象

- 用户在重置密码流程中输入验证码和新密码后提交。
- 密码实际已经更新成功，可以使用新密码登录。
- 但前端仍展示“网络请求超时，请检查网络”。

### 影响

- 用户可能误以为密码没有更新成功，重复提交或重新获取验证码。
- 不影响最终密码更新结果，当前判断为体验类低优先级缺陷。

### 初步判断

- `supabase.auth.updateUser({ password })` 可能已经成功写入，但 SDK 回调、会话刷新或后续流程未在超时时间内完成。
- 当前超时保护会把整体认证流程判定为失败，未区分“操作已经成功但前端响应慢”的情况。
- 与前期观察到的 Supabase Auth 前端 SDK 偶发“操作成功但响应慢 / 挂起”现象一致。

### 修改权重

- 权重：低。
- 暂不阻塞核心功能验证。
- 若后续出现“实际未更新但提示成功”或“大量用户重复触发”，再提升优先级。

### 建议处理方向

1. 将重置密码成功路径拆分为“验证验证码”和“更新密码”两个独立状态提示。
2. 对 `updateUser` 超时增加柔性提示，例如“密码可能已更新成功，请尝试用新密码登录”。
3. 超时后提供“返回登录”入口，避免用户停留在重复提交状态。
4. 如需精确确认，需要设计安全的二次验证流程，避免直接暴露账号状态。
