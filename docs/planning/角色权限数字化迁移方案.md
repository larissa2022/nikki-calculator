# 角色权限数字化迁移方案

## 0. 关联缺陷

| 项目 | 内容 |
| --- | --- |
| 缺陷编号 | `BUG-20260625-005` |
| 当前问题 | `profiles.role` 为 text，使用 `user`、`admin`、`super_admin` 区分角色 |
| 目标 | 使用数字角色等级作为数据库权威值，前端负责展示映射 |
| 风险等级 | 高 |
| 当前状态 | development 已应用，待权限冒烟测试；production 未执行 |

## 1. 为什么需要迁移

当前 `profiles.role` 使用字符串保存角色：

| 字符串 | 含义 |
| --- | --- |
| `user` | 普通用户 |
| `admin` | 普通管理员 |
| `super_admin` | 超级管理员 |

该设计的问题：

1. 容易出现非法值，例如拼写错误、大小写不一致、空字符串。
2. 前端、RPC、RLS 都需要写字符串判断，后续容易判断不一致。
3. 用户管理面板直接传字符串更新权限，缺少数据库层强约束。
4. 后续如果引入高信用玩家、临时管理员、任期管理员，字符串权限会继续膨胀。

迁移后的目标：

| 数字值 | 角色常量 | 含义 |
| --- | --- | --- |
| `0` | `USER` | 普通用户 |
| `1` | `ADMIN` | 普通管理员 |
| `2` | `SUPER_ADMIN` | 超级管理员 |

数字值只表达系统权限层级；页面展示仍使用中文文案，例如“玩家”“系统管理”“最高站长”。

## 2. 迁移原则

1. 不直接删除旧 `role` 字段，先进入兼容期。
2. 新增 `role_level` 字段，并从旧 `role` 回填。
3. 所有数据库函数先兼容 `role_level` 和旧 `role`。
4. 前端先接入统一映射工具，避免散落魔法字符串。
5. dev 环境验证通过后，再考虑生产执行。
6. 生产执行前必须备份 `profiles` 表。
7. 超级管理员账号必须在迁移前后均保持 `role_level = 2`。

## 3. 当前影响范围

### 3.1 数据库对象

| 对象 | 当前依赖 |
| --- | --- |
| `profiles.role` | 用户角色字段 |
| `handle_new_user()` | 新用户初始化写入 `role = 'user'` |
| `is_super_admin()` | 判断 `role = 'super_admin'` |
| `is_admin_or_super_admin()` | 判断 `role in ('admin', 'super_admin')` |
| profiles update policy | 使用 `is_super_admin()` 控制超管修改档案 |

### 3.2 前端对象

| 文件 | 当前依赖 |
| --- | --- |
| `src/composables/useAuth.js` | `role === 'admin' || role === 'super_admin'` |
| `src/api/adminService.js` | 读取和更新 `profiles.role` |
| `src/components/UserManageBoard.vue` | 按 `user`、`admin`、`super_admin` 分组和展示 |
| `src/views/AdminView.vue` | `currentUserRole === 'super_admin'` 控制用户权限大盘入口 |

## 4. 推荐迁移路径

### 阶段一：兼容字段

新增 `profiles.role_level`：

```sql
alter table public.profiles
  add column if not exists role_level smallint not null default 0;

alter table public.profiles
  add constraint profiles_role_level_check
  check (role_level in (0, 1, 2));
```

回填已有数据：

```sql
update public.profiles
set role_level = case role
  when 'super_admin' then 2
  when 'admin' then 1
  else 0
end
where role_level is distinct from case role
  when 'super_admin' then 2
  when 'admin' then 1
  else 0
end;
```

### 阶段二：数据库函数改为优先读数字字段

`is_super_admin()` 建议改为：

```sql
select exists(
  select 1
  from public.profiles
  where id = auth.uid()
    and (
      role_level = 2
      or role = 'super_admin'
    )
);
```

`is_admin_or_super_admin()` 建议改为：

```sql
select exists(
  select 1
  from public.profiles
  where id = auth.uid()
    and (
      role_level in (1, 2)
      or role in ('admin', 'super_admin')
    )
);
```

兼容期内保留旧字段判断，防止前端或旧数据尚未完全切换时管理功能失效。

### 阶段三：前端统一映射

新增角色工具，例如 `src/utils/roles.js`：

```js
export const ROLE_LEVEL = {
  USER: 0,
  ADMIN: 1,
  SUPER_ADMIN: 2
}

export const roleLevelToKey = (level) => {
  if (Number(level) === ROLE_LEVEL.SUPER_ADMIN) return 'super_admin'
  if (Number(level) === ROLE_LEVEL.ADMIN) return 'admin'
  return 'user'
}

export const isAdminLevel = (level) => Number(level) >= ROLE_LEVEL.ADMIN
export const isSuperAdminLevel = (level) => Number(level) === ROLE_LEVEL.SUPER_ADMIN
```

前端展示只依赖工具函数，不再到处手写字符串。

### 阶段四：用户管理写入数字字段

管理员改权限时，前端向数据库更新 `role_level`：

| 操作 | 写入值 |
| --- | --- |
| 降级为玩家 | `0` |
| 提拔为管理员 | `1` |
| 超级管理员 | 不通过普通面板修改 |

兼容期可同时写旧字段：

```js
{
  role_level: 1,
  role: 'admin'
}
```

这样即使有旧逻辑未迁移，也不会立刻断权限。

### 阶段五：观察期后移除旧字段依赖

至少完成以下条件后，才考虑删除或废弃 `role`：

1. dev 验证通过。
2. 生产上线后观察一段时间无权限异常。
3. 所有前端、RPC、RLS 均不再依赖 `profiles.role`。
4. 数据库导出的 schema 中不再出现旧字段判断。
5. 已有管理账号和普通账号权限均复查通过。

删除旧字段不是当前阶段目标。当前阶段只做安全兼容迁移。

## 5. 预检 SQL

执行迁移前先检查：

```sql
select role, count(*)
from public.profiles
group by role
order by role;

select id, email, role
from public.profiles
where role not in ('user', 'admin', 'super_admin')
   or role is null;
```

如果发现非法值，需要先确认如何映射，默认建议非法值统一降级为 `0`。

检查超级管理员：

```sql
select id, email, role, role_level
from public.profiles
where role = 'super_admin' or role_level = 2;
```

## 6. 验收清单

dev 环境必须验证：

1. 普通用户登录后不能进入图鉴管理。
2. `role_level = 1` 用户可以进入图鉴管理。
3. `role_level = 2` 用户可以进入权限大盘。
4. 超级管理员可以把普通用户提升为管理员。
5. 超级管理员可以把管理员降级为普通用户。
6. 普通管理员不能看到权限大盘。
7. 自动入库、管理员仲裁入库仍能通过 `is_admin_or_super_admin()`。
8. 新注册用户默认 `role_level = 0`。

## 7. 回滚方案

如果 dev 迁移后出现权限异常：

1. 前端回滚到读取 `profiles.role`。
2. 数据库函数回滚到旧版字符串判断。
3. 保留 `role_level` 字段不删除，避免进一步破坏数据。
4. 若需要同步旧字段，可执行：

```sql
update public.profiles
set role = case role_level
  when 2 then 'super_admin'
  when 1 then 'admin'
  else 'user'
end;
```

生产环境如需回滚，必须先记录受影响用户数和超级管理员账号状态。

## 8. 暂停确认点

以下操作必须由用户确认后才能执行：

1. 在 dev 库创建 `role_level` 字段。
2. 在 dev 库替换 `is_super_admin()` 和 `is_admin_or_super_admin()`。
3. 前端用户管理从字符串权限切换为数字权限。
4. 向生产库推送任何 role 相关 migration。
5. 删除或废弃旧 `profiles.role` 字段。

## 9. 当前建议

建议下一步只在 dev 环境执行“兼容字段迁移”：

1. 新增 `role_level`。
2. 回填现有 `role`。
3. 添加 check 约束。
4. 更新数据库函数为双轨兼容。
5. 生成类型并构建。

不建议当前阶段删除 `profiles.role`。
