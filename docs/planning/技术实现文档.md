# 技术实现文档

## 0. 文档目标

本文档基于 [`需求文档.md`](../requirements/需求文档.md) 与 [`开发文档.md`](开发文档.md)，描述后续开发的技术落地方案。它用于指导 Supabase 数据层、RPC、前端模块、权限控制、测试和上线流程。

约束：

1. 不在本文档中擅自改变需求规则。
2. 标记为“待确认”的内容，在开发前必须向产品确认。
3. 优先保证数据可审计、流程可回滚、前端不绕过数据库约束。
4. 线上数据库结构调整统一通过 Supabase migration。

## 0.1 当前实现状态

本节用于标注截至 2026-06-30 的近期实际技术实现状态；下方数据表、RPC、前端模块等章节仍保留为后续技术方案，不代表已全部实现。

### 已实现

- `complete_existing_clothes_from_pending`：已支持正式库已有但资料不全的补全路径，用于从 pending 数据补齐正式库缺失字段，避免唯一约束重复插入失败。
- 按分类 + 短编号录入衣柜：已支持用户选择分类并输入短编号批量录入衣柜；人工回归通过。
- 衣柜云端合并保存保护：已增加合并保存模式和大幅缩水拦截，避免用不完整本地数组覆盖云端已有衣柜。
- `clothes` / `stages` 分页加载：已改为分页读取完整数据，避免 Supabase 单次查询上限导致图鉴或关卡数据不完整。
- 提交者衣柜写回：缺失图鉴入库或补全后，相关有效提交者衣柜可自动获得入库部件。
- 生产构建禁用 Vue DevTools：production 构建不再加载 Vue DevTools，production 人工回归通过。

### 未实现 / 暂缓

## 1. 当前技术基线

### 1.1 技术栈

- 前端：Vue 3 + Vite。
- 数据库：Supabase Postgres。
- 数据访问：`src/api/supabase.js` 中的 Supabase client。
- 管理端主入口：`src/views/AdminView.vue`。
- 图鉴审核逻辑：`src/composables/useAudit.js`、`src/api/adminService.js`。
- 录入复用表单：`src/components/ClothesEntryForm.vue`。
- 缺失项补录：`src/components/MissingItemsQueue.vue`。

### 1.2 当前核心数据表

| 表名 | 当前状态 |
| --- | --- |
| `clothes` | 正式服装库，当前无 `needs_suit_review` |
| `suits` | 正式套装库，当前需要补唯一性保护 |
| `pending_clothes` | 待审核服装提交，已有 `status`、`submitted_by`、`suit_id` |
| `pending_suits` | 待审核套装提交，已有 `status`、`submitted_by` |
| `profiles` | 用户资料与角色，已有 `role`；不保存权威积分总分 |

## 2. 总体架构

推荐把后续功能分为四层：

| 层级 | 职责 | 主要文件 / 对象 |
| --- | --- | --- |
| 数据层 | 表结构、约束、RLS、索引 | Supabase migrations |
| 业务过程层 | 自动入库、投票、积分、重审流转 | Postgres RPC |
| API 封装层 | 前端调用数据库 / RPC | `src/api/*.js` |
| UI 状态层 | 页面展示、表单复用、交互反馈 | `src/views/*`、`src/components/*`、`src/composables/*` |

核心原则：

- 涉及积分、投票、入库、重审状态变更的操作优先放在 RPC 中。
- 前端只提交用户意图，不在浏览器里决定最终入库和积分。
- 所有关键行为保留来源记录，避免后续无法追溯。

## 3. 数据库实现方案

### 3.1 `clothes` 调整

用途：承接“缺套装但编号完整，可进入正式库，并标记待补套装”的查询需求。

可选字段：

```sql
alter table public.clothes
add column if not exists needs_suit_review boolean not null default false;
```

已确认：

- 缺套装待补状态的权威流程使用 `re_review_items` 追踪。
- `clothes.needs_suit_review` 仅作为可选查询加速 / 冗余标记，不作为权威状态来源。

### 3.2 `clothing_contributions`

用途：记录正式入库后的贡献者、来源提交、贡献类型和积分奖励。

建议结构：

```sql
create table public.clothing_contributions (
  id uuid primary key default gen_random_uuid(),
  clothes_id varchar not null references public.clothes(id) on delete cascade,
  user_id uuid references auth.users(id) on delete set null,
  source_pending_id bigint references public.pending_clothes(id) on delete set null,
  contribution_type text not null,
  awarded_points integer not null default 0,
  points_status text not null default 'pending',
  created_at timestamptz not null default now(),
  unique (clothes_id, user_id, contribution_type)
);
```

建议枚举值：

| 字段 | 值 |
| --- | --- |
| `contribution_type` | `auto_entry`、`admin_arbitration`、`re_review_fix`、`correction` |
| `points_status` | `pending`、`awarded`、`revoked`、`rejected` |

### 3.3 `points_ledger`

用途：积分唯一权威流水。总分、月榜、扣回都应从流水计算。

建议结构：

```sql
create table public.points_ledger (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  points integer not null,
  reason text not null,
  status text not null default 'awarded',
  source_type text not null,
  source_id text,
  occurred_at timestamptz not null default now(),
  effective_month text not null,
  created_at timestamptz not null default now()
);
```

建议规则：

- `points` 正数表示发放，负数表示扣回。
- `status = pending` 的流水不计入正式榜单。
- `effective_month` 使用 UTC+8 月份字符串，例如 `2026-06`。
- `profiles` 不保存权威积分总分。
- 用户总分、等级和排行榜通过 view / RPC 从 `points_ledger` 汇总。
- 后期可新增积分缓存表，但缓存只用于展示加速，必须能从 `points_ledger` 重建。

### 3.4 `jury_votes`

用途：陪审团投票，支持权重、去重、防自审。

建议结构：

```sql
create table public.jury_votes (
  id uuid primary key default gen_random_uuid(),
  target_type text not null,
  target_id text not null,
  user_id uuid not null references auth.users(id) on delete cascade,
  vote text not null,
  weight integer not null default 1,
  created_at timestamptz not null default now(),
  unique (target_type, target_id, user_id)
);
```

建议枚举值：

| 字段 | 值 |
| --- | --- |
| `target_type` | `pending_clothes`、`pending_suits`、`re_review_item`、`correction_request` |
| `vote` | `approve`、`reject` |

已确认：

- 投票阈值使用“达到阈值”触发，不要求恰好等于阈值。

### 3.5 `re_review_items`

用途：保存缺编号、字段冲突、被驳回或报错后需要修正的数据。

建议结构：

```sql
create table public.re_review_items (
  id uuid primary key default gen_random_uuid(),
  source_type text not null,
  source_id text,
  clothes_id varchar references public.clothes(id) on delete set null,
  payload jsonb not null default '{}'::jsonb,
  reason text not null,
  status text not null default 'open',
  submitted_by uuid references auth.users(id) on delete set null,
  resolved_by uuid references auth.users(id) on delete set null,
  resolved_as text,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  resolved_at timestamptz
);
```

建议枚举值：

| 字段 | 值 |
| --- | --- |
| `reason` | `missing_game_id`、`field_conflict`、`jury_rejected`、`correction`、`missing_suit` |
| `status` | `open`、`pending_review`、`admin_review`、`resolved`、`abandoned` |
| `resolved_as` | `to_pending`、`updated_clothes`、`rejected`、`abandoned` |

已确认：

- 重审净胜达到 5 且字段完整后，进入正式库。

### 3.6 `correction_requests`

用途：正式库数据报错与修正流程。

建议结构：

```sql
create table public.correction_requests (
  id uuid primary key default gen_random_uuid(),
  clothes_id varchar not null references public.clothes(id) on delete cascade,
  reported_by uuid references auth.users(id) on delete set null,
  reason text not null,
  proposed_patch jsonb not null default '{}'::jsonb,
  status text not null default 'pending',
  reviewed_by uuid references auth.users(id) on delete set null,
  reviewed_at timestamptz,
  created_at timestamptz not null default now()
);
```

建议状态：

- `pending`
- `jury_review`
- `admin_review`
- `approved`
- `rejected`
- `converted_to_re_review`

### 3.7 `admin_terms`

用途：记录普通管理员月度任期。

建议结构：

```sql
create table public.admin_terms (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  term_month text not null,
  source text not null,
  status text not null default 'active',
  granted_by uuid references auth.users(id) on delete set null,
  started_at timestamptz not null default now(),
  ended_at timestamptz,
  unique (user_id, term_month)
);
```

已确认：

- 管理员轮换第一版自动执行，并写入 `admin_terms`。

### 3.8 可选视图

推荐新增视图，减少前端重复计算：

```sql
create view public.user_points_summary as
select
  user_id,
  coalesce(sum(points) filter (where status = 'awarded'), 0) as total_points
from public.points_ledger
group by user_id;
```

后续可扩展：

- `monthly_points_summary`
- `leaderboard_current_month`
- `leaderboard_last_month`
- `user_privilege_summary`
- `user_points_cache`，可选缓存表，仅作展示加速，不作为权威来源

## 4. RPC 实现方案

### 4.1 `submit_clothing_contribution`

现状：已有 RPC 负责提交缺失项，并在 5 次一致时自动入库。

改造目标：

1. 防止重复提交污染 5 次一致判断。
2. 自动入库时写入 `clothing_contributions`。
3. 自动入库时写入 `points_ledger`。
4. 缺套装但编号完整时进入正式库，并写入 `re_review_items` 追踪套装待补状态。
5. 字段冲突时转入 `re_review_items` 或管理员仲裁。

建议返回结构：

```json
{
  "status": "pending | approved | re_review | rejected",
  "clothes_id": "string | null",
  "re_review_item_id": "uuid | null",
  "pending_count": 1,
  "message": "string",
  "needs_suit_review": false
}
```

待确认：

- 积分是自动 `awarded`，还是先写 `pending`。
- `game_id = N` 或缺编号是否完全不计分。

### 4.2 `cast_jury_vote`

用途：处理陪审团投票。

建议参数：

```sql
cast_jury_vote(
  p_target_type text,
  p_target_id text,
  p_vote text
)
```

RPC 内部职责：

1. 获取当前用户。
2. 判断是否自审。
3. 根据积分等级计算投票权重。
4. 插入 `jury_votes`。
5. 计算净胜票。
6. 触发状态流转。

待确认：

- 管理员终审是否也写入 `jury_votes`，还是写独立 `admin_decisions`。

### 4.3 `resolve_re_review_item`

用途：提交重审修正版或管理员处理重审结果。

建议参数：

```sql
resolve_re_review_item(
  p_re_review_id uuid,
  p_action text,
  p_payload jsonb
)
```

建议动作：

| `p_action` | 含义 |
| --- | --- |
| `submit_fix` | 普通用户提交候选修正版 |
| `to_pending` | 进入 pending 重新审核 |
| `approve_update` | 管理员批准并更新正式库 |
| `reject` | 驳回重审 |
| `abandon` | 关闭长期无效项 |

### 4.4 `submit_correction_request`

用途：用户提交正式库报错。

建议参数：

```sql
submit_correction_request(
  p_clothes_id varchar,
  p_reason text,
  p_proposed_patch jsonb
)
```

RPC 内部职责：

1. 校验用户登录。
2. 校验 `clothes_id` 存在。
3. 插入 `correction_requests`。
4. 对高风险字段变更转 `admin_review` 或 `re_review_items`。

### 4.5 `award_points_for_contribution`

用途：统一处理积分发放，避免多个 RPC 重复实现。

建议行为：

- 检查是否已经对同一来源发放过积分。
- 插入 `points_ledger`。
- 更新 `clothing_contributions.points_status`。

技术建议：

- 作为内部 security definer 函数使用，不直接暴露给前端。

## 5. 状态流转实现

### 5.1 通用状态

```text
pending
  -> approved
  -> re_review
  -> rejected

re_review
  -> pending
  -> admin_review
  -> abandoned

admin_review
  -> approved
  -> re_review
  -> rejected
```

### 5.2 状态字段建议

| 对象 | 状态字段 | 建议状态 |
| --- | --- | --- |
| `pending_clothes` | `status` | `pending`、`approved`、`re_review`、`rejected` |
| `pending_suits` | `status` | `pending`、`approved`、`rejected`、`conflict` |
| `re_review_items` | `status` | `open`、`pending_review`、`admin_review`、`resolved`、`abandoned` |
| `correction_requests` | `status` | `pending`、`jury_review`、`admin_review`、`approved`、`rejected` |

### 5.3 入库保护

以下情况不允许直接进入 `clothes`：

- 缺编号。
- 核心字段缺失。
- 候选字段冲突。
- 投票未达阈值。
- 当前用户是提交者本人且正在执行审核动作。

## 6. 权限与 RLS 方案

### 6.1 角色

| 角色 | 来源 | 权限 |
| --- | --- | --- |
| 匿名用户 | 未登录 | 只读公开数据 |
| 普通用户 | `auth.users` | 提交、投票、报错、查看公开审核项 |
| 普通管理员 | `profiles.role = admin` 或 `admin_terms` | 处理低风险项 |
| 超级管理员 | `profiles.role = super_admin` | 终审、授权、处理高风险项 |

### 6.2 RLS 原则

- `points_ledger`：普通用户只能读自己的流水；管理员可读汇总；写入只允许 RPC。
- `clothing_contributions`：公开读取贡献者展示；写入只允许 RPC。
- `jury_votes`：用户可写自己的投票；不可改他人投票；结果汇总可公开。
- `re_review_items`：开放可参与项；隐藏涉及自己提交且不可自审的审核入口。
- `correction_requests`：用户可创建和查看自己的报错；管理员可处理。

### 6.3 防自审策略

防自审必须在数据库层实现，前端隐藏只是体验优化。

建议判断来源：

- `pending_clothes.submitted_by`
- `pending_suits.submitted_by`
- `clothing_contributions.user_id`
- `correction_requests.reported_by`
- `re_review_items.submitted_by`

## 8. 积分与等级实现

### 8.1 积分计算

推荐规则：

- 只从 `points_ledger` 计算权威总分。
- `status = awarded` 计入正式总分。
- `status = pending` 不计入榜单。
- 扣回通过负数流水实现。
- `profiles` 不保存权威总分。
- view / RPC 用于实时汇总；缓存表只能用于展示加速。

### 8.2 等级计算

可继续复用 `src/composables/useUserPrivilege.js` 的等级规则：

| 等级 | 门槛 | 投票权重 |
| --- | --- | --- |
| Lv1 | 500 | 1 |
| Lv2 | 2000 | 2 |
| Lv3 | 5000 | 3 |
| Lv4 | 10000 或当月榜首 | 3 |

待确认：

- Lv4 `可信权重 +3` 是否只影响投票，不影响自动入库。

### 8.3 排行榜

建议实现方式：

1. 第一版用 SQL view / RPC 实时计算。
2. 数据增长后再做月榜快照表。
3. 每月 1 日 UTC+8 冻结上月榜。

待确认：

- 月榜冻结由数据库定时任务、手动触发，还是前端读取时计算。
- 上月前 10 权益是广告免除权、首页鸣谢，还是两者都有。

## 9. Migration 开发顺序

建议按以下顺序创建 migration：

1. `add_review_support_fields`
   - 可选：`clothes.needs_suit_review`
   - `suits` 唯一性保护或标准名字段
2. `create_contributions_and_points`
   - `clothing_contributions`
   - `points_ledger`
   - 积分汇总 view
3. `create_jury_votes`
   - `jury_votes`
   - 投票唯一约束
4. `create_re_review_and_corrections`
   - `re_review_items`
   - `correction_requests`
5. `create_admin_terms`
   - `admin_terms`
6. `create_review_rpcs`
   - `cast_jury_vote`
   - `resolve_re_review_item`
   - `submit_correction_request`
   - 更新 `submit_clothing_contribution`

每个 migration 后需要执行：


## 11. 上线与回滚策略

### 11.1 上线顺序

1. 先上只新增表 / 字段 / 约束的 migration。
2. 再上 RPC，但前端不立即展示入口。
3. 小范围接入提交与积分流水。
4. 接入陪审团和重审入口。
5. 最后接入排行榜和权益展示。

### 11.2 回滚思路

- 新增表字段一般不立刻删除，先停用入口。
- RPC 可保留旧版本兼容，新增版本使用新函数名或参数默认值。
- 前端入口可通过条件渲染关闭。
- 积分错误用 `points_ledger` 追加反向流水，不直接删除旧流水。
