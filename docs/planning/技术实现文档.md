## 0.1 当前实现状态

本节用于标注截至 2026-07-26 的近期实际技术实现状态；下方数据表、RPC、前端模块等章节仍保留为后续技术方案，不代表已全部实现。

### 已实现

- `complete_existing_clothes_from_pending`：已支持正式库已有但资料不全的补全路径，用于从 pending 数据补齐正式库缺失字段，避免唯一约束重复插入失败。
- 按分类 + 短编号录入衣柜：已支持用户选择分类并输入短编号批量录入衣柜；人工回归通过。
- 衣柜云端合并保存保护：已增加合并保存模式和大幅缩水拦截，避免用不完整本地数组覆盖云端已有衣柜。
- `clothes` / `stages` 分页加载：已改为分页读取完整数据，避免 Supabase 单次查询上限导致图鉴或关卡数据不完整。
- 提交者衣柜写回：缺失图鉴入库或补全后，相关有效提交者衣柜可自动获得入库部件。
- 生产构建禁用 Vue DevTools：production 构建不再加载 Vue DevTools，production 人工回归通过。
- `clothing_contributions` / `points_ledger`：DB-1 基础事实、DB-2 最小只读面、DB-3 正式库补全、DB-4 管理员仲裁和 DB-5 自动入库已在 development 实现并完成对应 development 验证。
- `re_review_items` 与陪审团闭环：DB-7 已在 development 统一接入待补套装、字段缺失、字段冲突和正式资料修正，并验证全字段补充、防自审、投票状态流转、积分和事务回滚。

### 未实现 / 暂缓

- `correction_requests` 报错受理：DB-8 用户提交、本人查询和前端入口已在 development 实现；管理员处理、转重审和积分仍后置。最小权限前向 patch 待精确授权。
- 排行榜相关 RPC / view：未实现 / 暂缓。

### 本阶段已确认技术点

- 自动入库必须让当前提交先形成 pending，再将有效来源 pending 统一标记为 `approved`；不得删除来源记录。
- 同一次初始入库中，自动入库与管理员仲裁互斥且每个用户只奖励一次；后续独立有效行为可按来源再次奖励，每个来源事件必须幂等。
- 用户账号删除后，贡献和积分流水不级联删除；用户关联置空，展示统一匿名化为“已注销用户”。
- 重审池采用“社区参与、系统处理、管理员兜底”；未参与原始提交的登录用户可提交候选修正版，原提交者和来源参与者由数据库层排除，候选不能直接覆盖正式库。

### 已确认技术口径

- 积分状态：第一版默认 `awarded`。图鉴审核通过后，积分立即生效。
- 积分分值：自动入库 / 管理员仲裁 +10，正式库空字段补全 +5，重审修正 +8，报错通过 +5。
- 积分扣回：只追加负数流水，不修改或删除历史记录。
- 前 5 有效提交者：与最终入库数据一致的提交者，按提交时间排序，取前 5 个获得积分。
- 前 3 展示贡献者：从前 5 有效提交者中，按提交时间排序，取前 3 个用于页面展示。
- 缺编号数据：不通过提交 / 入库校验，不进入积分判断分支。
- 缺套装但编号完整：允许正式入库，同时创建 `re_review_items`，状态为待补套装。

## 0.2 最小技术落地计划

本节只作为下一阶段开发前的技术拆包，不代表已实现。所有数据库结构、RPC 和 RLS 变更必须先在 development 验证，并按数据库安全方案记录变更。

### `points_ledger` 积分流水

- 第一版目标：新增积分流水表，让积分发放、扣回和来源都可追溯、可重算。
- 不做什么：不做排行榜 RPC / view，不做积分缓存表，不改 `profiles` 为权威积分来源。
- 依赖对象：`profiles`、`pending_clothes`、`clothes`、`clothing_contributions`、`submit_clothing_contribution`、`approve_pending_clothes_arbitration`、`complete_existing_clothes_from_pending`。
- 第一版口径：图鉴审核通过后积分默认 `awarded` 并立即生效。
- 第一版分值：自动入库 / 管理员仲裁 +10，正式库空字段补全 +5；扣回追加负数流水。
- 开发风险：流水状态和贡献状态不一致；历史 `profiles.total_points` 被误读为权威；自动发放后缺少扣回路径。
- 建议顺序：先建基础表和约束，再单独建最小只读面，最后逐条接入入库 / 补全 RPC。

### `clothing_contributions` 贡献者记录

- 第一版目标：记录正式条目的有效贡献者、来源 pending、贡献类型、积分状态；支持前 5 有效提交者和前 3 展示。
- 不做什么：不做荣誉权益，不做复杂排序 UI，不补造匿名历史用户。
- 依赖对象：`pending_clothes.submitted_by`、`clothes`、`user_wardrobes`、自动入库 RPC、管理员仲裁 RPC、正式库补全 RPC。
- 第一版口径：与最终入库数据一致的提交者按提交时间取前 5 获得积分；前 3 展示贡献者从前 5 中按提交时间取前 3。
- 已确认：所有来源 pending 持久保留；初始入库只奖励一次，后续独立事件可分别奖励；账号删除后保留并匿名化审计事实。
- 开发风险：有效提交者、衣柜写回用户、积分发放用户三者不一致；管理员纳入错误 pending 后污染贡献记录。
- 建议顺序：先建立贡献者表和唯一约束，再接入当前已验证的入库 / 补全路径，最后补前端只读展示。

### `re_review_items` 重审池

- 第一版目标：记录缺套装、字段冲突、字段缺失、报错转入等需要复核的数据，并保留来源和处理结果。
- 不做什么：不做完整陪审团投票，不允许普通用户直接覆盖正式库，不迁移全部历史 pending。
- 依赖对象：`pending_clothes`、`clothes`、后续 `correction_requests`、`ClothesEntryForm.vue`、管理员审核入口。
- 第一版口径：缺套装但编号完整的数据允许正式入库，同时创建 `re_review_items`，状态为待补套装。
- 社区入口：未参与原始提交的登录用户可查看开放项并提交一份候选修正版；每个重审项第一版只保留一份不可修改候选，后续投票与状态处理另行接入。
- 开发风险：状态过多导致积压；绑定正式套装后未自动关闭待补状态；重审直接改正式库破坏审计。
- 建议顺序：先建表、状态和来源枚举，再接入字段冲突 / 缺套装来源，最后接报错转重审。

### `correction_requests` 报错修正

- 第一版目标：记录用户对正式库条目的错误报告和建议修正，形成待处理状态。
- 不做什么：不做留言板建议、不做点赞排序、不自动覆盖正式库、不即时扣分。
- 依赖对象：`clothes`、`profiles`、管理员权限函数、后续 `re_review_items`。
- 已确认边界：空字段补全走管理员审核；非空字段修改或争议修正进入审核库和陪审团路径；报错通过 +5；扣回只追加负数流水。
- 已实现受理面：`submit_correction_request(varchar,text,jsonb)` 只接受登录用户、现有正式服装和单一允许字段；同内容重试幂等，不同内容不得覆盖活动报错。`get_my_correction_requests()` 只返回当前用户本人记录。
- 已实现安全面：底表启用 RLS 且不给 `anon/authenticated` 直表权限；两个 `SECURITY DEFINER` RPC 使用空 `search_path`、函数内校验 `auth.uid()`，只授予 authenticated / service_role 执行。
- 当前状态：development 已应用受理 migration 与独立最小权限 patch；service_role 仅保留 SELECT / INSERT / UPDATE，增强回滚 fixture、权限和类型回读均已完成。
- 开发风险：报错直接覆盖正式库；全部报错都进管理员终审造成积压；积分扣回规则未定导致争议。
- 建议顺序：提交和查询能力已完成；下一步接管理员处理状态，最后把非空字段修改和争议修正转入重审池。

### 阶段级顺序

1. 先做 `clothing_contributions` + `points_ledger`，让当前入库和补全主流程具备贡献与积分审计能力。
2. 再做 `re_review_items`，承接无法直接入库或需要补全的数据。
3. 再做 `correction_requests`，让正式库报错有独立入口。
4. `jury_votes`、排行榜相关 RPC / view、普通管理员轮换继续后置。

### 0.3.3 已确认缺口

- **来源追溯**：DB-5 已在 development 改为当前提交先落 pending、统一保留为 `approved`；live function definition、事务 fixture 和真实并发结果均已验证。
- **前 5 排名**：DB-5 按每位用户最早来源去重，再以时间、pending ID、用户 ID 稳定排序取 5；事务 fixture 已验证稳定前 5，第五 / 第六位并发只形成一个完整事件。
- **服务端一致性**：管理员仲裁的 `p_pending_ids` 来自前端，RPC 当前未逐条证明其 payload 与最终入库数据一致；前端聚类不能替代数据库校验。
- **生成产物**：`src/types/supabase.ts`、`supabase/schema.sql`、`docs/database/schema.md` 已按 development 重新生成或核验，DB-3 至 DB-5 对象均已同步。
- **权限面**：DB-3 至 DB-5 特权 RPC 已逐个验证 `auth.uid()` / 管理员校验、函数 `search_path`、可执行角色和 Security Advisor；底表权限未放宽。
- **读取面**：Supabase 的 Data API 暴露、table grants 与 RLS 是独立层；`security_invoker` view 仍依赖底层表权限，不能以“已启用 RLS”替代角色矩阵验证。
- **工具边界**：Supabase RLS Tester feature preview 当前已暂停，不作为验收依赖；使用可审计 SQL / 客户端角色测试和 Security Advisor。

### 0.3.4 第一阶段不变量

- 贡献记录、积分流水和原有衣柜写回由同一个数据库事务生成。
- 每条贡献必须关联持久保留的来源 pending；不可变快照可以补充，但不能替代来源记录。
- 只有与最终入库数据一致、`submitted_by` 为真实用户的提交参与排名。
- 先按提交时间升序，再按用户保留最早一条，最后取前 5；贡献排名和衣柜写回用户必须使用同一结果集。
- 同一次初始入库的自动 / 仲裁路径互斥且每个用户只奖励一次；后续独立有效行为可以再次奖励。
- 一条来源事件最多对应一条贡献和一条积分流水；重试不得重复写入。
- `points_ledger` 只追加，不允许客户端 UPDATE / DELETE；总分由 `sum(delta)` 重算。
- 基础表 PR 默认不开放 public view、不接入现有 RPC、不做历史回填。
- 任一新表位于 exposed schema 时启用 RLS，并单独确认 Data API 暴露与 grants。

### 0.3.5 推荐验证证据

后续 database PR 的完成证据至少包括：development project ref、migration list、前后 schema / types diff、重复键前检、角色矩阵、Security / Performance Advisor、RPC 重试幂等、事务失败回滚、原提交 / 审核 / 衣柜写回回归以及旧函数定义备份。详细操作和用户验收手册见 [`开发文档.md`](开发文档.md) 第 0.3.3 节。

### 0.3.6 Supabase 当前依据

- [Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security)：`public` 等 exposed schema 中的新表必须启用 RLS；`security_invoker` view 用于让底层 RLS 生效，但仍需验证底层权限。
- [Performance and Security Advisors](https://supabase.com/docs/guides/database/database-advisors)：development apply 后检查 RLS、`security definer` view / function、可变 `search_path`、未索引外键等告警。
- [Breaking changes](https://supabase.com/changelog?tags=breaking-change)：新表可能不再自动暴露到 Data / GraphQL API；验证时必须同时记录 Data API 设置、table grants 和 RLS。
- [RLS Tester feature preview](https://supabase.com/changelog/45233-feature-preview-rls-tester)：该预览已暂停，不能作为本项目验收前置；使用明确角色的 SQL / 客户端测试替代。

## 2. 总体架构

推荐把后续功能分为四层：

| 层级 | 职责 | 主要文件 / 对象 |
| --- | --- | --- |
| 数据层 | 表结构、约束、RLS、索引 | Supabase migrations |
| 业务过程层 | 自动入库、投票、积分、重审流转 | Postgres RPC |
| API 封装层 | 前端调用数据库 / RPC | `src/api/*.js` |
| UI 状态层 | 页面展示、表单复用、交互反馈 | `src/views/*`、`src/components/*`、`src/composables/*` |

核心原则：

- 涉及积分、投票、入库、重审状态变更的操作优先放在 RPC 中。
- 前端只提交用户意图，不在浏览器里决定最终入库和积分。
- 所有关键行为保留来源记录，避免后续无法追溯。

## 3. 数据库实现方案

### 3.1 `clothes` 调整

用途：承接“缺套装但编号完整，可进入正式库，并标记待补套装”的查询需求。

可选字段：

```sql
alter table public.clothes
add column if not exists needs_suit_review boolean not null default false;
```

已确认：

- 缺套装待补状态的权威流程使用 `re_review_items` 追踪。
- `clothes.needs_suit_review` 仅作为可选查询加速 / 冗余标记，不作为权威状态来源。

### 3.2 `clothing_contributions`

用途：记录正式入库后的贡献者、来源提交和贡献类型；积分值只记录在 `points_ledger`，本表不保存 `awarded_points` 或积分状态副本。

2026-07-16 已审定 DB-1 字段契约如下；它是后续独立 database PR 的实现输入，不代表已授权创建 migration：

| 字段 / 约束 | 要求 |
| --- | --- |
| `id` | `uuid primary key default gen_random_uuid()`，供 ledger 幂等引用 |
| `event_id` | `uuid not null`，由未来写入 RPC 为同一次业务裁决稳定生成并在重试时复用；不设置随机默认值 |
| `clothes_id` | `varchar not null references public.clothes(id) on delete restrict`；正式衣物存在贡献事实时不得直接删除 |
| `user_id` | `uuid null references auth.users(id) on delete set null`；账号删除后保留事实并展示为“已注销用户” |
| `source_pending_id` | `bigint not null references public.pending_clothes(id) on delete restrict`；来源 pending 必须持久保留 |
| `contribution_type` | `text not null`，仅允许 `auto_entry`、`admin_arbitration`、`existing_field_completion` |
| `contribution_rank` | `smallint not null`，仅允许 1～5，按来源提交时间稳定排序后生成 |
| `source_created_at` | `timestamptz not null`，保存用于排名的来源提交时间 |
| `created_at` | `timestamptz not null default now()`，记录贡献事实写入时间 |

DB-1 必须建立以下幂等约束和索引：

- `unique (source_pending_id)`：一条来源 pending 最多形成一条贡献事实。
- `unique (event_id, contribution_rank)`：同一业务事件的排名不可重复。
- `unique (event_id, user_id)`：同一真实用户在同一事件中只保留一次；`user_id` 置空后仍保留历史事实。
- `unique (clothes_id, user_id) where user_id is not null and contribution_type in ('auto_entry', 'admin_arbitration')`：自动入库与管理员仲裁共享初始奖励组，同一衣物、同一用户只能获得一次初始贡献。
- 为 `clothes_id`、`user_id` 建立查询索引；唯一约束已有的索引不重复创建。

第一版贡献者口径：

- 与最终入库数据一致的提交者，按 `pending_clothes.created_at` 提交时间排序，取前 5 个作为有效提交者并获得积分。
- 页面展示贡献者从前 5 个有效提交者中按提交时间取前 3。
- 同一用户多次提交时只保留最早一条进入本次排名。
- 匿名历史数据不补造真实用户。
- 贡献者写入必须和积分流水、原有衣柜写回处于同一事务。

### 3.3 `points_ledger`

用途：积分唯一权威流水。总分、月榜、扣回都应从流水计算。

2026-07-16 已审定 DB-1 字段契约如下；它是后续独立 database PR 的实现输入，不代表已授权创建 migration：

| 字段 / 约束 | 要求 |
| --- | --- |
| `id` | `uuid primary key default gen_random_uuid()` |
| `user_id` | `uuid null references auth.users(id) on delete set null`；账号删除后保留流水和 delta |
| `delta` | `integer not null` 且非零；正数发放、负数扣回 |
| `status` | `text not null default 'awarded'`，DB-1 仅允许 `awarded` |
| `source_type` | `text not null`，仅允许 `clothing_contribution` 或 `reversal` |
| `source_id` | 发放流水指向 `clothing_contributions(id) on delete restrict`；扣回流水必须为空 |
| `reversal_of` | 扣回流水指向原 `points_ledger(id) on delete restrict`；发放流水必须为空 |
| `occurred_at` | `timestamptz not null default now()`；UTC+8 月份在查询时派生，不存重复字符串 |
| `created_at` | `timestamptz not null default now()`，记录流水写入时间 |

DB-1 必须建立以下形状约束和索引：

- 发放：`source_type = 'clothing_contribution'`、`source_id is not null`、`reversal_of is null`、`delta > 0`。
- 扣回：`source_type = 'reversal'`、`source_id is null`、`reversal_of is not null`、`delta < 0`。
- `source_id` 在发放流水中局部唯一，保证一条贡献只发放一次。
- `reversal_of` 在扣回流水中局部唯一，DB-1 只支持对原流水进行一次完整反向；部分扣回或多次调整如有业务需求必须另行决策。
- 为 `(user_id, occurred_at desc)` 建立查询索引。

规则：

- `points_ledger` 只允许追加；客户端和普通管理入口均不得 UPDATE / DELETE。
- 自动入库 / 管理员仲裁写入 `delta = 10`，正式库空字段补全写入 `delta = 5`。
- 后续重审修正写入 `delta = 8`、报错通过写入 `delta = 5`，但不在第一阶段接入。
- 扣回通过新的负数流水实现，原流水不修改、不删除。
- `profiles` 中历史积分字段不作为权威来源；用户总分和月积分由 ledger 聚合重算。
- 首个基础表 PR 不创建排行榜、缓存或 public summary view。
- DB-1 不通过触发器或跨表检查固化具体分值；+10 / +5 与用户一致性由未来接入 RPC 在同一事务内校验。
- 未来扣回 RPC 必须校验 `reversal_of` 指向正向发放流水、用户一致且 `delta` 与原值完全相反；DB-1 不用触发器提前接入这段业务逻辑。

### 3.8 DB-2 最小只读面

DB-2 只建立两个查询结果面，DB-1 两张基础表继续保持客户端零授权、RLS 无 policy。不能直接用普通 `security_invoker` view 查询底表：该模式要求调用者拥有底层关系权限，会迫使 `anon` / `authenticated` 获得底表 `SELECT`，扩大 Data API 面。

实施状态：migration `20260717050640_db2_create_read_surfaces` 已在 development 应用，并由 PR #83 合入 `develop`；角色矩阵、Data API 隔离、fixture rollback、Advisor、schema / types、tests 与 build 均已完成验证。

#### 3.8.1 对象结构

| 对象 | 安全属性 | 用途 |
| --- | --- | --- |
| `private_db2.current_user_points()` | 非 exposed schema；`SECURITY DEFINER`；`STABLE`；`search_path = ''` | 按 `auth.uid()` 聚合当前用户全部 `awarded` 正负流水 |
| `private_db2.public_initial_contributors()` | 非 exposed schema；`SECURITY DEFINER`；`STABLE`；`search_path = ''` | 生成每件服装初始入库贡献者的安全公开字段并稳定取前 3 |
| `public.user_points_summary` | `security_invoker = true`；`security_barrier = true`；只读 | Data API 中当前用户积分结果面 |
| `public.clothing_contributors_public` | `security_invoker = true`；`security_barrier = true`；只读 | Data API 中贡献者公开结果面 |

`private_db2` 必须不在 PostgREST exposed schemas 中。helper 全部使用全限定对象名、无动态 SQL、无 DML；创建后立即撤销 `PUBLIC` / `anon` / `authenticated` / `service_role` 的默认权限，再只授予 view 执行所需的 schema `USAGE` 与精确函数 `EXECUTE`。两个 public view 同样先撤销全部默认权限，再最小授权。

#### 3.8.2 输出契约

`public.user_points_summary`：

| 字段 | 类型 | 规则 |
| --- | --- | --- |
| `total_points` | `bigint` | `coalesce(sum(delta) filter (where status = 'awarded'), 0)`；只聚合 `user_id = auth.uid()` |

该 view 不返回 `user_id`、流水明细、来源或时间。`auth.uid()` 为空时返回 0，不允许借参数查询其他用户。

`public.clothing_contributors_public`：

| 字段 | 类型 | 规则 |
| --- | --- | --- |
| `clothes_id` | `varchar` | 正式服装 ID |
| `contribution_rank` | `smallint` | 每件服装稳定排序后的 1～3 |
| `display_name` | `text` | 删除账号显示“已注销用户”；有 `username` 使用去空格值；否则使用稳定匿名代号 |
| `contributed_at` | `timestamptz` | 贡献来源时间 |

公开贡献者只包含 `auto_entry` 与 `admin_arbitration`。按 `clothes_id` 分组，以 `source_created_at`、原 `contribution_rank`、`created_at`、`id` 稳定排序后重新编号并取前 3；不得返回 `user_id`、email、nickname、完整 UUID、`event_id`、`source_pending_id` 或积分。

#### 3.8.3 角色矩阵

| 对象 / 行为 | anon | 普通用户 | admin | super admin |
| --- | --- | --- | --- | --- |
| DB-1 两张底表 SELECT / 写入 | 拒绝 | 拒绝 | 拒绝 | 拒绝 |
| `user_points_summary` SELECT | 拒绝 | 仅自己 | 仅自己 | 仅自己 |
| `clothing_contributors_public` SELECT | 公开字段 | 公开字段 | 公开字段 | 公开字段 |
| 两个 public view 写入 | 拒绝 | 拒绝 | 拒绝 | 拒绝 |
| `private_db2` Data API / RPC | 不可见 | 不可见 | 不可见 | 不可见 |

admin 与 super admin 在 DB-2 不获得跨用户积分查询；后续管理查询必须另建接口并独立评审。

#### 3.8.4 Data API 与失败处理

- `public` view 依靠显式 SELECT grant 暴露；grants 决定对象可达，helper 的鉴权与输出约束决定结果范围，不能只依赖平台默认值。
- `private_db2` 一旦出现在 exposed schemas，立即停止 apply；不得通过前端隐藏或仅撤销 view grant 补救。
- 匿名读取积分应得到权限错误；未知 `clothes_id` 过滤结果为空；过期 token 降为 anon 后同样不能读积分。
- 新增 Advisor WARN / ERROR、底表 grant / policy 漂移、view 可写、helper 可从 Data API 直接调用、跨用户积分可见或公开字段超出契约，任一项即判定失败。

后续可扩展但不属于 DB-2：

- `monthly_points_summary`
- `leaderboard_current_month`
- `leaderboard_last_month`
- `user_privilege_summary`
- `user_points_cache`，可选缓存表，仅作展示加速，不作为权威来源

## 4. RPC 实现方案

### 4.1 `submit_clothing_contribution`

现状：已有 RPC 负责提交缺失项，并在 5 次一致时自动入库。

改造目标：

1. 防止重复提交污染 5 次一致判断。
2. 自动入库时写入 `clothing_contributions`。
3. 自动入库时写入 `points_ledger`。
4. 缺套装但编号完整时进入正式库，并写入 `re_review_items` 追踪套装待补状态。
5. 字段冲突时转入 `re_review_items` 或管理员仲裁。

建议返回结构：

```json
{
  "status": "pending | approved | re_review | rejected",
  "clothes_id": "string | null",
  "re_review_item_id": "uuid | null",
  "pending_count": 1,
  "message": "string",
  "needs_suit_review": false
}
```

已确认：

- 积分第一版默认 `awarded`。
- 与最终入库数据一致的提交者按提交时间取前 5 个获得积分。

已确认：缺编号、`N` 或其他非数字短编号不通过提交 / 入库校验，也不进入积分判断分支。

### 4.2 `cast_jury_vote`

用途：处理陪审团投票。

建议参数：

```sql
cast_jury_vote(
  p_candidate_id uuid,
  p_vote text
)
```

RPC 内部职责：

1. 获取当前用户。
2. 判断是否自审。
3. 校验审核项绑定的是当前完整且未过期的待审核资料。
4. 按一人一票插入 `jury_votes`。
5. 统计同意票和反对票。
6. 按顺序触发三分支状态流转：
   - 同意票数 >= 5 且同意票数 > 反对票数时通过，按本轮完整资料修改正式库。
   - 反对票数 - 同意票数 >= 3 时退回重审，要求重新补充完整资料，不修改正式库、不关闭审核项。
   - 其他情况保持投票状态。

已确认：

- 管理员可按普通陪审员身份投一票；投票后不能终审同一审核项。
- 管理员终审写入独立终审记录，不写入 `jury_votes`。
- 永久驳回只能由未参与该项投票的管理员通过独立终审决定，不能由反对票门槛自动触发。

## 6. 权限与 RLS 方案

### 6.1 角色

| 角色 | 来源 | 权限 |
| --- | --- | --- |
| 匿名用户 | 未登录 | 只读公开数据 |
| 普通用户 | `auth.users` | 提交、投票、报错、查看公开审核项 |
| 普通管理员 | `profiles.role = admin` 或 `admin_terms` | 处理低风险项 |
| 超级管理员 | `profiles.role = super_admin` | 终审、授权、处理高风险项 |

### 6.2 RLS 原则

- DB-1：`points_ledger` 与 `clothing_contributions` 均启用 RLS、不创建 policy，并撤销 `PUBLIC`、`anon`、`authenticated` 全部表权限；所有客户端角色直接读写均拒绝。
- DB-2：普通用户、admin、super admin 均只能通过 `user_points_summary` 读取自己的积分汇总；贡献者公开展示通过 `clothing_contributors_public` 提供。跨用户管理汇总或积分流水仍须另建独立只读接口，不得放宽 DB-1 基础表权限。
- 未来写入：只允许经过独立审计的内部 RPC 在同一事务内追加，不向客户端开放基础表 INSERT / UPDATE / DELETE。
- `jury_votes`：用户可写自己的投票；不可改他人投票；结果汇总可公开。
- `re_review_items`：开放可参与项；隐藏涉及自己提交且不可自审的审核入口。
- `correction_requests`：用户只能通过受控 RPC 创建和查看自己的报错；底表默认拒绝客户端直读写。管理员处理仍由后续独立 RPC 接入。

### 6.3 防自审策略

防自审必须在数据库层实现，前端隐藏只是体验优化。

建议判断来源：

- `pending_clothes.submitted_by`
- `pending_suits.submitted_by`
- `clothing_contributions.user_id`
- `correction_requests.reported_by`
- `re_review_items.submitted_by`

## 8. 积分与等级实现

### 8.1 积分计算

推荐规则：

- 只从 `points_ledger` 计算权威总分。
- DB-1 只允许 `status = awarded` 并计入正式总分；如未来引入 `pending`，必须另行决策并修改约束。
- 扣回通过负数流水实现。
- `profiles` 不保存权威总分。
- view / RPC 用于实时汇总；缓存表只能用于展示加速。

### 8.2 等级计算

可继续复用 `src/composables/useUserPrivilege.js` 的等级规则：

| 等级 | 门槛 | 陪审团计票 |
| --- | --- | --- |
| Lv1 | 500 | 1 |
| Lv2 | 2000 | 1 |
| Lv3 | 5000 | 1 |
| Lv4 | 10000 或当月榜首 | 1 |

已确认：等级只用于排序和展示，不影响陪审团票数、自动入库或积分计算。

### 8.3 排行榜

建议实现方式：

1. 第一版用 SQL view / RPC 实时计算。
2. 数据增长后再做月榜快照表。
3. 每月 1 日 UTC+8 冻结上月榜。

待确认：

- 月榜冻结由数据库定时任务、手动触发，还是前端读取时计算。
- 上月前 10 权益是广告免除权、首页鸣谢，还是两者都有。

## 10. 测试方案

### 10.1 数据库测试用例

必须覆盖：

1. 同一用户重复提交不计入 5 次一致。
2. 5 个不同有效提交者完全一致后自动入库。

## 11. 上线与回滚策略

### 11.1 上线顺序

1. 先上只新增表 / 字段 / 约束的 migration。
2. 再上 RPC，但前端不立即展示入口。
3. 小范围接入提交与积分流水。
4. 接入陪审团和重审入口。
5. 最后接入排行榜和权益展示。

### 11.2 回滚思路

- 新增表字段一般不立刻删除，先停用入口。
- RPC 可保留旧版本兼容，新增版本使用新函数名或参数默认值。
- 前端入口可通过条件渲染关闭。
- 积分错误用 `points_ledger` 追加反向流水，不直接删除旧流水。
